# Internationalisation & Localisation

The requirement: the application must support **every language**. That covers not just
translation, but timekeeping, sorting, search, text direction, and formats.

---

## 1. The ground rule: the server delivers no display text

Every human-facing output of the API consists of a **code plus parameters**, never a finished
sentence:

```json
{
  "code": "activity.item_completed",
  "params": { "actor": "Anna", "item_title": "Review the quote", "at": "2026-08-14T09:12:00Z" }
}
```

This makes every language possible without a backend change (quality scenario QS-08), and the same
event can appear in different languages in different clients.

**Exceptions** where the server does have to render (email, push, ICS feed, PDF export): rendering
goes through the `i18n` port using the locale of the **recipient**, not of the trigger.
The catalogue is embedded in the binary (`embed`) and can additionally be overridden from a
directory.

## 2. The locale model

| Level | Field | Resolution priority |
|---|---|---|
| Request | `Accept-Language` | 1 (only for anonymous/client responses) |
| Account | `account.locale`, `account.time_zone`, `account.week_start?` | 2 |
| Tenant | `tenant.default_locale`, `tenant.default_time_zone` | 3 |
| Installation | `HUBTASK_DEFAULT_LOCALE`, `HUBTASK_DEFAULT_TIMEZONE` | 4 |

* Locale format: **BCP 47** (`de`, `de-DE`, `de-AT`, `pt-BR`, `zh-Hans`, `ar-EG`).
* Negotiation through `golang.org/x/text/language` (`language.NewMatcher`) with the fallback chain
  `de-AT → de → en`.
* Time zones: **IANA** (`Europe/Berlin`), never fixed UTC offsets. Time zone data is embedded via
  `time/tzdata`, so the container needs no system tzdata.
* The permitted locales are data, not constants: `/meta/capabilities` returns `supported_locales`
  (derived from the catalogue files present).

## 3. The message catalogue

| Aspect | Decision |
|---|---|
| Format | **ICU MessageFormat** (plural, select, gender, nested arguments) |
| Files | `locales/<locale>.json`, source language `en` |
| Keys | Hierarchical and semantic: `errors.capability_not_supported`, `activity.item_completed`, `email.reminder.subject` |
| Plural rules | CLDR categories (`zero/one/two/few/many/other`) — required for Arabic, Polish, Russian |
| Translation process | Weblate or Crowdin against `locales/en.json`; community contributions by pull request |
| CI | Missing keys = warning, unknown keys = error; placeholder consistency is checked |
| Fallback | A missing translation falls back to the source language, never to an empty string or a key name in the UI |

## 4. Date, time, calendar

| Topic | Rule |
|---|---|
| Storage | `timestamptz` (UTC) plus the relevant IANA time zone stored separately where local time matters to the business logic (due dates, reminders, recurrence) |
| All-day due dates | `due_date_only = true`; interpreted as a date without a time in the user's time zone |
| Recurrence | RFC 5545 RRULE plus a time zone; DST transitions are resolved via local time (09:00 stays 09:00) |
| Reminders | Relative (`-PT30M` before the due date) or absolute. **The entry's zone decides when it fires, the recipient's decides how it reads.** `fire_at` is one instant and cannot be several: an all-day due date is counted from the start of its day in its own zone (`DueDate.Anchor`), and the message is then rendered in the recipient's locale and zone like every other notification (§1). The earlier wording — "firing accounts for the recipient's time zone" — could not be true of one column, and three recipients in three zones would have needed three reminders (D-03) |
| Start of week | From CLDR per locale, overridable per account (calendar week views) |
| Calendar weeks | ISO-8601 by default, the CLDR variant where it differs (`en-US`, for example) |
| Non-Gregorian calendars | Display is the client's business (the server delivers instants); ICS feeds stay Gregorian per RFC 5545 |
| Working hours and holidays | Not part of 1.0; planned as a `WorkCalendar` extension (the automation condition "on working days only") |

## 5. Text: storage, comparison, search

| Topic | Rule |
|---|---|
| Encoding | UTF-8 throughout; database encoding `UTF8`, collation `und-x-icu` (locale-independent, stable sorting) |
| Normalisation | Input is NFC-normalised (`golang.org/x/text/unicode/norm`) before being stored or compared |
| Length limits | In Unicode code points (grapheme clusters for title truncation in clients) |
| Uniqueness | Bucket and label names are case- and accent-insensitive per scope (`unaccent` + `lower`) |
| Sorting in the UI | Server-side `ORDER BY name COLLATE "und-x-icu"`; alternatively client-side sorting with `Intl.Collator` |
| Full-text search | `tsvector` with a language-dependent configuration; an item's language is set (`item.content_language`), defaulting to the creator's locale; fallback `simple` for a language the installation has no configuration for, CJK included. The document is maintained by a trigger rather than generated, and the configuration is resolved from the catalogue at write time ([ADR-0034](../adr/ADR-0034-language-dependent-search.md)). Detection from the text itself is not implemented: it would be a dependency, and a client that knows its own language can say so |
| CJK/Thai | The `simple` configuration plus a trigram index (`pg_trgm`) as a supplement, so search works without word boundaries |
| Semantic search | Optional, via embeddings (pgvector) — cross-lingual, and it covers the weaknesses of lexical search |

## 6. Text direction and presentation

The server makes no layout decisions but supplies the necessary metadata: `/meta/capabilities`
contains, per supported locale, `{ "locale": "ar-EG", "direction": "rtl", "week_start": "sat",
"decimal_separator": "." }`. Frontends must support RTL — documented as a binding requirement for
the frontend that will be specified later.

Colours are carried as **tokens** (`color.red.500`) rather than hex values, so that themes,
contrast modes, and accessibility stay solvable in the frontend; custom hex values are additionally
allowed.

## 7. Other localisation-relevant points

| Point | Implementation |
|---|---|
| Names and forms of address | Only `display_name`, no split into first and last name (not culturally universal) |
| Email addresses | IDN-capable validation (Punycode normalisation) |
| Slugs and URLs | Transliteration to ASCII for slugs, but display always through `display_name` |
| Numbers and units | CLDR formatting in the client; the API returns raw values |
| Timestamps in events and webhooks | Always RFC 3339 in UTC plus a `time_zone` field where relevant |
| Translatable user data | Item titles and similar are user content and are **not** translated (optional AI translation as a suggestion, never persisted automatically) |
