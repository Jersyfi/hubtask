# Internationalisation & Localisation

The requirement: the application must support **every language**. That covers not just
translation, but timekeeping, sorting, search, text direction, and formats.

---

## 1. The ground rule: the server delivers no display text

Every human-facing output of the API consists of a **code plus parameters**, never a finished
sentence ([ADR-0011](../adr/ADR-0011-i18n-message-codes.md)):

```json
{
  "code": "activity.item_completed",
  "params": { "actor": "Anna", "item_title": "Review the quote", "at": "2026-08-14T09:12:00Z" }
}
```

This makes every language possible without a backend change (quality scenario QS-08), and the same
event can appear in different languages in different clients.

**Exceptions** where the server does have to render: **email**, and the sentences `hubctl` shows a
person. Rendering goes through the `i18n` port using the locale of the **recipient**, not of the
trigger — the account's own, else the workspace's default, else the installation's (§2). The ICS
feed is not an exception: it composes no sentence, only a title somebody wrote, two timestamps and
a link. The product has no push notifications and no PDF; the one notification channel is `EMAIL`.

The catalogues are embedded in the binary (`embed`, every `locales/*.json`) and can additionally be
overridden from a directory, `HUBTASK_LOCALE_DIR`: a file for a tag the binary carries overrides it
key by key, and a file for a new tag adds the locale.

## 2. The locale model

| Level | Field | For a signed-in person | For an anonymous request |
|---|---|---|---|
| Account | `account.locale`, `account.time_zone`, `account.week_start?` | 1 | — |
| Request | `Accept-Language` | 2 | 1 |
| Tenant | `tenant.default_locale`, `tenant.default_time_zone` | 3 | — |
| Installation | `HUBTASK_DEFAULT_LOCALE`, `HUBTASK_DEFAULT_TIMEZONE` | 4 | 2 |

A preference somebody set on their account is not overridden by whichever browser they happen to
be sitting at; the header decides only where no account has spoken. The server resolves the chain
in `AuthenticateToken` and the client in `locale.ts`, by the same rule.

* Locale format: **BCP 47** (`de`, `de-DE`, `de-AT`, `pt-BR`, `zh-Hans`, `ar-EG`).
* Negotiation through `golang.org/x/text/language` (`language.NewMatcher`), built once over the
  catalogues present with the source language as the default, and used by the REST middleware and
  the renderer alike ([ADR-0056](../adr/ADR-0056-golang-x-text-and-idna.md)): `de-AT` lands on
  `de` when that is what there is, `pt-BR` prefers `pt-BR` over `pt`, and `fr, de;q=0.8` on an
  installation with German and no French lands on German. What travels on the actor is the
  client's own tag, region and all — an entry's content language and the week a person starts on
  want the region — and the catalogue is matched again at render time, down the chain
  `de-AT → de → en`.
* An `Accept-Language` the matcher cannot place, or one that is malformed or over the bound,
  resolves to the installation default and is **never refused**: a wrong language is a nuisance, a
  refused request an outage.
* Time zones: **IANA** (`Europe/Berlin`), never fixed UTC offsets. Time zone data is embedded via
  `time/tzdata`, so the container needs no system tzdata.
* The permitted locales are data, not constants: `/meta/capabilities` returns `supported_locales`,
  derived from the catalogue files present — the embedded ones and an operator's
  `HUBTASK_LOCALE_DIR` (§1) — so that adding a language is a file and not a release. Each entry
  carries the locale's direction, week start and decimal separator (§6). The account's language
  picker is this list.
* **The `1.0` locale set** is eleven: the ten most spoken languages by total speakers (Ethnologue
  2025) and German — `en`, `zh-Hans`, `hi`, `es`, `ar`, `fr`, `bn`, `pt`, `ru`, `id`, `de`. A
  locale is *selectable* when its catalogue file is present; the binary carries `en` and `de`. The
  metadata table behind §6 covers all eleven, so a catalogue that arrives is fully described the
  moment it does.

## 3. The message catalogue

| Aspect | Rule |
|---|---|
| Format | **ICU MessageFormat**, in the subset below |
| Files | `locales/<locale>.json`, one flat file per locale, source language `en` |
| Keys | Hierarchical and semantic: `errors.capability_not_supported`, `activity.item_completed`, `email.reminder.subject`. A key beginning with `_` is a note to translators, not a message, and both renderers skip it in every file |
| Plural rules | CLDR categories (`zero/one/two/few/many/other`) — required for Arabic, Polish, Russian |
| Register | A translation keeps one register through its whole file — the second person of [voice-and-tone.md](../design/voice-and-tone.md) 1.4, in German the informal *du*. A code whose English is a placeholder stays a placeholder |
| Translation process | Pull requests against `locales/`, in a layout Weblate reads unchanged; `CONTRIBUTING.md` § "Translating" says how, `make locales` says how far, the gate says what is wrong. A catalogue is translated by hand by somebody who reads the language: a machine translation nobody read is not shipped, because the source-language fallback is better than a catalogue that only claims to be German. A Weblate instance is deferred until there is a translator to serve ([ADR-0055](../adr/ADR-0055-translation-process.md)) |
| CI | `test/architecture/translations_test.go` (`make gate-architecture`): an unknown key fails, a placeholder that differs from the source fails, a missing key is reported by family and does not fail; the loader refuses a message outside the ICU subset and a key written twice, in every catalogue. `make locales` prints the same coverage, per family, for a contributor |
| Fallback | A missing translation falls back to the source language, never to an empty string or a key name in the UI |

### Two renderers, one catalogue

`locales/en.json` is read by both halves of the product, and neither of them has a copy of it. The
Go binary embeds it through `locales/Embed.go`; the client imports the same path from
`apps/webapp/src/lib/i18n/catalogue.ts`, which is the one place in the workspace allowed to reach
out of its own member for it (`project-structure.md` §2.1). The client bundles the source
catalogue and loads every other catalogue lazily, one chunk per file, when the resolved locale asks
for it.

They implement **the same subset of ICU**, and each side has a gate that says so:

* simple arguments, `plural` with `offset:` and `=n`, `selectordinal`, `select`, `#` inside a
  plural, nested messages in every branch, and ICU's apostrophe quoting;
* everything else — `number`, `date`, `time`, any other argument type — is **refused by name**
  when the message is parsed. A date reaches a message as text that was formatted first (§4).

The CLDR plural categories come from each side's platform: `Intl.PluralRules` in the browser,
`golang.org/x/text/feature/plural` in the binary ([ADR-0056](../adr/ADR-0056-golang-x-text-and-idna.md)).
`catalogue.test.ts` parses every message of every catalogue for the client; the Go catalogue
loader parses every message of **every** catalogue — embedded or laid over by an operator (§1) —
and refuses the file on the first construct outside the subset, so the refusal is heard when the
message is written or when the installation starts, never when a recipient reads Polish.
`infrastructure/i18n/Message_test.go` mirrors `format.test.ts` case for case.

The one deliberate difference: the client groups digits through `Intl.NumberFormat` (`1,234`).
The server carries no number symbols — the locale metadata of §6 is a table, not CLDR data — and
writes a number as it was given. The only numbers it renders are counts and limits.

The consequence is a rule about the catalogue: **a message may use what the subset implements**, in
the source and in every translation, and a construct beyond it is extended on both sides first. The
source language phrases around plurals where it can (a count last, after a colon); a translation
that cannot may use `plural`, and renders the same in an email as on a screen.

Client-only display text lives in the same file, under `app.*`. A second catalogue under `apps/` is
the one thing a source of truth must not have.

## 4. Date, time, calendar

| Topic | Rule |
|---|---|
| Storage | `timestamptz` (UTC) plus the relevant IANA time zone stored separately where local time matters to the business logic (due dates, reminders, recurrence) |
| All-day due dates | `due_date_only = true`; interpreted as a date without a time in the user's time zone |
| Recurrence | RFC 5545 RRULE plus a time zone; DST transitions are resolved via local time (09:00 stays 09:00) |
| Reminders | Relative (`-PT30M` before the due date) or absolute. **The entry's zone decides when it fires, the recipient's decides how it reads.** `fire_at` is one instant: an all-day due date is counted from the start of its day in its own zone (`DueDate.Anchor`), and the message is rendered in the recipient's locale and zone like every other notification (§1) |
| Start of week | From CLDR per locale, overridable per account: `account.week_start` where set, otherwise the locale's row (§6's table, through the same matcher a message is rendered through, so `de-AT` reads `de`'s), otherwise Monday. Resolved onto the actor by authentication and read by the query language's `@start_of_week` and `@end_of_week` — two colleagues reading one saved view may see two weeks, and each sees their own |
| Calendar weeks | ISO-8601 by default, the CLDR variant where it differs (`en-US`, for example). A week *number* is the client's to draw (`Intl` knows both); the server shows nobody one. Its only week number is the backup expiry's bucket, which is ISO by design |
| Non-Gregorian calendars | Display is the client's business (the server delivers instants); ICS feeds stay Gregorian per RFC 5545 |
| Working hours and holidays | Not part of 1.0; planned as a `WorkCalendar` extension (the automation condition "on working days only") |

## 5. Text: storage, comparison, search

| Topic | Rule |
|---|---|
| Encoding | UTF-8 throughout; database encoding `UTF8`. The collation names sort under is the **query's**, not the database's: migration `0080` defines `hubtask_name` from `und-x-icu` (the ICU root collation — locale-independent, stable, the same on every installation) where PostgreSQL was built with ICU, and from the database's own locale where it was not, and every name-ordered read says `COLLATE hubtask_name` (a gate holds them to it). A database's own collation is an `initdb` decision no migration can reach, which is why the promise is made per query. No index is built on `hubtask_name`: the lists it orders are short, and an indexed ICU collation is one whose version has to be tracked across upgrades |
| Normalisation | Input is NFC-normalised **once, on the way in**: the domain constructor of each text kind — a title, a name, a body, a display name, a reason — brings the text to normal form C through `core/port/text.Normalizer` before it bounds and checks it, with `golang.org/x/text/unicode/norm` as the adapter ([ADR-0056](../adr/ADR-0056-golang-x-text-and-idna.md)). A constructor handed no port refuses text that is not ASCII rather than storing it in whatever form it arrived, and a gate holds every constructor to being handed one. So what the domain answers, the change set records and the row holds are one string, and the length limit counts the form a person sees. The rows keep their own `normalize(…, NFC)` on the title, the names and the body as a second line for a writer that reaches a row without a constructor; both produce the standard's form. Every text a query compares is bound as `normalize($n, NFC)` by the compiler, the search words included. **No backfill:** a row written before normalisation existed keeps its bytes until its next edit, so a label written decomposed and the same label typed composed are two labels until then |
| Length limits | In Unicode code points (grapheme clusters for title truncation in clients) |
| Uniqueness | Bucket and label names are case- and accent-insensitive per scope (`unaccent` + `lower`) |
| Sorting in the UI | Server-side `ORDER BY name COLLATE hubtask_name` — lists of containers, buckets, labels, groups, backup targets, and a query sorted by `title`; `/meta/capabilities` answers `natural_ordering` so a client that sorts with `Intl.Collator` knows whether the server already sorted the same way. `order_key` stays `COLLATE "C"`: a rank key rests on byte order and is never a name |
| Full-text search | `tsvector` with a language-dependent configuration ([ADR-0034](../adr/ADR-0034-language-dependent-search.md)). An item's language is set (`item.content_language`), defaulting to the creator's locale; fallback `simple` for a language the installation has no configuration for, CJK included. The document is maintained by a trigger, and the configuration is resolved from the catalogue at write time. It carries a `simple` copy of the same text at the same weights, so the **word forms** are in it beside the stems ([ADR-0066](../adr/ADR-0066-search-is-one-question.md)): a query is read under the searcher's configuration, and the copy lets a reader whose configuration is not the entry's still find it. **There is therefore no language to choose when searching** — the client sends none. The beginning of the last word a searcher typed is matched under `simple` as a prefix, because a configuration would stem a beginning into something that is not one and drop a one-letter word as a stop word. Language detection from the text is not done: it would be a dependency, and a client that knows its own language can say so. A row records which configuration built its document; entries indexed before an installation gained a configuration are brought current by `ReindexSearch` (`POST /search:reindex`, `hubctl search reindex`), which rewrites exactly the stale rows in batches and answers how many there were. Of the `1.0` locale set, `zh-Hans` and `bn` have no stock configuration in any PostgreSQL the support matrix names and are `simple` plus the trigram index |
| CJK/Thai | The `simple` configuration plus a trigram index (`pg_trgm`) as a supplement, so search works without word boundaries |
| Semantic search | Optional, via embeddings (pgvector) — cross-lingual, and it covers the weaknesses of lexical search ([ai-first.md](./ai-first.md) §2) |

## 6. Text direction and presentation

The server makes no layout decisions but supplies the necessary metadata: `/meta/capabilities`
contains, per supported locale, `{ "locale": "ar", "direction": "rtl", "week_start": "SATURDAY",
"decimal_separator": "." }` — the week start in the account's own vocabulary, so a client compares
the two without translating, and the account's value overriding it where set (§4). The direction
is the script's, inferred where the tag states none; the week start and the decimal separator are
a table in `infrastructure/i18n` covering the `1.0` locale set (§2), checked against what a
browser's `Intl` answers for the same tags, because `golang.org/x/text` exposes neither as data
([ADR-0056](../adr/ADR-0056-golang-x-text-and-idna.md)). A catalogue whose locale has no row in the
table is answered with its script's direction, `MONDAY` and `.`, and the server logs once at start
which locales lack a row, so a twelfth language is a row rather than a surprise.

Colours are carried as **tokens** (`color.red.500`) rather than hex values, so that themes,
contrast modes, and accessibility stay solvable in the frontend; custom hex values are additionally
allowed.

### What every frontend owes

This is the localisation half of the binding client requirements. The accessibility half is
[`design-system.md` §10](../design/design-system.md#10-accessibility). A first-party client builds
against this list; a third-party one is told about it.

1. **Speak the negotiated locale.** Read `supported_locales` from `/meta/capabilities` and resolve
   the chain of §2 — the account's preference first for a signed-in person, the browser's
   `navigator.languages` before there is an account, the workspace's default, the installation's —
   with the same fallback the server uses: a regional tag lands on its language, a language nobody
   serves lands on the source. The client's catalogue is the server's file, read from the same
   directory (§3); a second catalogue under `apps/` is the one thing a source of truth must not
   have.
2. **Render every code through the catalogue, with the fallback.** A missing translation renders
   the source language, never a key and never an empty string (§3). The ICU subset is §3's.
3. **Format with `Intl`, from the account's locale.** Numbers, units, dates, times and relative
   times through `Intl.NumberFormat`, `Intl.DateTimeFormat` and `Intl.RelativeTimeFormat`; sort
   with `Intl.Collator` where a list is sorted on the client, and read `natural_ordering` to know
   whether the server already sorted it the same way (§5). The API returns raw values (§7).
4. **A moment is read on the reader's clock; a due date on its own.** `occurred_at`, `created_at`
   and every other instant in the account's zone (`account.time_zone`, else the workspace's, else
   the browser's); a due date in the zone it carries (`due_time_zone`), with the zone named when it
   is not the reader's; an all-day date with no time in any locale (§4).
5. **The week starts where the manifest says.** `week_start` from the account's preference, else
   from `supported_locales[].week_start` for the resolved locale — the same answer the server's
   `@start_of_week` computes with, so a calendar and a saved view agree (§4). A week *number*, if a
   client ever shows one, is ISO 8601 unless the locale's `Intl.Locale(...).getWeekInfo()` says
   otherwise.
6. **The document runs the way the locale's script runs.** `dir` on the root from
   `supported_locales[].direction`; `start`/`end` and logical properties throughout, never
   `left`/`right` (`design-system.md` §3); every component rendered in both directions through the
   workbench's direction axis ([ADR-0037](../adr/ADR-0037-component-workbench.md)).
   `lint-direction.js` refuses a physical inline side in any client tree, and an icon with a
   direction turns round by itself.
7. **Everything grows by 40 %.** `design-system.md` rule 4: no fixed width outside a genuine
   exception, and the workbench's pseudo-locale axis is where a layout that breaks in German is
   found before German arrives.
8. **Truncate by grapheme cluster, count by code point.** `Intl.Segmenter` for a title that has to
   be cut; the server's length limits are code points (§5), and a client that counted UTF-16 units
   would refuse what the server accepts.
9. **An entry's language is data.** `content_language` is what a person says the entry is written
   in, defaulting to their locale; a picker is `text_languages` from the manifest, and a language
   not in it is still stored and searched word by word (§5).
10. **Keyboard input that follows the locale.** Decimal separators typed as the locale writes them
    (`supported_locales[].decimal_separator`), parsed before a number reaches the contract as a
    raw value.
11. **Names are `display_name`, whole.** No split into first and last, no initials computed from
    a name (§7).

What the client does **not** owe: detecting a language from text (§5 declines it), translating
user content in place (§7), or a week number the server would compute — it computes none.

## 7. Other localisation-relevant points

| Point | Implementation |
|---|---|
| Names and forms of address | Only `display_name`, no split into first and last name (not culturally universal) |
| Email addresses | IDN-capable: the domain half is brought to its ASCII (Punycode) form through `core/port/text.DomainEncoder` — `golang.org/x/net/idna`, confined to `infrastructure/text` ([ADR-0056](../adr/ADR-0056-golang-x-text-and-idna.md)) — before an address is stored or looked up, so that `anna@müller.de` and `anna@xn--mller-kva.de` are one account. The local part keeps its case-folding and nothing more. Without the port a Unicode domain is refused, not stored as typed. No backfill: an address stored before IDN handling keeps its form and is found by it |
| Slugs and URLs | A slug is ASCII by validation — lower-case letters, digits and hyphens, refused otherwise — never transliterated: it is typed once by an operator. Display is always through `display_name`, which is Unicode |
| Numbers and units | CLDR formatting in the client; the API returns raw values |
| Timestamps in events and webhooks | Always RFC 3339 in UTC plus a `time_zone` field where relevant |
| Translatable user data | Item titles and similar are user content and are **not** translated in place. `AiTranslate` ([ai-first.md](./ai-first.md) §2) reads one entry in another language on request, through the workspace's provider, bounded and display-only: the answer is handed back with its provenance and stored nowhere |
