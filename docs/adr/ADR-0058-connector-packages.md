# ADR-0058 — The connector packages: generated, dependency-free here, typed there

**Status:** accepted · **Date:** 2026-09-16 · **Accepted:** 2026-09-17

## Context

[`automation.md`](../architecture/automation.md) §3.3 has promised since phase 0 "an official
**n8n community node** and a **Zapier app**, both generated from OpenAPI plus the capability
manifest, so that they stay complete automatically", and `0.5.0` and `0.6.0` built what they
need on the server side — the REST hooks pattern, trigger polling, OAuth2 with PKCE — with the
sentence "this milestone builds the endpoints they will be generated against". Milestone `0.9.0`
generates them (P-04, P-05 in [`milestone-0.9.0.md`](../backlog/milestone-0.9.0.md)).

Both packages are TypeScript or JavaScript, both live in `packages/` as workspace members, and
both are loaded by a platform this repository does not run: an n8n community node imports
`n8n-workflow` and is loaded by n8n against n8n's own copy of it; a Zapier app imports
`zapier-platform-core` and is bundled and run by Zapier's CLI against the version it pins. In
each case the platform library is the package's *peer* — the loader supplies it — and installing
it here would add it to this repository's lockfile, its licence scan and its vulnerability scan
for the sake of one thing: a local typecheck of the generated description against the platform's
types.

[`CLAUDE.md`](../../CLAUDE.md) makes every dependency a supply chain decision, and this is one
that a pull request must not take in passing. It is also one where the value is genuinely
unclear: the n8n declarative node format is JSON with a documented schema, and a schema written
into the generator's tests catches a malformed description as surely as a `.d.ts` would — but
not a *renamed* property in a new n8n release, which only the real types would.

## Options

**A. No dependency here. Peer dependencies in the packages, a format schema in the tests, the
real platform in the walk.** The generator emits JSON and plain JavaScript; each `package.json`
names its platform library as a `peerDependency` at the version range the platform documents;
the generator's tests hold the output to a schema of the platform's package format written from
its documentation; and P-17 loads the n8n node into `n8nio/n8n` in Docker against the Compose
stack, which is the typecheck that matters — the platform either loads it or does not. What it
costs: a format change in n8n or Zapier is found by the walk, not by `pnpm typecheck`.

**B. `n8n-workflow` and `zapier-platform-core` as development dependencies of their packages.**
`pnpm -r typecheck` proves the description compiles against the real types. What it costs: two
packages with their transitive trees in the lockfile — `n8n-workflow` alone brings a few dozen
— in every Node lane, in the licence report, in Dependabot's queue; and a version pinned here
that the platform loading the package does not use anyway.

**C. Hand-written packages in their own repositories.** How most community nodes are made. What
it costs is the sentence in `automation.md`: a hand-written node is complete on the day it is
written and drifts from the contract with the next milestone, which is the thing generation
exists to prevent.

## Decision

**Proposed: A**, with one question open for the owner: whether to take `n8n-workflow` alone as a
development dependency of `packages/n8n-nodes-hubtask` (B for one of the two), because n8n's
declarative format is the one with a real type and a history of renames, while Zapier's schema
is JSON validated by their own CLI at publication time and gains little from a local `.d.ts`.

Whatever the answer, the generator, the packages, the schema tests and the walk are built as A
describes; B's dependency would be added to one package in one pull request with a lockfile
change and nothing else.

## Consequences

* Two new workspace members, `packages/n8n-nodes-hubtask` and `packages/zapier-app`, each
  depending on `packages/api-client` for the document and on nothing else the workspace
  installs; the workspace map gains the two edges.
* The generated description is regenerated by `pnpm build` in each package from the document
  `make api-client` writes, so a contract change changes the node in the same pull request —
  which is what "complete automatically" means.
* The lockfile gains nothing under A. If the owner chooses B for n8n, `n8n-workflow` joins it as
  a development dependency of one package, and `docs/architecture/ci-cd.md`'s licence and
  vulnerability rows apply to it as to any other.
* Publication — the n8n community node registry, Zapier's marketplace — is an account and a
  review somebody else runs, and is not part of the milestone (`milestone-0.9.0.md`, "what is
  deliberately not in this milestone").

## Amendment — 2026-09-16, what P-04 found building the node

A peer dependency is not free of the lockfile after all: pnpm's `autoInstallPeers` is on in this
workspace, and a `peerDependencies` entry in a member's manifest installed `n8n-workflow` and
fifty-four packages beneath it on the first `pnpm install` — which is the tree option A exists to
keep out. Marking the peer optional did not stop it either. So the workspace's manifest for
`packages/n8n-nodes-hubtask` names no platform library at all, and the manifest n8n and the
registry read is a *second* one, generated into `dist/package.json` by the build: the registry's
unscoped `n8n-nodes-hubtask` name, the `n8n` block naming the node and credential files, and
`n8n-workflow` as the peer. What is published is `dist/`; what the workspace installs is the
api-client link. The Zapier app (P-05) has the same shape with one difference the platform
imposes: the CLI requires `zapier-platform-core` as a *dependency* at the exact version it
pins, so the generated `dist/package.json` names it as one — and the workspace's manifest still
names nothing.

The description is generated whole — a resource per tag, an operation per identifier with its
routing, a property per path parameter, a field per body property with `send: body`, the
optional ones in a collection, the query parameters in another, `If-Match` as a header — and the
credential too; the trigger is the one hand-written node, because a webhook subscription is
procedural in n8n's model and the twenty lines it takes are the same for every event type. The
schema in `scripts/schema.mjs` is the typecheck A promised and a selftest proves it can fail.

## Amendment — 2026-09-17, on acceptance: the open question is closed, and closed as A

Option A is accepted in the shape the amendment above describes — a workspace manifest naming no
platform library, and a generated `dist/package.json` that names it for the platform — which is A's
intent kept against a package manager that would have undone it. The question this record left
for the owner, `n8n-workflow` as a development dependency of one package, is answered **no**, on
what P-17's walk showed rather than on principle: loading the generated node into a real n8n found
[#723](https://github.com/Jersyfi/hubtask/issues/723) (a delivery body lost to a content type n8n
does not parse) and the Zapier CLI found [#722](https://github.com/Jersyfi/hubtask/issues/722)
(forty-six descriptions failing the platform's own check). Neither is a defect a `.d.ts` would have
caught, and both are what the walk exists to catch. A renamed property in a future n8n release — the
one case B was better at — is found by the same walk one milestone later, which is the cost A named
and the owner accepts. Should that cost turn out to be paid often, B is one pull request with a
lockfile change and this record gains a second amendment; nothing else moves.
