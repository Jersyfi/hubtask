# SC-15, D2 — a household without a mail server

**When:** 2026-10-13 · **Commit:** `00be810b` (branch `claude/sc-15-walk`; the commit after it,
`24b6bded`, changes only the readiness record)
**Kind:** using ([README](./README.md), "How to walk"). The server was built with `go build` from a
copy of that tree, with the web app (`apps/webapp/dist`) embedded. It ran as one binary on port
18520 in **single mode** (`HUBTASK_TENANCY_MODE=single`), with every role, **no
`HUBTASK_SMTP_HOST`**, and `HUBTASK_RATE_LIMIT_BURST=600`. `/meta/capabilities` answered
`features.mail: false`. Its database was its own PostgreSQL 16 (pgvector) container, migrated to
0137 with `cmd/migrate`, and the server reached it as `hubtask_app`, so row level security was in
force. `hubctl` was built from the same tree and signed in with `hubctl login` as the parent. The
browser was Chromium through Playwright, in the light theme and in English, at 1280 × 900 and at
375 × 812 (a phone with touch).

**The household:** the workspace "The Hollands", set up with the *Set up Hubtask* card and the
setup code the server printed. Its owner is the technical parent, Pat Holland
(`pat@hollands.example`). Alex, Kim and Sam are seeded family members. Every account is a throwaway
account on a database that no longer exists.

**Use case checks it shows:**
- UC-ID-14 check 5: no mail is sent, the link is shown once, and it works.
- UC-ID-14 check 6: inviting an address that is already here says so. The address may belong to an
  active account or to one that was invited and has not arrived yet.
- UC-ID-06 check 2: a session says it was opened by "Invitation".
- UC-ID-12 checks 1, 4, 5, 6, 7, 8 (the refusal half) and 9.
- UC-ID-18 check 5.
- UC-AUD-01 checks 1 (screen, API and `hubctl`), 2, 3, 5 (recorded as it is, see "What was found"),
  6, 7 and 8.

UC-ID-04 is not walked: its *Where it ends* puts a household without a mail server outside it.

## What was found

1. **The trail's unknown-outcome refusal does not carry the use case's code.**
   `GET /audit?outcome=MAYBE` answers `usecase.input_invalid` with `usecase.field_not_in_enum` on
   `/outcome`, not `audit.outcome_invalid`. The registry's enum check answers before the use case's
   own (known-traps, "`Handler.Invoke` skips validation"). UC-AUD-01 check 7, second half: not met
   as written.
2. **A plain member who asks for the whole trail is answered, not refused.** The answer holds only
   their own events, with 200 and no entry. Only a colleague's events are refused, with
   `access.not_permitted` and a DENIED entry. `api/openapi.yaml` describes exactly this, so the
   check's first half and the contract disagree. UC-AUD-01 check 5 is under question, as the brief
   says.
3. **A minimum password length of 500 is accepted** without a bound or a warning, after a step-up.
   - The screen shows 500, "Set here."
   - `/auth/sign-in-rules` answers `min_length: 128`.
   - At the next sign-in the parent, and every member whose password is shorter, meets *Choose a
     new password* with "At least 128 characters" (`12c-…`).
   - One typo locks the household into 128-character passwords until the parent finds the screen
     again. The rule's refusal at its field (UC-ID-12 8) could therefore not be seen for a value a
     server should refuse.
4. **An invitation's refusal is drawn out of view.** At 1280 × 900 the banner's top was at −306 px
   when the parent pressed the button at the form; at 375 × 812 it was at −630 px.
   - The email field is emptied and the focus stays on the button.
   - The live region announces the sentence, but a sighted parent at the form sees a cleared form
     and nothing else.
   - SC-13 noted the placement at 1280 px. The phone makes it worse.
5. **Every page a plain member opens writes refusals to the trail.** The shell asks for
   `health.report_read` and `quota.read`, which a member may not read. Each load adds two to four
   DENIED entries, and the console shows 403s. When the parent filtered for refusals, ten of the
   trail's twelve were these. A parent filtering for *Refused* finds noise, not what a
   child tried.
6. **The screen and the other doors name an erased actor differently.** The screen shows "former
   user", the account's new display name. The API and `hubctl` show the stable pseudonym
   `former-user-373464343663`. Two erased family members would both read "former user" on the
   screen. A refused entry's actor carries no `label` in the API before the erasure.
7. **"Forgot your password?" promises a mail that cannot go.** On this installation without mail
   (`features.mail: false`) the sign-in card still offers it, and it says "If an account exists for
   it, a link is on its way". UC-ID-04 says that in D1/D2 without mail the reset cannot arrive. The
   screen does not say so, unlike the invitation form.
8. **A required switch names the wrong source.** *Refuse commonly used passwords* and *Refuse the
   address, the name and the workspace name inside a password* are on and disabled with "The
   installation requires this, so it stays on here." Their origin line reads "Hubtask's default.",
   and this installation decided nothing. The hint is chosen whenever the installation's effective
   value is true, whatever its source (`requiredAbove` in `SignInSettingsView.svelte`).
