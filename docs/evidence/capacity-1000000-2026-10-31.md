# Capacity at 10⁶ entries — the owner's workstation

**2026-10-31, `make capacity` (F-10, observability-reliability.md §13.2), commit `78ac9e9db`.**
10⁶ entries over 200 workspaces in a long tail, each read path that grows with a workspace held
for the largest, a middle and the smallest credentialled workspace: 30 s after a 5 s warm-up,
eight closed-loop callers, paced at 400 requests a second. One process serving every role, against
PostgreSQL 16 (pgvector image) in a container. The run's JSON is
[`capacity-1000000-2026-10-31/capacity-1000000.json`](capacity-1000000-2026-10-31/capacity-1000000.json).

## What the run showed, and what was fixed

The first attempt did not get past its seed: thirty minutes into one COPY of 10⁶ rows. Every entry
loaded without a number rewrote its collection's counter row, inside one statement; each later
write and each foreign-key check on that collection walked the growing chain of row versions, so
the load grew with the square of the entries per collection. A restore of a large collection paid
the same. Migration 0289: an entry that brings its number writes no counter row, and the next draw
catches up with the collection's highest number.

The first measured run (commit `6a0a1465c`), against the largest workspace, and the last:

| Path | P95 before | P95 after | What changed |
|---|---|---|---|
| a collection's page | 37 | 7 | the parent spelled `= OR IS NULL`: read in order from `wi_level_order_idx` instead of sorting the level |
| board by completion | 79 | 47 | rows numbered over identifiers; only the kept rows are read whole |
| the hub's level | 379 | 254 | the figures skip the hidden-ancestor lookup where nothing is narrowed; PROGRESS anti-joins the gathered parents; `jit = off` |

Found beside the paths: a create read its level's last rank by scanning the level (25 ms at 56 745
entries, now 0.1 ms), and a vacuum of the loaded table failed on the container's 64 MB `/dev/shm`
(the reference compose file now gives the database 256 MB).

## What this is not

* **Not the hub's level within 200 ms under load.** One request for the largest workspace's level
  costs about 75 ms of database time (PROGRESS 41 ms, DUE 33 ms, measured alone); eight concurrent
  readers of the same workspace wait 254 ms at P95. The figures are counted on every read, in
  proportion to the entries of the collection; at 10⁶ entries in one workspace that is several
  times this. Kept as a gap (S-12, README), not hidden here.
* **Not 10⁷.** That run belongs to the integration server and has not run (test/load/README.md
  says what it needs and the command).
