# RT-6 — Overload, and what shedding holds

**2026-09-02, development machine.** RT-6 asks whether a load beyond capacity engages the load
shedding, holds the interactive P95 inside its target, and stays inside its memory
([observability-reliability.md §12](../architecture/observability-reliability.md)). Until H-11 it
could not be run at all: §6 has described an `inflight_requests` threshold answering `503` +
`Retry-After` since the document was written, and there was nothing to engage.

This is the first run. It is on the machine the work was done on and not on named hardware, which
is why the numbers below are a shape rather than a capacity figure — see "What this is not".

## The run

Three stages, one client, everything against one process serving all four roles.

| | |
|---|---|
| Stages | 60 req/s for 30 s → **3 000 req/s for 60 s** → 60 req/s for 30 s |
| Client concurrency | 64 |
| Mix | two interactive calls (list, create) to one deferrable (`POST /items:query`) |
| Threshold | `HUBTASK_LOAD_SHED_INFLIGHT=8` |
| Dataset | 5 000 items over 10 tenants, long tail |
| Machine | Apple silicon laptop, PostgreSQL 16 in a container, pool of 10 |

| | Result |
|---|---|
| Requests | 82 296 |
| Shed (`503`, deferrable) | **26 224** |
| Shed (interactive) | **0** |
| Server errors beyond the refusals | **0** |
| Transport failures | **0** |
| Interactive P95 — baseline stage | **9 ms** |
| Interactive P95 — overload stage | **94 ms** |
| Interactive P95 — after the load came off | **11 ms** |
| Answered per second, overload stage | **873** |
| **Answered per second per vCPU, at a held P95 of 94 ms** | **62.4** over 14 vCPU |

The three sentences that matter, in the order the test asserts them:

1. **The mechanism engaged.** 26 224 deferrable calls were refused with `503` and a `Retry-After`
   while the process was above its threshold.
2. **It engaged only where it may.** Not one interactive request was refused, and nothing answered
   a five hundred that the harness had not asked for.
3. **The interactive path held, and came back.** 9 ms → 94 ms under an offered load fifty times the
   baseline's, and 11 ms again within half a minute of the load coming off. Shedding for ever is not
   graceful degradation; it is falling over politely.

The overload figure is what the client's own concurrency implies rather than a failure: 64 requests
in flight against a pool of ten wait for a connection, and what shedding buys is that the wait stays
a wait. That is the state `engineering-guidelines.md` §4's 200 ms read target does not describe,
which is why the test's target is five times it.

The **62.4 answered requests per second per vCPU** is the one number here that is a capacity figure
in kind, and it is measured where it means something: in the stage where the offered rate is past
what the process can serve. Below saturation a throughput figure is the rate the run was started
with. It is still not a number to quote — see below.

## The memory half

Not asserted here. The process's resident size is read from `/proc`, which this machine does not
have; the nightly does, and the run holds the process to `GOMEMLIMIT=768 MiB` — the API role's own
limit in `k8s/values.yaml` rounded down, so the ceiling is one somebody deploys.

## What this is not

It is not a capacity figure and nothing here may be published as one.

* **The per-vCPU figure above is this laptop's, over five thousand items.** The figure a provider
  can convert into money is the same measurement on the second tier: the full ramp, on the
  integration server, over the two-million-item dataset, per release
  ([test/load/README.md](../../test/load/README.md)) — and what makes it useful is its *decay* with
  items per tenant, which one dataset cannot show. A laptop's number over a toy dataset is a shape,
  not a capacity.
* **A concurrent-user count is a derived figure and never a headline.** It is throughput divided by
  a behaviour model, and the model moves it by an order of magnitude: 500 req/s is 5 000 users at
  six requests a minute each, or 500 users at sixty. Wherever a user count appears, the model
  appears beside it — or the number does not appear.
* **Nothing is published outside** until the figures are stable (the owner's decision of
  2026-08-21, decision 7 in [milestone-0.6.0.md](../backlog/milestone-0.6.0.md)).

## How it was run

```bash
HUBTASK_LOAD_TENANTS=10 HUBTASK_LOAD_ITEMS=5000 \
  go test -tags load ./test/load/ -run RT6 -v
```

It brings up its own installation: a PostgreSQL container, the migrations, the seeded dataset from
`test/load/seed`, and the real `cmd/server` binary. The binary and not a stack wired together in a
test, because RT-6 asks what a *process* does — its garbage collector, its pool, its memory — and a
test-assembled one is a different process from the one that is deployed.

From now on it runs nightly through `make gate-load`, and the run leaves its numbers as an artefact
whether it passes or fails: a red load test is read from its timeline, not from the assertion that
failed.
