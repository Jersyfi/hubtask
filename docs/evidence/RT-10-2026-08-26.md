# RT-10 — The schedule across a time change and an outage

**2026-08-26, local development machine.** RT-10 asks what happens to the two timed duties when
the clock does something unusual: a daylight saving transition, and two hours in which nothing ran
([observability-reliability.md §12](../architecture/observability-reliability.md)). Until D-05 the
row had no owner — the reminder half arrived with D-03 and the materialisation with this task, and
neither could be asked the question alone.

From this pull request onwards it runs in `gate-resilience` on every pull request. This file
records the run that proved the gate before it became one; the later evidence is every green
`Resilience RT-1..RT-12` check.

| | Value |
|---|---|
| Test | `TestRT10TheScheduleSurvivesATimeChangeAndAnOutage` ([test/resilience/rt10_clock_and_dst_test.go](../../test/resilience/rt10_clock_and_dst_test.go)) |
| Environment | macOS (Apple Silicon), Docker Desktop, server 29.1.2 |
| Image | `postgres:16-alpine` |
| Duration | 1.52 s for the test; 7.93 s for the whole `gate-resilience` suite |
| Zone under test | `Europe/Berlin`, the spring transition of 29 March 2026 |
| Series | `FREQ=DAILY` at 09:00 local, `ON_SCHEDULE`, five-day window |
| Occurrences materialised | 3, on both sides of the transition, all at 09:00 local |
| Outage | 2 h with no pass running, with one reminder due inside it |
| Reminders fired after the outage | 1 — once, late, with the delay in the metric (≈ 5 400 s) |
| Second pass at the same moment | 0 fired, 0 materialised, 0 additional announcements |
| Announcements | one `recurrence.occurrence_created` per occurrence, counted through the outbox |

## What the run proves

**The local time is what holds.** The window reaches across the transition, and every occurrence
it produced reads 09:00 in Berlin — which means the instants are not evenly spaced: 07:00Z after
the change, 08:00Z before it. A series that had been expanded in UTC would have produced 08:00
local on one of those days, and nobody would have noticed until somebody missed a morning.

**Nothing fires twice and nothing is missed.** The two hours of silence are not simulated with a
sleep; the clock is a value the test moves, so the passes see exactly what a scheduler that was
away would see. The reminder due inside the window fires on the first pass afterwards — once, and
visibly late in `hubtask_reminder_delivery_delay_seconds` — and a second pass at the same moment
fires nothing and materialises nothing, because the reminder left `PENDING` once and the series'
watermark moved once.

**The counts are read the way a consumer reads them.** The occurrences are read back through the
item repository, so `recurrence_rule_id` is asserted as an answer a client would get rather than as
a column this test knows about; the announcements are counted through the outbox's own claim, which
is the only reader it has.

## What it does not cover, and where that lives

* **Two leaders at once** is proved at the level where the guard is: the watermark's
  compare-and-set (`TestAPassThatReadAStaleWatermarkRefuses`) and the reminder's guarded transition
  against a real database with two concurrent transactions
  (`TestTwoPassesOverOneReminderProduceOneSend`). RT-10 is about the clock, not about concurrency.
* **The hour that does not exist and the hour that happens twice** are pinned as golden files over
  the port ([infrastructure/recurrence/testdata](../../infrastructure/recurrence/testdata)), where
  the expansion can be stated in local times and instants side by side rather than inferred from
  rows.
* **A backwards clock jump on the host** is not asserted. The passes read the clock through the
  port and compare stored moments against it; a jump backwards makes them do less work rather than
  wrong work, and the delay metric would show it. There is no bounded catch-up to break because
  nothing here is scheduled by counting ticks.
