# R-08 — A day's work in the application, walked again

**2026-09-08, a local stack.** The pass of 2026-09-04
([evidence](./R-08-2026-09-04.md)) ended with "Walking it again": the same route against the next
milestone's own backlog, and what to compare is the **kind** of finding rather than the count. This
is that second walk, at the end of F3, and the route is longer because the milestone built the
surfaces the extra steps need.

**Read the method before the findings.** The 2026-09-04 pass drove a browser. This one did not.
Signing the client in means typing a bearer token into a field, and entering a credential into a
form is not something this session does — so every step below was driven through the API with
`curl` against a running server, and the client half of the comparison is a **reading of the
source**, not a use of the screens. That is a weaker instrument for exactly the kind of finding the
first walk was best at, and the comparison at the end says so rather than working around it.

| | Value |
|---|---|
| Server | `go run ./cmd/server`, `ROLES=api` on `:8081`, against the development PostgreSQL, migrations at `0070` |
| Storage | `HUBTASK_STORAGE_KIND=local` — the bytes go through this server's own `/media/{id}:content` |
| Credential | a `f3-20 walk` personal access token, all scopes, three hours, revoked when the pass ended |
| Client | not driven. `apps/webapp` was read, not clicked — see the method note above |
| Work | this repository's own backlog: milestone F3 and its twenty tasks |
| Performed with | the HTTP API alone. No step used the browser, and none used `hubctl` |

## The route

Nineteen steps: the ten of F2-16, then the nine the milestone's own work adds. Each says what
happened and what it needed.

### 1. Create the hub and the collection — **the API**

A hub "F3-20 walk", a collection "The route" under it, and a first task in it. The surface
[#359](https://github.com/Jersyfi/hubtask/issues/359) asked for exists now:
`CreateContainerDialog.svelte` is reached from `WorkspaceNav` and from `ContainerView`. This pass
did not open it.

### 2. Put the milestone's entries in — **the API**

Four entries at the collection's top level. `POST /items` takes `collection_id`, not
`container_id`; the pass spent a round of `usecase.input_invalid` on that, which is the contract
being read carelessly rather than a finding.

### 3. Break one into work packages and an activity — **the API**

`parent_id` on create, three levels deep: task → work package → activity. The capability profile
took it without complaint, which is what `depth` and `path` in the answer confirm.

### 4. Label them — **the API**

`POST /containers/{id}/labels` made "Walked" with `color_token: green`, and `PUT
/items/{id}/labels/{id}` put it on: 200. Making a label was
[#361](https://github.com/Jersyfi/hubtask/issues/361) last time; `LabelsDialog` is wired into
`ContainerView` now.

### 5. Order them — **the API**

`POST /items/{id}:reorder` with `before_item_id`, 200, and the entry moved. Naming the entry
*itself* as `before_item_id` answers 422, which is right and is how the pass first mis-read the
route.

### 6. Move one between collections — **the API**, and [#358](https://github.com/Jersyfi/hubtask/issues/358) is fixed

The first walk's one server defect: `:move` treated an explicit `"target_parent_id": null` as an
omitted field, so an entry could never leave its parent. Walked again, twice:

* a task with `{"target_parent_id": null, "target_collection_id": "<other>"}` — **200, the other
  collection, top level**;
* an activity with `{"target_parent_id": "<another package>"}` — **200, now under the second
  package**.

A work package sent to a collection's top level is refused, `items.parent_item_required` with
`item_type: WORK_PACKAGE` and a field error on `/parent_id`. That is the capability profile
answering, not the old defect: the refusal names the type and the field, which is what the fix
made possible.

### 7. Complete a few — **the API**

`:complete` on two entries; `completion.is_completed` reads true on both.

### 8. Find one by a word in its notes — **the API**

`PATCH /items/{id}` wrote the note *and* set `content_language: "en"` in the same call, which is a
thing the first walk could not do at all ([#360](https://github.com/Jersyfi/hubtask/issues/360) —
`items.update` reached no screen). `POST /search` for `marmalade` found it, with and without an
explicit `language`.

The language consequence the first walk recorded is unchanged and is now handled in the client:
F3-19 searches under the reader's own languages first and offers the rest as a second stage,
rather than making the reader find a control they have no reason to look at.

### 9. Archive what is finished — **the API**

`:archive`, 200, and `archived_at` is set.

### 10. Look at what changed — **the API**

Eighteen activity entries, newest first, each with an `actor`, a `code`
(`activity.item_archived`, `activity.item_updated`, `activity.item_reordered`, …) and a
`change_set`. The note edit reads `{"notes": {"changed": true}}` and
`{"content_language": {"from": "de", "to": "en"}}` — the fact of the change without the text of it,
which is ADR-0017's rule holding where it is easiest to break.

Reaching the entry from the list was [#364](https://github.com/Jersyfi/hubtask/issues/364);
`EntryList.svelte:841` passes an `href` now.

### 11. Assign it, and put a second person on it — **the API**

`:assign`, then `PUT /items/{id}/members/{accountId}`: one member. The candidates an assignee
picker needs are what F3-01 added `GET /memberships` for.

### 12. Comment on it, and reply — **the API**

A comment, then a reply under it: both posted.

### 13. Attach a file, and put an image on the card — **the API**

The three-step transfer end to end: `POST /media` for the ticket, the bytes to the URL it names,
`:confirm`, then `POST /items/{id}/attachments` and `PUT /items/{id}/cover`. Under `local` the URL
is this server's own; under `s3` it is a bucket the interface's policy does not name, which is what
the draft [ADR-0047](../adr/ADR-0047-media-origin-in-the-interface-policy.md) is for and what the
owner still has to decide.

### 14. Describe it in a custom field — **the API**

A `NUMBER` definition at collection scope, `effort = 2.5` on the entry, and the value comes back in
the item's `custom_fields`.

### 15. Give it a due date, a start date and a reminder, and read the timeline — **the API**

Due `2026-10-05T07:00:00Z` with `due_time_zone: Europe/Berlin`, start `2026-10-01T07:00:00Z`, a
reminder that fires `2026-10-04T07:00:00Z`, and the entry appears once on a timeline query for that
window.

### 16. Make it repeat, and skip an occurrence — **the API**

`PUT /items/{id}/recurrence` with `FREQ=WEEKLY;BYDAY=MO`, then `:skip`, and the next occurrence
moves to `2026-10-12`. Two things the walk learned here became issues:

* the end of a series is `ends_at` or `max_count` **beside** the rule, never `UNTIL=` or `COUNT=`
  inside it — the server refuses that with `recurrence.rrule_carries_end`, and the client now
  splits the rule before sending it;
* an occurrence carries no way back to the entry it repeats from
  ([#428](https://github.com/Jersyfi/hubtask/issues/428)).

### 17. Stamp a work package out of a template — **the API**

A template at collection scope with a task and a work package under it, then `:instantiate` with an
anchor date: **2 entries created, 0 dropped references**.

### 18. Save the view, share it, export it, subscribe a calendar — **the API**

`POST /views` with the query, `:share` to `SCOPE`, `:export` to CSV (608 bytes) and ICS (320
bytes), and a calendar feed minted with its URL shown once.

The stored query has to be **anchored and flat** — `scope_container_id` as a sibling of the rest,
not the nested `scope: { container_id }` a caller writes to `/items:query`. A view stored the other
way is created without complaint and then refuses at every export with `query.scope_required`. That
is [#431](https://github.com/Jersyfi/hubtask/issues/431), and it cost this walk two rounds.

### 19. Watch a change arrive with a second client open — **the API**

A second connection on `GET /stream`, then a `PATCH` on the entry from the first. The second
client received it in under a second:

```text
event: item
data: {"entity":"item","op":"UPSERT","payload":{"title":"Walk the route (seen live)"},
       "seq":265,"hlc":"1788890282268:00000:server-…","occurred_at":"2026-09-08T17:58:02.268Z"}
```

`retry: 3000` and a resumable `id:` on every frame, which is what `Last-Event-ID` needs and what
`FetchTransport` sends itself — a browser's `EventSource` cannot carry a bearer, and a token in a
URL is forbidden.

## What was left

Every gap this milestone's work ran into has an issue, labelled and left unmilestoned until F4
exists. Each one names what was attempted.

| # | What | What it is |
|---|---|---|
| [#426](https://github.com/Jersyfi/hubtask/issues/426) | `DELETE /memberships/{id}` answers 500 for a membership that exists | An operation faults. It 404s correctly for an unknown one and logs nothing for the real one |
| [#427](https://github.com/Jersyfi/hubtask/issues/427) | A descriptor's enum shadows the contract's, so a written refusal is unreachable | The two disagree about a shape. `PUBLIC_LINK` and `week_start` both; a gate comparing them is suggested |
| [#428](https://github.com/Jersyfi/hubtask/issues/428) | An occurrence cannot reach the entry it repeats from | A hole in the model — the client can show the occurrence and not what it belongs to |
| [#429](https://github.com/Jersyfi/hubtask/issues/429) | `LAPSED` is a reminder state the contract's enum omits | The two disagree about a shape |
| [#430](https://github.com/Jersyfi/hubtask/issues/430) | Every `PATCH` sends `application/json` where the contract declares merge-patch | The two disagree about a shape. The server accepts both, so nothing failed — which is why it survived a milestone |
| [#431](https://github.com/Jersyfi/hubtask/issues/431) | A saved view's stored query must be anchored and flat, and nothing says so | Documentation. The shape is real and undocumented, and every export depends on it |

Nothing in this list is "there is no way to do this in the application".

## The comparison, by kind

The first walk's eight findings and this walk's six do not divide the same way, and the division is
the point.

**2026-09-04 — four of eight were a missing surface.** #359, #360, #361 and #362 each named a write
that existed in a store and reached no screen: creating a hub or a collection, editing an entry,
making a label, making a column. #363, #364 and #365 were the application saying or connecting the
wrong thing. One, #358, was the server's.

**All eight are closed, and the surfaces are there.** `CreateContainerDialog` is reached from two
places, `LabelsDialog` from `ContainerView`, `BucketDialog` from `Board`, `app.entries.add_child`
is used at `EntryList.svelte:926` where two controls once shared a name, and the row carries an
`href`. #358 was walked again above and is fixed.

**2026-09-08 — none of six is a missing surface.** Four are the client and the server disagreeing
about a shape (#427, #429, #430, #431), one is an operation that faults (#426), and one is a hole in
the model (#428).

**Which kinds are gone:** "no way to do this in the application", and "the application says the
wrong thing". Both were the majority last time and neither appears now.

**Which kind is new, and it is the whole of this walk's list:** the client and the server hold
different beliefs about the same thing — an enum, a content type, the shape of a stored query — and
the disagreement is invisible until something specific is attempted. #430 is the clearest: the
server accepts both content types, so every `PATCH` in the client worked for a whole milestone
while sending the wrong one. These are the findings of a surface that is filling in rather than
churning: nothing that worked on 2026-09-04 fails now, and what is left to find has moved from
"the control does not exist" to "the two ends describe it differently".

**What the method cost.** A pass driven through the API cannot find the first walk's best kind of
finding — a control that is missing, mislabelled or unreachable — because it never looks at a
control. The source says the four missing writes now have callers, and that is a weaker statement
than a person clicking them. The third walk should be driven through the browser by somebody who
can sign in, and should treat this file's client claims as the thing to check first.

## What this says about R-08

After two walks the risk is not "the frontend decision is absent" and no longer "a day's work
cannot be done in the application" either: the route was walked end to end, nineteen steps, and
every one of them completed. What remains is narrower and has two parts. The pass is still done by
the people who built the thing. And the walk that would catch the next class of defect — the one
where a control exists and behaves differently from what the server does — has to be driven through
the interface, which this one was not.
