# R-08 — The route, walked again, and the one nobody had walked

**2026-09-11, a local stack, in a browser.** The third pass. The first two
([2026-09-04](./R-08-2026-09-04.md), [2026-09-08](./R-08-2026-09-08.md)) walked the end-user route.
This one walks the administration area — which had never had a screen before F4 and had never
been opened by anybody until #526 made a local stack signable — and it does what the second walk
said the third one must: it is **driven through the interface**, by somebody signed in with a
password, and it treats the second walk's client claims as the thing to check first.

| | Value |
|---|---|
| Server | `cmd/server` built from `main` at `bc7d0a4` (F4-19 merged), all four roles in one process, on `:8080` |
| Database | a fresh PostgreSQL 16 container, migrated from empty to `0079`, the server connected **as `hubtask_app`** — never the owner role, for the reason `CONTRIBUTING.md` gives |
| Configuration | `HUBTASK_TENANCY_MODE=multi`, a `LOCAL` backup volume, one encryption key, private networks released for the webhook receiver, an SMTP sink on `:2525` for the invitation mail |
| Workspace | `demo`, provisioned by `scripts/dev-workspace.sh --bootstrap` and `scripts/dev-workspace.sh`; `owner@example.org` with a password |
| Client | `apps/webapp` under `vite`, at `http://demo.localhost:5174/`, driven in a browser — clicks, typed fields, the address bar |
| `hubctl` | not used. Two things a client cannot do were done with `curl`: seeding completed entries for the retention preview, and the idempotency-key reproduction in §"Two things this walk could check" |
| Receivers | a Python webhook receiver on `127.0.0.1:8099` that answers `200`, or `500` while a file named `fail` exists beside it; a Python SMTP sink that writes every message to a file |
| Authenticator | RFC 6238 computed locally from the enrolment secret — the walk's phone |

**Method.** Each step names what was attempted, what happened, and what it needed. A gap became an
issue, labelled, and left unmilestoned; nothing was fixed on the way. Three of the screens walked
here were built earlier in the same session as this walk (#535, #536, #538, #539, #540, #541), so
the walk is by the people who built them — the residual risk the second walk named, and still open.

## The route

Fourteen steps: the ones F4-21 names, in its order.

### 1. Sign in with a password — **the browser**

`owner@example.org` at `demo.localhost`, the password typed, the workspace opened. Signed out and
in again at every step that needed a fresh session below. Nothing to report.

### 2. Enrol a second factor, and sign in in two steps — **the browser**

`/profile` → *Set up a second factor*. The secret in groups of four, *Open in my authenticator*
as a link, ten recovery codes, the acknowledgement, then a code: computed from the secret, typed,
*Turn it on* → *The second factor is on. Your next sign-in asks for a code.*

Signed out; signed in with the password → *One more step. Your password was right. This account
also asks for a code from your authenticator* → the code → `/profile`. Two-step sign-in works.

This is ADR-0053's C and D. The enrolment is complete and it is what the ADR says it is: not the
one somebody expects from a product in 2026.

### 3. Invite somebody, and redeem the invitation — **the browser, and a mail**

`/administration/people` → *Invite somebody*: `ada@example.org`, *Member*. The row appears as
*Invited, not yet arrived*. The mail reached the sink with `<base>/redeem#token=…`; opened in a
second tab, the fragment was gone from the address before the first request (checked: the bar
read `/redeem`), the password set twice, *Set the password and sign in* — and the frame said
*Signed in as Ada* above a main area that said *There is nothing at this address. /redeem*.
*Back to the start* works. [#545](https://github.com/Jersyfi/hubtask/issues/545).

### 4. Grant a role, with a step-up — **the browser, then curl**

Ada → *Owner* → *Grant*. Refused by the server, `403 auth.step_up_required`, and the *Prove it is
you* prompt opened — **the step-up stops something.** *Not now*: Ada is still a member and the
refusal is rendered in the server's words, which are a script's words
([#549](https://github.com/Jersyfi/hubtask/issues/549)). The prompt offered the password only,
although the account had just armed a factor; the refusal carried `"methods": "PASSWORD TOTP"` and
the client splits on commas ([#544](https://github.com/Jersyfi/hubtask/issues/544)).

*Grant* again, the password proved (`POST /auth/step-up` → `201`), and the retry was refused
**again** with `auth.step_up_required`. Reproduced with `curl`: the client mints one idempotency
key outside the step-up wrapper on purpose, and the server answers the repeated key with the
refusal it stored, so the proof is never read and the grant it was consumed for is gone. A fresh
key with the same proof succeeds. **An `OWNER` grant cannot be made from the application.**
[#543](https://github.com/Jersyfi/hubtask/issues/543).

### 5. Mint a token — **the browser**

`/profile/tokens`: a name, an expiry, one scope, *Mint*. Shown once, masked, with the
acknowledgement before *Done*. The `read only drill` token minted earlier with `retention:read`
alone read `/retention-policies` (`200`) and was refused a write (`403 access.insufficient_scope`),
which is the auditor's shape F4-18 asks for.

### 6. Write a rule, dry-run it, enable it, watch it run — **could not be walked**

`/administration/rules` → *Write a rule*. The editor opens; **Starts on** offers only its
placeholder and **What it does** offers no action kind. The editor reads
`manifest.automation.triggers` and `.actions`, as `apps/webapp/CLAUDE.md` demands; the manifest
answers no `automation` at all, and `GetCapabilities.go` says so in its own comment. No rule can
be written from the application. [#542](https://github.com/Jersyfi/hubtask/issues/542) — the one
missing surface of this walk, and the third time this milestone has met the same gap (`event_types`
in #536, the retention catalogue in #538).

### 7. Subscribe a webhook, and replay a dead letter — **the browser**

`/administration/webhooks`: the picker offered the manifest's 46 types; `http://127.0.0.1:8099/hook`
with two types; the secret shown once. An entry created → a **signed** delivery at the receiver
(`X-Hubtask-Signature: t=…,v1=…`, `X-Hubtask-Event-Id`, attempt `1`, answered `200`). The receiver
switched to `500`: attempts 1…8, *The target answered 500*, the next attempt shown while there was
one, attempt 8 *Given up on*, the subscription carrying its failure count and last error. The
receiver fixed, *Send it again*: attempt **9**, the **same** event id, `200`.

The ladder is eight attempts over two days by design; the dead letter was reached with the backoff
shortened in a local build, and that change is in no branch. And this step could not have been
walked at all before #536: until it, no delivery had ever been retried on any installation, because
a row read back carried no tenant — the finding the second walk's method could not have made.

### 8. Configure a target, run a backup, verify it — **the browser**

`/administration/backup`: a `LOCAL` target from the form, *Test the connection* (*Wrote, read and
deleted a file in 8 ms · 672.6 GB free*), *Back up now* → the indeterminate bar (this server answers
`progress: null` throughout) → *The archive was written*; a second run *Stop it* → *The run was
stopped*. *Check that it opens* → *Opens · checked 10:47 PM*, and the target's line moved from
*No archive here has ever been checked* to *An archive here was last checked …*. A schedule
written, read back as *Every day at 03:00 · Next run Sep 11, 2026, 3:00 AM* with its plan and its
`min_keep` floor, switched off, removed; the target's delete refused while the schedule named it,
with the server's sentence — *1 backup schedule(s)*
([#547](https://github.com/Jersyfi/hubtask/issues/547)).

### 9. Restore, as a dry run — **the browser**

`/administration/restore`: the target, the archive from the listing, *Look inside it* → a
rehearsal → its report. *Replace this workspace*: the button disabled with its reason, the sentence
about credentials above the confirmation, the acknowledgement, `Demo` typed, the safety copy
switched off → its own confirmation; then the rehearsal refused by the server for want of a proof →
the prompt → proved → the destructive **dry run** ran to its report. `MERGE` for real after its
rehearsal: *Left as they are: 28 · Collisions the rule above decided: 28*, `SUCCEEDED`. The first
attempts named the archive by its manifest id and answered `backup.archive_chain_broken`; the
archive is named by its path ([#548](https://github.com/Jersyfi/hubtask/issues/548)).

`REPLACE_TENANT` was not run for real. It ends the session that runs it, which is the sentence the
screen exists to put in front of somebody.

### 10. Preview a retention rule — **the browser**

`/administration/retention`: `COMPLETED_ITEM` from the manifest's 17 kinds, written **switched
off** and previewed at once — *Things it would act on: 4 · 80 per cent* with the four titles — and
*This rule was stored as an announcement* with the reason, because a twentieth of the workspace is
the line. A tenant-wide hold placed with a reason → the preview: *Held back by a legal hold, and
not touched: 4*. Armed, then the effective listing for the hub: *In force here · from the whole
workspace*. The hold lifted with its reason. Arming was impossible before #538 — every `PATCH` on
a rule answered `lifecycle.rule_incomplete`, the same missing-tenant shape as the webhook rows.

### 11. Query the audit trail, verify the chain — **the browser**

`/administration/audit`: the trail with outcome, severity, action, sequence, actor, target and
changes; `backup.` as a prefix narrowed it to the three backup actions; *Check the chain* over
September → *The chain holds · Entries checked: 34*, with the sentence that nothing has anchored it
outside the database. The break branch was not produced against a real chain — that needs a write
behind the application's back, which is what the chain exists to detect — and is a pure function
with both branches asserted instead.

### 12. Export the trail — **the browser**

A period, `JSONL`, the `LOCAL` target → watched → *It is at the target Local disk, with its
checksums beside it* and no download. The archive was on disk as
`hubtask-audit-<tenant>-<from>-<to>`, and the trail then carried `audit.exported` — which the screen
says it will.

### 13. Record a data subject request — **the browser**

`/administration/privacy`: a case for `ada@example.org` (no account) — *Owed Oct 11, 2026 · in 4
weeks*; three cases ordered by deadline with *Owed soon* on tomorrow's; an `ERASURE` case defaulting
to *Keep what other people depend on* with the sentence about third parties, `FULL_DELETE` beside it
with what it costs; `RECEIVED → IN_PROGRESS → COMPLETED` and a refusal with its reason; an account
restricted and a consent withdrawn, both confirmed in the database. `INSTALLATION` appears nowhere
and the alternative is on the screen.

### 14. The area tagging — **a test**

`routes.test.ts` now asserts the administration set **by name** — the seventeen screens this
milestone built, read off the running application — beside the prefix rule it already asserted;
and that every route resolves to one of ADR-0032's three areas, with the profile pair named.

## The comparison, by kind

**2026-09-04 — four of eight were a missing surface**, three were the application saying or
connecting the wrong thing, one was the server's.

**2026-09-08 — none of six was a missing surface.** Four were the two ends describing the same
thing differently, one an operation that faults, one a hole in the model. The walk was driven
through the API, and said it could not find the first walk's kind.

**2026-09-11 — one of eight is a missing surface, and it is the interesting number.** An area that
had never had a screen might have been expected to produce four or five; it produced one, and that
one is not a control nobody drew but a picker with nothing to offer — a manifest gap, the third of
its kind in this milestone, each found by the task that needed the list. The rest divide the way
the second walk's did: two are the two ends disagreeing about a shape (#543, #544), three are the
application saying the wrong thing (#545, #547, #549 — two of them in the server's own words), one
is a control that does not mount (#546), one is documentation (#548).

**Which kind is new, and what it says about the method.** Three findings of this milestone —
the webhook rows and the retention rule that came back without their tenant — were invisible to
every unit test, every service test and every previous walk, and became visible only when a
finished screen was driven against a real server: a retry that had never run, a `PATCH` that had
never succeeded. The second walk predicted this kind exactly ("a control exists and behaves
differently from what the server does") and said it could not find it. This walk found three, and
would have found #543 the same way if the second had been able to sign in. That is the case for the
method: driving the interface finds what reading it cannot.

**What the method still cannot do.** The walk was by the people who built the screens, in the
session that built them. Two branches were asserted rather than produced — a broken chain and an
overdue case — because producing them means writing behind the application's back. And
`REPLACE_TENANT` was rehearsed and not run, for the reason on the screen.

## What this says about R-08

The area that had never had a screen has seventeen, every one of them was opened, and thirteen of
fourteen steps completed. What remains is narrower than after the second walk and different in
shape. It is no longer "the frontend decision is absent", nor "a day's work cannot be done in the
application", nor "the walk could not sign in". It is one picker with nothing to offer, one retry
that is answered before it is read, and the standing fact that the pass is done by the people who
built the thing — which the fourth walk, whoever makes it, should be the first not to be.
