# RT-1 — Dependency failure, against real containers

**2026-08-25, local development machine.** RT-1 asks what happens when an optional dependency
fails: the core write path must stay open, the degradation must be visible and correctly
attributed, and recovery must need nothing but the dependency coming back
([observability-reliability.md §12](../architecture/observability-reliability.md)). Until C-12 the
test proved this against an HTTP stand-in; this is the first run in which the dependencies are the
real adapters against real containers, stopped mid-flight.

Unlike RT-8, which needs a cluster and a by-hand rollout, this test runs in `gate-resilience` on
every pull request from C-12 onwards. This file records the run that proved the gate before it
became one — the later evidence is every green `Resilience RT-1..RT-12` check.

| | Value |
|---|---|
| Test | `TestRT1AStoppedContainerDegradesExactlyItsOwnFeature` ([test/resilience/rt1_container_dependency_test.go](../../test/resilience/rt1_container_dependency_test.go)) |
| Environment | macOS (Apple Silicon), Docker Desktop, server 29.1.2 |
| Images | `minio/minio:latest`, `axllent/mailpit:latest`, `postgres:16-alpine` |
| Duration | 4.14 s for the test; 7.76 s for the whole `gate-resilience` suite |
| Outages | 2 — object storage and SMTP, each a `docker stop`, one at a time |
| Core writes during the outages | 40 requested / 40 committed / 0 slowed (bound: 2 s per 20, held with the storage timeout at 5 s) |
| Messages delivered | 3 sent / 3 in the mailbox — one while everything was up, one **during** the storage outage, one as the recovery probe after the SMTP outage |
| Degraded features during the storage outage | exactly `media`, reason `dependency.unavailable`, with a timestamp |
| Degraded features during the SMTP outage | exactly `notifications`, reason `dependency.unavailable`, with a timestamp |
| `/readyz` during both outages | ready — an optional dependency never gates readiness |
| Recovery | automatic in both cases: the container back, the cool-down passed, one probe — no restart, no reconfiguration, no manual step |

## What the run proves that the stand-in could not

The stand-in scripts its outage: a handler answers 500, and the timing, the error shape, and the
recovery are all the test's own fiction. Here the outage is a stopped container — a refused
connection on a port that answered a moment ago, which is what a dead MinIO or mail server
actually presents — and the code under test is the shipped composition: the S3 and SMTP adapters
behind the same breakers, bulkheads, and probes `cmd/server/main.go` wires, reporting through the
same registry and metrics. The write path is real too: rows through `infrastructure/postgres`
into a migrated PostgreSQL, not a counter.

Two details of the run are worth keeping:

* **Attribution is asserted, not assumed.** Each outage runs while the *other* dependency is up
  and probed, and the report must name exactly one degraded feature. The message sent during the
  storage outage — and found in the mailbox — is the positive proof that a stopped bucket does
  not touch mail.
* **The metrics tell the whole story both ways.** `hubtask_circuit_breaker_state`,
  `hubtask_dependency_up`, and `hubtask_degraded_mode` were asserted at 2/0/1 during each outage
  and back at 0/1/0 after each recovery — a gauge that only ever went up would keep showing an
  outage that ended hours ago.

## What it does not cover, and where that lives

* **The AI row of the degradation table** stays with the stand-in in
  [rt1_optional_dependency_test.go](../../test/resilience/rt1_optional_dependency_test.go) until
  `0.7.0` builds the adapter.
* **Both dependencies down at once** is not asserted. Each breaker, probe, and feature is
  per-dependency state with no shared path, and the single-outage runs in both directions pin the
  attribution; a combined outage adds no new mechanism.
* **The catch-up half of the SMTP row** — notifications queued during an outage delivered after
  it — belongs to the delivery job and its queue (C-09), not to this test. What RT-1 pins is the
  degradation and the recovery of the send path itself.

## Repeating it

```bash
make gate-resilience
```

Docker is the only requirement beyond `make tools`. The images are overridable
(`HUBTASK_TEST_MINIO_IMAGE`, `HUBTASK_TEST_MAILPIT_IMAGE`, `HUBTASK_TEST_POSTGRES_IMAGE`) so the
support matrix can vary them. The dependency containers bind fixed loopback ports for the length
of the test, because the daemon re-allocates a random binding on restart — an endpoint that moved
during the outage would test reconfiguration, not recovery.
