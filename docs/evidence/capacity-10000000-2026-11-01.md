## What the run found, and R2

A diagnosing run (`HUBTASK_LOAD_EXPLAIN=1`, test/load/README.md) kept the slowest plan per query:
[`plans-10000000.json`](capacity-10000000-2026-11-01/plans-10000000.json). R2 then repeated R1 with R3's walk on
commit `15d444f8a`, with the fixes below:
[`capacity-10000000-r2.json`](capacity-10000000-2026-11-01/capacity-10000000-r2.json),
[`errors-10000000-r2.json`](capacity-10000000-2026-11-01/errors-10000000-r2.json). No server error
and no refusal on any path or side.

The hub's level beside two writers: P95 23 ms in the largest workspace (R1 351), 86 and 61 ms in
the others (R1 101 and 73); writes P95 44, 21 and 21 ms.

1. **A collection's page - fixed.** The plan was PostgreSQL's generic plan of a prepared
   statement: it keeps both branches of `narg IS NULL OR …`, so `wi_level_order_idx` answered
   neither and 326 898 rows were read and sorted for 51. The pools now plan every statement for
   its own arguments (`plan_cache_mode = force_custom_plan`, known-traps.md).
2. **The board and the count over the hub in the largest workspace - open.** Both read every
   entry they cover: the board numbers 407 923 rows of one collection by a window function, the
   count reads 1 223 768 rows of the hub's three collections. That is linear in the entries, not
   a wrong plan; at 1.2 million entries it misses the 200 ms read target. What would close it is a
   count kept the way the hub's figures are (UC-WRK-29) and a board read per column; neither is
   built yet.
3. **The hub's level in the largest workspace - fixed.** Its figures took longer than the read's
   300 ms deadline, so nothing was kept and every read paid the deadline again for the mark. A
   count the deadline cuts off is now counted once more beside the read and kept, one at a time
   per figure (domain-model.md §2, UC-WRK-29).
4. **The cancelled statements - explained, fewer.** They were the figure deadline's: 833 of
   `CountFigureProgress` and 71 of `CountFigureDue` in the diagnosing run, now named by query in
   the error rows. R2 has 352, all in the mixed phase, where every write leaves the kept count
   behind and the first read after it is cut off before the late count answers the next; a read
   while that count runs is marked at once and counts nothing.
5. **R3's walk - a walk now.** It signs in with every scope a session carries, settles on a
   screen's own requests rather than the network, and counts every refusal with its path. It
   found that a collection read the workflows in a workspace without the module (`refused 403:
   GET /api/v1/workflows` on every workspace) - fixed - and that the browser's replica of a
   workspace this size cannot be taken: the snapshot of 1.2 million entries is about a gigabyte
   (offline-sync.md §1 asks for everything; 66 867 entries measured 60 MB). The walk aborts the
   snapshot as it aborts the stream; how far a browser's replica reaches is the owner's question.
   R2's walk of the three workspaces' start, hub and collection then saw no console error, no
   failed request and no refusal.
