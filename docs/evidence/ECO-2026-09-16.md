## 1. CalDAV: the calendar of a view, read and written back

A collection with three dated entries; a view *ECO dated* over them (`due_at` not null); a
calendar feed minted over the view (`hubctl calendar mint`).

| Step | Request | Answer | Read back through the API |
|---|---|---|---|
| 0. Discovery | `GET /.well-known/caldav`, unauthenticated and with Basic | **401, no redirect** — the redirect sits behind the Bearer-only middleware | — |
| 1. Principal and home | `PROPFIND /caldav/` (Basic) → `current-user-principal`; `PROPFIND` the principal → `calendar-home-set` | `/caldav/principals/{account}/`, `/caldav/calendars/{account}/` | — |
| 2. The calendars | `PROPFIND` depth 1 on the home | *Calendars*, and *ECO dated* with a `getctag` | — |
| 3. The todos | `REPORT calendar-query` for `VTODO` | three `VTODO`s: *Book the venue*, *Send the agenda*, *Print the badges*, each with `getetag "2"` | — |
| 4. Tick one | `PUT` *Book the venue* with `If-Match: "2"`, `STATUS:COMPLETED`, `PERCENT-COMPLETE:100` — and no `DUE`, which a curl forgets and a client would not | `204` | `is_completed: true`, `completed_by` the owner — **and `due_at: null`**: a PUT replaces the resource, so the due date the body did not carry is gone, which is WebDAV and not a defect. The entry thereby left the *dated* view |
| 4b. Edit it again | `PUT` the same address, with and without `If-Match` | **500** — the address is no longer a member of the calendar, so the write took the "create" path and `CreateWorkItem` met the primary key | — |
| 5. Redate one | `PUT` *Send the agenda* with `If-Match: "2"`, the whole `VTODO`, `DUE;VALUE=DATE:20261224` | `204` | `due_at: 2026-12-24T00:00:00Z`, `due_date_only: true`, `version: 3` |
| 6. Make one | `PUT` a new address with `If-None-Match: *`, a random (v4) UID as Reminders would | **`403 creation-needs-uuidv7`** — by design (`CalDavWrite.go`): the client's UID becomes the entry's id only when it is a UUIDv7 | — |
| 6b. Make one, v7 | the same with a v7 UID minted by hand | `201` | *Made in the calendar client*, `TASK`, in the view's collection, `due_at` the date given |

Three findings, filed: [#719](https://github.com/Jersyfi/hubtask/issues/719) (discovery answers
401), [#720](https://github.com/Jersyfi/hubtask/issues/720) (a PUT to an existing entry outside
the view is a 500), [#721](https://github.com/Jersyfi/hubtask/issues/721) (creation needs a v7
UID, which Apple's clients do not mint — a product question).

## 2. Imports: the file, its counts, and the run's report

**Trello.** The fixture holds 4 lists, 4 labels, 5 cards (one with an empty name), 4 checklists
with 5 items (one card carries three checklists, so three work packages), 2 comments and 3 member
assignments. `hubctl --json import trello … --wait 3m`: `SUCCEEDED`, report
`{containers: 1, buckets: 4, labels: 4, work_items: 12, item_labels: 4, comments: 2}`, `new: 27`,
`refused: [{row: 5, code: imports.row_title_missing}]`, `withheld: {unmapped_members: 3}` — the
lists are buckets of one collection, the twelve entries are four cards, three work packages and
five checklist items, the empty card is refused by name, and the three members no account here
matches are withheld rather than invented. **The same file again:** `new: 0`, `skipped: 27` —
idempotent under the source's own identifiers.

**Google Tasks and Microsoft To Do**, after P-10 deployed: the Takeout with a list, a task and its
subtask → `SUCCEEDED`, `{containers: 1, work_items: 2}` (the subtask a `WORK_PACKAGE` under its
task, which is the fix P-10's own e2e run found on its first pass — a `TASK` with a parent is what
the model refuses); the Graph dump with a task, a checklist item and a reminder in *Pacific
Standard Time* → `SUCCEEDED`, `{containers: 1, work_items: 2, reminders: 1}`.

## 4. The n8n node, loaded and fired

`n8nio/n8n:latest` (Node 26) in Docker, the generated package (`pnpm build` → `dist/`: 242
operations under 27 resources, 46 event types, one credential) mounted as a custom extension, so
the two nodes are `CUSTOM.hubtask` and `CUSTOM.hubtaskTrigger`. A credential (*Hubtask API*: the
server on the host at `http://host.docker.internal:8080/api/v1`, a token) and one workflow
imported through the CLI, then activated:

| Step | What happened |
|---|---|
| The credential and the workflow imported (`n8n import:credentials`, `n8n import:workflow`) | both listed |
| Activation (`n8n update:workflow --active=true`, restart) | the trigger's `create` ran `POST /integrations/webhooks` for `de.hubtask.work.item.completed.v1` with the node's own webhook address: the subscription is on the server, `ACTIVE`, `http://localhost:5678/webhook/…/webhook`. The first attempt met `403 access.insufficient_scope (automation:manage)` — the walk's token lacked the scope a subscription needs, which is the token's fault and not the node's — and succeeded once the scope was there |
| An entry completed by hand (`hubctl item complete`) | the server delivered (the subscription's delivery: `SUCCEEDED`, `200`, attempt 1); the workflow ran; the *Hubtask* node's `items → createWorkItem` made a new entry in the collection — **an entry created by it** |
| What the follow-up says | *Follow up on:* — the expression over `$json.data.title` rendered empty, and a probe (`JSON.stringify($json)`) rendered empty too: **the trigger hands on nothing** |
| Why | a listener beside n8n recorded the delivery: `Content-Type: application/cloudevents+json; charset=utf-8`, the CloudEvent whole with `data.title`. n8n parses `application/json` and the form types; anything else leaves the body empty, and the node declares no `rawBody`, so the signature cannot be verified over the bytes either (it answered 200 all the same, which is its own question) |

One finding, filed: [#723](https://github.com/Jersyfi/hubtask/issues/723). The node loads, subscribes,
fires and acts; what it acts on is empty until it reads the delivery as the CloudEvent it is.

## 5. The Zapier app under the platform's validator

`zapier validate` on the generated app (23 checks): **no structural error**. 47 publishing
tasks — 46 of them D021, *description must start with "Triggers when "*, one per generated
trigger, which the generator writes from the contract's own sentence — and 68 warnings: 53
D028 (`cleanInputData` at its default), 13 D004 (an id field without a dynamic dropdown), one
D026 (`base_url` as a free domain field), one D027 (core 17.0.0 where 19.1.0 is current). None
blocks a push; the 46 block the App Directory, which is the owner's step (ADR-0058). Filed as
[#722](https://github.com/Jersyfi/hubtask/issues/722). The schema test (`pnpm test`, 8 tests)
passes beside it and holds what it held.
