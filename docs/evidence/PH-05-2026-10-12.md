## The household

Set up through the product's own operations: the installation's setup (`scripts/dev-workspace.sh
--bootstrap`) made *Paul* the workspace's owner — his display name was then set to *Paul Parent* in
the database, the one step not taken through the product, for the screenshots' sake. Paul gave
*Mara Parent* and *Lena Kind* accounts without an address (`POST /accounts:create-managed`, both
`MEMBER`); each changed the start password at the first sign-in. Lena made the private hub *Diary*
with a collection *Summer* and one entry; Mara made the private hub *Presents*.

## What the database and the API said

From `walk.log`:

- Each opening stored one access ending an hour later, one `EMERGENCY_ACCESS` record for the
  member — `SUPPRESSED notifications.no_address`, the member having no address — and one
  `container.emergency_access_opened` entry whose `changes` do not hold the reason in clear.
- With the switch off, `POST /containers` with `private: true` as Mara answered
  `403 containers.private_hubs_off`, and *Diary* and *Presents* stayed private.
- No script error on any screen.

The mail a member with an address receives — who, when, until when in their zone, the reason, the
hub's name only where they let titles travel — is `RecordEmergencyAccess_test.go`; that the access
notifies before it answers any read, against PostgreSQL, is `private_hub_emergency_test.go`.

## What was seen and left

- On the opened hub, the web app works out the owner's rights from the memberships it holds, which
  leave the workspace's roles out along a private hub (PH-04): for a moment *Import* reads "Working
  out whether you may create collections here". The server decides every act; the screen's own
  gates do not know the emergency access. Reading, which is what the access is for, is unaffected.
- At 375 px the list scrolls sideways, as it did before this change; the emergency column is its
  last.
