# SC-15, D1: a private person and the security of their own account

**When:** 2026-10-13 · **Commit:** `00be810b` (branch `claude/sc-15-walk`)
**Kind:** using ([README](./README.md), "How to walk"). The walk plays a private person who owns a
fresh installation and is its only administrator (`D1`). The server was built from that commit
with the web app embedded, as a native binary on `localhost:18515`, with
`HUBTASK_TENANCY_MODE=single`, roles `api,worker,scheduler` and `HUBTASK_RATE_LIMIT_BURST=600`. It
had **no SMTP** (`/meta/capabilities` answered `features.mail: false`). Its database was its own
PostgreSQL 16 (pgvector), migrated to 0137 and reached as `hubtask_app`, so row level security was
in force. The workspace "Paula at home" was created through the *Set up Hubtask* card, with the
setup code the server printed. The owner is a throwaway account (`paula@d1b.example`). Two more
throwaway accounts, Ben and Carl, were invited by link. The onboarding tour was ended through
`PATCH /accounts/{id}/preferences`. The browser was Chromium through Playwright, in the light theme
and in English, at 1280 × 900 and at 375 × 812 (a phone with touch). The authenticator was the
walk script, which computed RFC 6238 codes from the secret shown on the screen. Each code came from
a fresh 30-second window, because a second code in the same window is refused as a replay. `hubctl`
was built from the same commit.

The screenshots and `walk.log` are in [`SC-15-D1-account-2026-10-13/`](./SC-15-D1-account-2026-10-13/).
The secrets, recovery codes and tokens in them belonged to a database that was deleted after the
walk.

## What was seen

- **The replay rule held throughout.** Every code was taken from a fresh window. A wrong code, a
  replaced recovery code and a used one were each refused with the same one sentence.
- **The trail of proofs:** each privileged press first answered `403 auth.step_up_required`
  (`methods: PASSWORD TOTP RECOVERY`) and then succeeded after `POST /auth/step-up` (201). The
  presses were new codes, turning the factor off, the password change, the token with
  `admin:tenants`, and saving the sign-in rules.
- **Without SMTP, the reset request queues a mail job that cannot go out.**
  `notification.password_reset` failed with `dependency.unavailable` eight times, then was
  dead-lettered. One job was queued for roughly forty requests.
- **A session opened by choosing a new password at sign-in is recorded as `PASSWORD`.** In step
  33, the sign-in proved the authenticator code, then required a new password. The database
  recorded `signed_in_with=PASSWORD` for that session, not "Password and second factor".
- **The *Client* column shows the raw user agent string**, for example "Mozilla/5.0 (Macintosh; …)
  HeadlessChrome/153…", and `hubctl/dev` for the command line. Whether a real Chrome is named more
  plainly was not seen. Sessions opened through the code step show "—" under *Network*, while
  password-only sessions show `127.0.0.0/24`.
- **No script error** was reported on any screen (`pageerror` was listened to throughout).
- **At 375 px** the sign-in card, the session list and the *Sign-in* screen did not scroll
  sideways (`scrollWidth` 375). The profile's setup did (see below).

## What was not walked

- **UC-ID-06 check 2, "Reset":** without a mail server, a reset link never reaches anybody, so no
  session could be opened through a reset. The walk invented no way around the mail.
- **A provider's name in the session list** (the same check): this deployment has no identity
  provider, and the project has none (milestone SC, decision 9).
- **UC-ID-04 check 1, "provider-only account":** there is no provider. The brief's disabled account
  was walked instead. No screen disables a person, so Ben's status was set to `DISABLED` directly in
  the database for that probe. An invited account that had not arrived (Carl) was also compared.
- **The clipboard on a real phone:** *Copy all ten* was proven in desktop Chromium with clipboard
  permission granted.

## What was found

1. **At 375 px the profile's second-factor setup scrolls sideways.** While the secret and the
   code field are shown, the six-place code field measures 356 px wide and its right edge sits at
   389 px, so the page is 389 px wide. The bottom bar is dragged out to 389 px too. The same field
   on the sign-in card fits (375). Measured with `getBoundingClientRect` (walk.log, 22:35:01).
2. **Out-of-range sign-in rules are saved instead of refused at the rule (UC-ID-12 check 8, not
   met).** *Remember previous passwords* = 11 (the hint says "0 to 10", and ADR-0068 caps history
   at ten) and *Minimum length* = 2000 (a password can be at most 1024 characters) were both saved
   with "The sign-in rules were saved." and "Set here." The tenant's settings stored `11` and
   `2000`. The screen then showed 128 for the length, and sign-in enforced `min_length: 128`
   and `history_count: 10`. The person was never told the value was changed. The effect at once:
   the owner's next sign-in demanded "Choose a new password… At least 128 characters". Only the
   browser's own `max` stopped *End a session after* = 31.
3. **A refused recovery code is told to use the authenticator.** In recovery-code mode, a wrong or
   old code gets "That code did not verify. Enter the current code from your authenticator." The
   person typing a recovery code is usually the one without the authenticator.
4. **While the ten codes are shown on the profile, the card above still says the factor is off.**
   It reads "Off. Your password is the only thing between somebody and your account." and "…there
   is no second factor on this account yet", although the factor is already on
   (`03-ten-codes-continue-off-desktop.png`).
5. **The password change's confirmation is drawn in the *Second factor* card,** not in the
   *Password* card where the change was made (`17-password-changed-375.png`).
6. **On an installation without mail, *Forgot your password?* promises a link that cannot come.**
   The card says "If an account exists for it, a link is on its way". The server queues a mail job
   that is dead-lettered. In `D1`, the person is told to wait for a mail that never arrives,
   instead of being pointed to recovery codes. UC-ID-04 says a household without a mail server is
   a separate use case. Here, the card itself is what misleads.
7. **The reset request's response time tells a known address from an unknown one.** The bytes are
   identical (check 1 is met), but over 30 interleaved requests the median was 5.07 ms for a known
   address, 2.36 ms for an unknown one and 2.76 ms for a disabled one, measured from localhost
   (walk.log). That is the information the identical answer is meant to withhold.
8. **An invitation's own sign-in is not routed into the required setup.** With *Required of →
   Everyone* already in force, Ben's *Set the password and sign in* on the invitation card took him
   straight into the workspace with an "Invitation" session and no factor. The setup came only at
   his next password sign-in. The rule's hint does say "at their next sign-in", so this may be
   intended. It is recorded because UC-ID-03's story says a person without a factor "is led through
   the same setup during sign-in".
9. **The *Skip the tour* press did not keep.** After it, the tour came back at the next sign-in and
   kept a later `goto` on the overview, until the tour was ended through
   `PATCH /accounts/{id}/preferences`. The README's step 5 already says to end it that way.
10. **A session that proved the second factor and then chose a new password is listed as
    "Password"** (see *What was seen*). UC-ID-06 check 2 says each session names how it was
    opened.
