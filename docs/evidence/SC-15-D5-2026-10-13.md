# SC-15, D5 — a provider for consumers, on an offered model

**When:** 2026-10-13 · **Commit:** `24b6bded` (branch `claude/sc-15-walk`; the commits after it,
up to `ef0fb177`, touch the trail's screen, the audit list and a switch's hint, none of the paths
walked here)
**Kind:** using ([README](./README.md), "How to walk"). The server was built with `go build` from a
copy of that tree, with the web app (`apps/webapp/dist`) embedded. It ran as one binary on port
18540 in **multi mode** (`HUBTASK_TENANCY_MODE=multi`), with every role, with
`HUBTASK_BASE_URL=http://hubtask.localhost:18540` (Chromium resolves every `*.localhost` to the
loopback address, so each workspace answers at `<short name>.hubtask.localhost:18540`), with an
encryption keyring (`HUBTASK_ENCRYPTION_KEYS`), with `HUBTASK_RATE_LIMIT_BURST=600`, with no SMTP,
and with **`HUBTASK_HTTP_ALLOW_PRIVATE_NETWORKS=true`**. The server needed that setting to reach the
stub model server on 127.0.0.1. Its database was its own PostgreSQL 16 (pgvector) container,
migrated to 0137 with `cmd/migrate`. The server reached it as `hubtask_app`, so row level security
was in force. `hubctl` was built from the same tree. The browser was Chromium through Playwright,
in the light theme and in English, at 1280 × 900 and at 375 × 812 (a phone with touch).

**The installation:** the provider's own workspace "Provider operations" (`ops`), set up with the
*Set up Hubtask* card. Its owner and first operator is Olga Operator (`olga@provider.example`).
A colleague, Paul Platform, was invited into `ops` by link. Two consumer workspaces were provisioned
through the product: `scripts/dev-workspace.sh` ran with an `admin:tenants` token that Olga minted
behind a step-up. They are "Anna's tasks" (`anna`) and "Anna's book club" (`anna-club`), both owned
by Anna (`anna@consumer.example`). Every account is a throwaway account on a database that no longer
exists. The command output and the measured values are in
[`SC-15-D5-2026-10-13/walk.log`](./SC-15-D5-2026-10-13/walk.log).

**The offered model** is a stub, an OpenAI-compatible server that the walk ran on 127.0.0.1:18541.
It logged every request it received and answered `chat/completions` with a fixed JSON title and
`embeddings` with a constant 1536-wide vector. No real AI provider was called. That follows the
spirit of milestone SC Decision 9 and record decision D5.

## What was seen

- **The subdomain.** The setup card itself stayed on `hubtask.localhost:18540` after *Create* and
  signed Olga in there. The workspace answered at `ops.hubtask.localhost:18540`, and provisioning
  printed `http://anna.hubtask.localhost:18540/` and `http://anna-club.hubtask.localhost:18540/`.
  Each one opened its own sign-in card naming its host.
- **No call before consent.** The stub's log stayed empty through all of the following:
  - offering three models;
  - setting the `ai` area;
  - provisioning;
  - Anna's `suggestion ask` and `:suggest-fields` (refused `503 ai.unavailable`);
  - `:duplicates` (`204`);
  - two searches;
  - opening the AI screen, the entry and search in the browser.

  In that state `hubctl ai source show` read `source OWN`, `may use OFFERED, LOCKED (INSTANCE)`. The
  workspace's own model was not allowed there, so nothing answered. The screen showed both switches
  off.
- **One call after consent.** The stub's first and only line from the suggestion is:
  `POST /v1/chat/completions model=stub-chat-large-2 auth=Bearer stub-k…`. That is Birch's completion
  model as changed by `admin ai set`, with Birch's key, kept across the change.
- **Search by meaning on the offered model.** With Birch chosen from `hubctl` by name, the search
  query reached the stub as `POST /v1/embeddings model=text-embedding-3-small`. The entries had not
  been embedded yet, because the embedding pass runs hourly, so the search found nothing. That shows
  the query takes the offered model's path. It does not show a ranked answer.
- **The budget.** The figure went from 0 to 132 tokens after the suggestion, which is exactly the
  `total_tokens` the stub answered. After the query embedding it read 164 tokens; the stub had
  answered 8 for that call. `usage_record` holds `ai_tokens_per_day 164`.
- **Switching off.** Both the screen's switch and `ai source set --source NONE` stopped the next
  call. The stub received nothing after either.
- **The keys are sealed.** `ai_provider.api_key_enc` is 111 bytes under key id `a` for both offered
  models, and the made-up key text does not occur in it. The instance journal holds four
  `instance.ai_provider_configured` entries and one `instance.ai_provider_removed`.
- **Admission for a provider without a directory.** `--admits ANY` on GENERIC is refused before
  anything is stored: "GENERIC has no directory to bound who it admits, so offered to every
  workspace on this installation it may only let in people each workspace invited. A workspace may
  still configure it for itself with a wider rule." The screen offers only that answer.
- **The issuer must be https.** The local fake issuer on `http://127.0.0.1:18542` is refused by the
  screen's rules and by `hubctl`: "That is not an issuer address. It has to be an https URL…"

## What was found

1. **An installation cannot offer a sign-in provider (UC-INS-11 checks 1–3, not met).** Every
   *Save the provider* and every `hubctl admin provider add` that passes validation fails, for
   Google and for GENERIC alike. Olga sees "Something went wrong on our side. Reference …". The
   server logs `use_case=ConfigureInstanceIdentityProvider error="INTERNAL: internal
   (audit.entry_incomplete)"` (references `b2541aff…`, `4f450f8b…`, `9f7d39e3…`, `33b9fd57…`), and
   `identity_provider` keeps 0 rows.

   The likely cause, read and not changed:
   - `ConfigureInstanceIdentityProvider.Execute` passes the zero tenant to
     `IdentityProviderWriter.ConfigureAt`
     (`core/application/service/admin/InstanceProvider.go`).
   - `ConfigureAt`'s `record` writes the workspace-trail entry with that `TenantID`
     (`core/application/service/identity/IdentityProviderConfig.go`, `record`).
   - `audit.Entry.Validate` refuses a zero tenant (`core/port/audit/Port.go`).

   The same form in a workspace works: Anna's own Google provider was answered `201`. This blocks
   the D5 promise "sign-in with public providers that admit only people who were invited".
2. **`hubctl admin ai set` as its usage line says does not work.** The usage line is
   `admin ai set <id> --name …`. With the identifier first, the flag parser stops at it and answers
   "admin ai set needs --name, --processor, --kind, --base-url and --jurisdiction", followed by the
   whole usage text. With the identifier last, the change works. `adminAiWrite`
   (`cmd/hubctl/AiOffered.go`) reads the identifier from the remaining arguments. It does not read it
   through `takeID`, which exists for exactly this trap (`cmd/hubctl/Command.go`).
3. **The Google preset leaves *Issuer* empty.** The field is required. On the installation's
   *Offer a provider*, saving it empty sends the form and answers only "The request contains invalid
   values." A workspace's *Add a provider* leaves the field empty too; it was filled there before
   saving. One issuer serves every Google account, and the preset's own banner says so.
4. **The locked legal line is printed twice.** Under each locked field on a workspace's *Sign-in* →
   "Legal links", "Set by the installation for every workspace." appears twice, at 1280 and at
   375 px (`13-…`).
5. Smaller observations, recorded rather than judged:
   - The GENERIC refusal names the code "GENERIC" where the screen says "Another provider".
   - The day's AI figure counted 32 tokens for a query embedding the stub reported as 8.
   - While no model is switched on, the entry has no *Ask AI* at all rather than a disabled one with
     its reason.
