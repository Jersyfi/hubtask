# O-1 — The alerting backend, stood up and made to fire

**2026-09-01, a local `kind` cluster.** O-1 asked which backend carries the alerts of the
environments we run, and H-12 answered it with a manifest rather than a paragraph
([observability-reliability.md §13.1](../architecture/observability-reliability.md)). This file
records the run that proved the manifest before the integration host was ever touched: the stack
applied to a throwaway cluster, a target discovered, an alert driven to fire from a real scrape,
and the mail read at the far end.

The rehearsal is not the environment. What it establishes is that
[`deploy/integration/monitoring.yaml`](../../deploy/integration/monitoring.yaml) works as written
— which is what makes running `bootstrap.sh` on the host an application of a tested file rather
than a first attempt.

| | Value |
|---|---|
| Cluster | `kind`, Kubernetes v1.34.0 (the host runs k3s v1.36.3) |
| Manifest | `deploy/integration/monitoring.yaml`, one edit: `storageClassName` `local-path` → `standard`, kind's default |
| Prometheus | `prom/prometheus:v3.6.0` — the Makefile's `PROMTOOL_VERSION` |
| Alertmanager | `prom/alertmanager:v0.34.0` |
| Catcher | `axllent/mailpit:v1.31.0` |
| Rule files loaded | 4 — the three shipped, built into a ConfigMap from `deploy/observability/alerts/`, plus the environment's own |
| Alert rules evaluated | 23 — 21 from the catalogue, 2 from the environment |
| Target discovered | 1, by `role: endpointslice`, relabelled to `instance=<pod>`, `role=api` |
| Alerts delivered | 2 — the watchdog, and a provoked A-14 |

## What the run proves

**The rules that ran are the files the gate tests.** Prometheus loaded four rule groups, and three
of them came from a ConfigMap `bootstrap.sh` builds out of `deploy/observability/alerts/` — the
same three files `make gate-observability` checks with the same Prometheus version. Nothing was
transcribed, so there is no second copy to drift.

**Discovery finds pods the way the chart exposes them.** The synthetic target was given the
chart's own service name (`hubtask-metrics`) and port name (`ops`), and nothing else — so what was
under test was the relabelling, not a hand-fed series. Prometheus found it, kept it, and labelled
it `instance=fake-hubtask-67fb866844-mmvw6`, `role=api`: the pod's name rather than an endpoint
address that would not exist by the time anybody read the alert.

The first attempt to this target failed, and the failure is worth keeping: `non-compliant scrape
target sending blank Content-Type`. Prometheus 3 refuses an exporter that does not say what it is
sending, which is a check on the exporter and not a setting to loosen — the fake was fixed to send
`text/plain; version=0.0.4`, and `fallback_scrape_protocol` was deliberately *not* added.

**A catalogue alert reached the far end, with its runbook.** `hubtask_config_invalid_total{key=
"config.base_url_missing"} 1` was served from the target at 17:36:17Z; A-14 became pending at once,
fired at 17:41:17Z after its `for: 5m`, and the mail landed at 17:41:47Z:

```text
Subject: [FIRING:1] HubtaskMisconfigured A-14 (integration fake-hubtask-… hubtask
                    config.base_url_missing api ticket)
To:      ticket@integration.hubtask.eu

alertname = HubtaskMisconfigured      severity = ticket
alert_id  = A-14                      environment = integration
key       = config.base_url_missing   role = api

runbook = RB-A14-misconfiguration.md
summary = The process is running with flagged configuration (config.base_url_missing)
```

The catalogue ID, the environment, the pod, the offending key and **the runbook filename** all
arrive in the message. §11's rule is that no alert ships without a runbook; this is that rule
holding at the only moment it matters, which is the moment somebody is reading the page.

**The watchdog proves the path continuously.** `HubtaskAlertingPathAlive` fired on the first
evaluation and was delivered to its own mailbox at 17:32:06Z, thirty seconds after Prometheus
started. Every silence from every other rule means nothing until that message has arrived, and
nothing inside Prometheus can establish that for itself.

## What the run found

**Discovery was using a deprecated API.** The first configuration used `role: endpoints`, and the
cluster answered in the log — `v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1
EndpointSlice` — on every refresh. The host runs 1.36. It was changed to `role: endpointslice`,
with the Role moved into the `discovery.k8s.io` group, and re-proved against the same target.

**A-12 fires here permanently, and correctly.** The rule is written as `absent(...)` on purpose:
no backup metric at all is exactly what "nobody configured a backup" looks like, and it is a page
on any real installation. This environment keeps no backups by a decision written down in its own
README. So A-12 is routed to a receiver that sends nothing — not silenced by hand, because a
silence expires and this decision does not, and because a route sits in a diff where somebody can
argue with it. Verified with Alertmanager's own router:

```text
severity=watchdog                    -> watchdog
severity=page,alert_id=A-01          -> page
severity=page,alert_id=A-12          -> muted
severity=ticket,alert_id=A-09        -> ticket
severity=info,alert_id=A-18          -> info
```

## What it does not prove

The integration host has not run this yet — `bootstrap.sh` applies it, and applying it is the
owner's step. What is untested until then is k3s rather than kind: the `local-path` storage class,
and discovery under 1.36 rather than 1.34. Neither is a property of the manifest, and both fail
loudly at `rollout status` rather than quietly.

And no alert here came from Hubtask. The target was a synthetic exporter serving one series,
because what needed proving was the path — discovery, evaluation, routing, delivery — and a real
deployment would have proved the same path while taking longer to arrange. The first alert from
the application itself will be the ordinary operation of the environment, not an experiment.
