# QS-09 — The product without AI

**2026-09-09, local development machine.** The claim
[arc42.md §10.2](../architecture/arc42.md) makes in one line — *"the AI provider fails or is
disabled → all core features stay available"* — and the one
[`ai-first.md`](../architecture/ai-first.md) opens with: *AI is never a dependency of the core.*
[ADR-0012](../adr/ADR-0012-ai-first-mcp.md)'s positive consequence is the same sentence
from the other side: *"the application is fully usable without AI."*

`0.7.0` added a port, two adapters, four features and three protocol methods across sixteen tasks.
J-17 is the seventeenth, and its whole job is to run the product with none of it configured and
look.

## The environment carried no AI variable

There is exactly one, and it is an operator's signature rather than a switch:
`HUBTASK_AI_ALLOW_THIRD_COUNTRY_TRANSFER` ([deployment.md](../architecture/deployment.md),
[data-protection.md](../architecture/data-protection.md) §6). It defaults to false and nothing in
this run set it. `HUBTASK_AI_API_KEY` is `hubctl`'s, on the other side of the wire, and the session
never used the command that reads it.

So "no AI variable at all" is not a mode the suite was put into. It is the ordinary state of every
gate in this repository, which is the stronger version of the claim: the product's default
configuration *is* the configuration with no AI in it.

switches one section rather than selecting a subset: a second script written for this run would be
a script written to pass.

The one section that changes is the provider's. With AI it configures a stub and asks it things;
without, it asks the five routes what they answer to somebody with no provider.

## The refusal, and why it needed a fix first

Every route answered `503` on the first run, which was right, and the problem document was this:

```json
{"type":"https://docs.hubtask.dev/errors/dependency_unavailable",
 "title":"dependency_unavailable","status":503,"code":"dependency_unavailable",
 "request_id":"c59580233b59f49b2eb73a745e597bc4"}
```

No `detail_code`. The QS-09 row promises `ai.unavailable`, `locales/en.json` carries the sentence
for it, and the client could never receive the code to render it. `ProblemFrom` was stripping
`detail_code` and `params` for every status at or above `500` — correct reasoning for a `500`,
whose parameters may come from a driver, and exactly backwards for a `503`, which exists to say
which dependency is out of reach.

The `sync-engine`'s own test asserted `detail_code: 'sync.stream_unavailable'` with `params`, a
response the server could not send. Both sides passed, against each other's imagination.

That is issue #500, fixed in #501, and this run is the one that found it.

## Two things this file does not prove

**That an installation with a *broken* provider degrades correctly.** It is the other half of the
row and it is proved elsewhere, against a real stopped container:
[RT-1-2026-09-09.md](./RT-1-2026-09-09.md), `TestRT1AStoppedContainerDegradesExactlyItsOwnFeature`.
The distinction between the two is the point — *not configured* is not *broken*, and this run's
`/meta/health` says `ok` with an empty `degraded_features` where RT-1's says `down` with two
features, a reason and a timestamp.

**That a client renders the absence well.** The manifest now answers `ai_suggestions: false` and
`semantic_search: false` (issue #502), which is what a client needs; whether the web app uses it is
F5's, and `AISuggestion` is specified as *"gone without residue when AI is switched off"* in
[roadmap.md](../roadmap.md)'s F5 row.

## What was found

Three defects, all invisible to the suite, all left as their own issue because J-17's acceptance
says a defect found here becomes one:

| | |
|---|---|
| #500 → #501 | A `503` lost its detail code, so no client could tell which dependency refused |
| #502 → #505 | The manifest never mentioned AI, and `semantic_search` answered whether the *store* existed rather than whether meaning search could happen — so the reference stack, which runs pgvector, published `semantic_search: true` with no provider and every search lexical |
| #507 | `/api/v1/meta/health` answers `404 route.operation_not_available`. The report is complete and is served on the internal listener; the authenticated door the contract declares was left "until A-06", and A-06 landed in `0.1.0`. W-03's acceptance in `milestone-0.3.5.md` says the route answers in a running container, and F1 plans a `HealthBanner` fed from it |

None of them is a failure of the claim QS-09 makes. The product **is** usable with no AI:
everything worked, nothing crashed, and no route answered `500`. All three are failures of the
product to *say so* — the refusal without its code, the manifest without its answer, and the report
without its door — which is the part that only gets tested by somebody running the installation
nobody runs and then asking it how it feels.
