# F8 — The rule flow, walked

**2026-09-20, a local server built from the F8 branches (`main` at `5bb2d315` with F8-07's
branch, PostgreSQL 16 in a container), the web client driven by Playwright over the real
API.** The walk [`milestone-F8.md`](../backlog/milestone-F8.md) F8-08 asks for: a rule written
on the canvas from nothing, probed, saved, switched on, run by a real event, read back on the
runs page, its label deleted and the finding seen, repaired, switched on again. Walked twice —
once as the branches stood, which is where the findings below come from, and once on the same
evening's fixes, which is the transcript below. The walk on the integration environment waits
for `main` to be deployed with F8 on it.

| | Value |
|---|---|
| Server | `go build ./cmd/server` from the checkout with the built web bundle embedded, `HUBTASK_ROLES=api,worker,scheduler,automation`, single tenancy, the credential burst raised to 60 for the reason finding 7 gives |
| Workspace | `f8-walk`, seeded by SQL the way `scripts/hubctl-e2e.sh` seeds its bootstrap: one `USER` account *Walker* with `OWNER` at the workspace, its password hashed by `infrastructure/crypto.Passwords` and stored on the account so the walk signs in the way a person does |
| Session | `POST /auth/sessions` — a real session, because a personal access token cannot open the stream or the snapshot and the client then burns its own budget looping (the memory of the F6 walks) |
| The world | hub *Kitchen renovation* → collection *Permits*, labels *Urgent* (red) and later *Priority* (amber), a service account *Automation* given `MEMBER` on the hub after finding 6, three entries created over `POST /items` |
| Credentials | the password and the token in a scratch directory with mode 600; in no file of this repository, no log and not this document |
| Transcript | Playwright scripts, one per stage, each opening the client at the route named and reading the DOM; the pictures they took stayed in the scratch directory |

**Method.** Every stage is what a person would do on the screen, driven by the same locators
the F8-05 to F8-07 walks use, against the real server rather than a stub. Where the walk
needed something the screen does not offer — an entry created by another person, a label
deleted, an account retired — the API did it under the same session. Everything the first pass
found is an issue, not a fix in this task (F6-15's rule); the four that blocked the walk's own
path were fixed in pull requests of their own the same evening and the second pass ran on them.

## 1. A rule from nothing

`/administration/rules/new` opens with the trigger card *Something happens* holding no event,
the empty gate *runs on every match*, no step, and the guardrails *Stop the run · no hourly
bound*. The header says *Not saved yet* and the name reads *When : nothing yet* with the
*automatic* mark.

The trigger card selected, *Which event* set to `de.hubtask.work.item.created.v1` — the card
says *item created* under its title (after finding 5; before, it printed the wire name). The
*Applies in* pill: *The collection Kitchen renovation · Permits*; *Runs as*: *Automation
(service account)*. *Add a label* clicked in the palette lands as step 0 with its form from the
manifest's `action_fields`: `item id` marked *Required at the run — The entry to label*, and
`label id` as a picker over the collection's labels, *Urgent* chosen. The name follows:
*When item created: add a label*; the sentence: *When item created happens in The collection
Kitchen renovation · Permits, then add a label — as Automation (service account).*

## 2. Probed, unsaved

The Probe tab, the event `item.created`, the subject found by typing *permit* into the search
and choosing *Building permit application* (an entry created a minute earlier). *Run it
through* — the canvas: trigger *starts it*, step 0 *would run*; the panel says one step would
run. The definition that left was the canvas's, unsaved.

## 3. Saved, switched on

*Save the rule* → `201`, the editor moves to `/administration/rules/01a0c068-cb51-…` and the
header offers *Switch it on*. Switched on: *Switch it off* and the *On* badge.

## 4. A real event

`POST /items {type: TASK, title: "Electrical inspection", collection_id: Permits}` under the
session. Within two seconds the run is in the log:

```
GET /automation/runs?rule_id=01a0c068-cb51-74b2-bb81-79076c9e0be9
  status SUCCEEDED, trigger EVENT, action_results [{path "0", kind ADD_LABEL, status SUCCEEDED}]
item_label: "Electrical inspection" → "Urgent"
```

The first two attempts of this stage are findings 1 and 6: `usecase.input_invalid` (the run
supplied no `item_id`) and `items.not_found` (the service account held no role). The Runs tab,
opened after the run, says *Failing · 2 of 3 runs failed* over the three attempts and draws
the succeeded run onto the canvas — *started it*, *ran* — when its row is clicked (after
finding 5; before, the tab said *No run yet* until a reload).

## 5. The runs page

`/administration/runs`: the strip *3 runs shown · 1 succeeded · 0 did not apply · 0 held back ·
2 failed*, the three runs newest first with their rule's name, *Started by: Something
happens*, and the failed ones' `automation.action_failed` in words. `?rule_id=…` opens
prefiltered with the rule chosen in the *Rule* select.

## 6. The label deleted, the finding seen

`DELETE /containers/{Permits}/labels/{Urgent}` → `204`. Six seconds later, without opening
anything:

```
GET /automation/rules/{id}
  enabled true, checked_at 2026-09-20T20:12:34Z,
  findings [{level ATTENTION, path /actions/0/params/label_id,
             code automation.finding.reference_gone, params {kind label, id 01a0c061-c176-…}}]
```

— the deletion's subscriber queued the `automation.check` job and the worker ran the sweep.
`/administration/rules`: *The check found one rule that needs your attention. 0 cannot run and
have been switched off; 1 run, but a step would find nothing where it points.* The card:
*Needs attention*, and under it *Step 0: The label this step points at no longer exists; the
step would find nothing.* The rule's own screen: the flag at step 0's card in the same words,
the banner *Needs attention* under the header.

## 7. Repaired

Step 0 selected, `label id` set to *Priority*, *Save the rule*. The first pass answered `500`
(finding 2). On the fixes: `200`, the check runs right after the save (finding 4), the flag
leaves the card, the banner goes, the list says *Works*. The rule was never switched off — an
`ATTENTION` finding is information — so *switched on again* did not arise on this path.

## 8. The BROKEN path — blocked

The service account set to `DISABLED` (there is no route for it; SQL stood in for an
operator), then `/administration/rules` opened: `POST /automation/rules:check` answers `503`
and the list shows the failure instead of the rule. The server log:

```
CheckRules … writing the notification …: insert or update on table "notification"
  violates foreign key constraint "notification_item_id_fkey"
```

Finding 3. The check found the rule broken and disabled it inside its transaction, then the
notification to the author could not be written and the transaction rolled back — so nothing
was switched off, nothing was told, and the list is unreadable for as long as a rule is
broken. The same write ends the failure streak of G-07, which has therefore never switched a
rule off either. The path is walked to the end once #814 is fixed.

## 9. Phone width and dark

At 375 px the canvas stays, the sheet bar offers *Details* and *Probe*, a card tapped opens the
sheet with its form. Dark scheme: every surface and mark from the tokens, nothing lost.
