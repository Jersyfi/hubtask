# SC-15, D4: a company running Hubtask itself, signing in through Microsoft Entra ID

**When:** 2026-10-13 · **Commit:** `00be810b` (branch `claude/sc-15-walk`)
**Kind:** using ([README](./README.md), "How to walk"). This walk plays the company's IT
administrator, who is the workspace owner. The workspace is `Acme GmbH` on a single-workspace
installation (`HUBTASK_TENANCY_MODE=single`), set up with the printed setup code through
`scripts/dev-workspace.sh --bootstrap`. It has its own PostgreSQL 16 (pgvector), migrated to 0137
and reached as `hubtask_app`, so row level security is in force. Mail went to a local mail catcher
(mailpit). The browser was Chromium through Playwright in the light theme and in English, at
1280 × 900 and at 375 × 812 (a phone with touch).

The server ran in two ways, both built from that commit with the web app embedded:

- **Part A (Microsoft):** a native binary on `localhost:18530`. Private networks were **not**
  allowed.
- **Part B and after (the fake issuer, the auditor, the service account):** the same commit built
  for Linux and run in an `alpine:3.20` container, against the same database and on the same
  port. It ran with `HUBTASK_HTTP_ALLOW_PRIVATE_NETWORKS=true`. The workspace demands an `https`
  issuer, and on macOS a Go binary trusts only the system keychain. In the container,
  `SSL_CERT_FILE` could add the walk's own throwaway CA instead. The fake issuer was a small Node
  script on this machine, signing RS256 ID tokens and publishing a JWKS:
  - the server reached its discovery, token and key endpoints at
    `https://host.docker.internal:18533`;
  - the browser reached its authorization endpoint at `http://localhost:18534`.

  The fake issuer checks PKCE: the verifier matched the challenge on every exchange. It was
  configured in the product as the third kind, *Another provider*.

The throwaway accounts were all seeded through the product (an invitation, its mail and its
redemption):

- the owner `it-admin@d4.example`;
- `audrey.auditor@acme.example`, holding the `AUDITOR` role;
- `erika.mustermann@acme.example`, a member with a password and a second factor.

Newcomers who arrived through the fake issuer: Nora, Otto and Paul (`@acme.example`). The
transcript of every press and answer is [`SC-15-D4-2026-10-13/walk.log`](./SC-15-D4-2026-10-13/walk.log).

## What was seen

- **No script error** on any screen.
- **The issuer was checked before saving, both ways.** Microsoft's public discovery document was
  fetched from this machine. The fake issuer logged the server's `GET /.well-known/openid-configuration`
  at each save.
- **The fake issuer's authorization requests** carried `response_type=code`,
  `scope=openid profile email` and `code_challenge_method=S256`:
  - a sign-in sent no `prompt`;
  - the connect link and the step-up sent `prompt=login max_age=0`.
- **The audit entries.** `identity.provider_configured`, `identity.provider_offered`,
  `identity.provider_linked`, `access.token_created` and `auth.step_up` were all present. None
  held an address, a secret or a token.

  and the password field every later time.
- **The auditor's screens.** The auditor's account menu offers *Workspace administration*, and
  its navigation lists every section, *The trail* included. The screens draw their controls
  enabled for the auditor (*Save*, *Change*, *Remove*, *Add a provider*, *Require a new password

  showed nothing. *Overview* offers the auditor *Create hub*.

  account, and offers `admin:tenants` on a single-workspace installation.
- **A date typed is not the date shown.** A token expiry typed as 2026-12-31 is listed as

## What was not walked

- **Microsoft's sign-in itself, the token from Microsoft, and a real tenant's admission.** The
  project has no Entra account (milestone SC, Decision 9). The walk stopped at the authorization
  request (step 9) and fetched only Microsoft's public discovery document. The directory id saved
  is made up. Through Microsoft, nothing shows that a person of a listed directory is admitted,
  that one outside it is refused (UC-ID-08 check 3), or that the shared `organizations` endpoint
  verifies a real token. The return from a provider, the newcomer's role, the LINK step and the
  session's name were walked with the local fake issuer, configured as *Another provider*. That
  issuer is not authoritative for any address, so it always goes to the LINK step for an
  existing account.
- **UC-ID-10 check 3's count.** That a wrong password in the LINK step counts against the sign-in
  limits was not measured. The right password followed at once, and a success clears the counter.
  The trail has no entry for a failed password anywhere, by design.
- **UC-ID-08 checks 3, 4 and 6 at the provider**, and `hubctl` for UC-ID-17 check 3 and UC-INS-06
  check 2. Only the web app was walked. A platform's service-account token on an installation
  with operators (multi mode) is D5/D7's.
- **The fresh-proof dialog the owner met with the password off and no provider connected.** The
  script was waiting for a password field that did not come, and closed. The code (`StepUp.go`)
  offers no password proof while the password is switched off, so this owner had no proof to
  give in that session.

## What was found

1. **A workspace without the password cannot connect its provider by mail. The arrival fails as
   "Internal".** It happened twice, with two fresh links (step 18).
   - **What the owner does:** asks *Get a sign-in link by mail* with the password off, opens the
     link, and signs in at the provider with the same address.
   - **What happens:** `POST /auth/oidc:callback` answers 500. The server logs
     `CompleteOidcSignIn … INTERNAL: internal (audit.entry_incomplete)` (request ids
     `540bfecb…`, `5490f936…`). Nothing is connected (`account_identity` 0).
   - **Likely cause, read and not tested:** `connectByMail` reads the account with
     `Accounts.Find`, whose mapper (`accountFrom`, `infrastructure/postgres/IdentityRepository.go`)
     never fills `TenantID`. `OidcWriter.record` writes `TenantID: account.TenantID`, so
     `audit.Entry.Validate` refuses the zero tenant. That is known-traps' "a row mapper that drops
     `tenant_id`". The LINK path does not hit this.
   - **Why it matters for D4:** the sentence beside the password switch sends the two people
     without a provider exactly this way. An owner who switches the password off before
     connecting a provider is then left with one way back: the LINK step with the password, at
     the provider.
2. **The card shows the bare word "Internal"** for that failure (`23b-…`). It is not a sentence,
   and no reference is shown, unlike the other refusals on the same card.
3. **The Microsoft form contradicts itself about the shared endpoint.**
   - The preset's instructions say "use that directory's issuer address, **not the shared one**".
   - The box beneath says shared addresses serve "everybody you name below", and the shared
     endpoint is accepted once a directory is listed.
   - The refusal for an empty list says "without a list it is **all of them**", while the field's
     own hint says "An empty list **lets nobody in**".

   The administrator reads three answers to one question.
4. **Two trail entries name the workspace's id as the provider's.** These are
   `identity.provider_sign_in_started` (`recordStart`) and `identity.provider_refused`
   (`recordRefusal`), in `core/application/service/identity/OidcSignIn.go`. Both write
   `TargetType: identity_provider` with `TargetID` set to the tenant id. The screen reads "about
   the identity_provider 01a13237-…-64a45d384cd3", which is the workspace, not *Acme Microsoft*
   (`01a1323b-…`). With two providers, only the issuer field tells them apart.
5. **The connect mail says "Somebody asked to reset the password for this address"** when the
   person asked for a sign-in link, on a workspace that has no password.
6. Smaller observations: see *What was seen*. They are the step-up dialog's first focus, the
   auditor's enabled controls and *Create hub*, "You have no tokens." for a service account,
   `admin:tenants` offered in single mode, and an expiry typed as 31 December listed as 1 January.

Items 1 and 2 are the ones a person cannot get past. 1, 3 and 4 are worth a `finding` issue each.
