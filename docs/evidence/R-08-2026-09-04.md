# R-08 — A day's work in the application

**2026-09-04, a local stack.** Risk R-08 was answered in `0.2.0` with "a reference CLI plus a
minimal reference client as a dogfooding tool", and `roadmap.md` phase 5 says F2 is where that
interim ends. Ending it is a task rather than a feeling: somebody does a day's real work in the
application and writes down what they had to leave.

This file is that pass. It is a route, so that it can be walked again next milestone and the two
runs compared — which is the only way to tell a surface that is filling in from one that is
churning.

| | Value |
|---|---|
| Server | `make run ROLES=api` against the development PostgreSQL, migrations at `0069` |
| Client | `apps/webapp` on Vite, proxying `/api` — the same bundle `presentation/webui` embeds |
| Browser | Chromium, 1400 × 900, `navigator.languages = ['de', 'de-DE']` |
| Work | This repository's own backlog: milestone F2 and its five remaining tasks |
| Performed with | The application alone, except where a step is marked **fell back** |

## The route

Ten steps, in the order the backlog names them. Each says what happened and what it needed.

### 1. Create the collection for the milestone — **fell back** (#359)

There is no control anywhere in the application that creates a hub or a collection. The sidebar
lists hubs, the hub screen lists collections, and neither offers to add one; the home screen still
says the first views arrive with hubs and collections (#365).

`containers.create` exists in the store, fully written, and no component calls it. Eight message
codes for the form are in `locales/en.json` and unused.

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"type":"COLLECTION","parent_id":"<hub>","name":"Milestone F2","description":"…"}' \
  "$API/containers"
```

### 2. Put the milestone's tasks in — **the application**

Five entries through the add form at the end of the list. The type chooser did not appear, which is
right: the manifest offers one root type here, and a select with one option is a decision nobody
has.

### 3. Break one into work packages and an activity — **the application**, with a catch (#363)

The row's own "Add an entry" adds *inside* that row. It works, and it is named exactly the same as
the control at the end of the list that adds to the collection — on a list of seven rows there are
eight controls called "Add an entry", and the pass put four tasks in the wrong place before the data
said so. `app.entries.add_child` — "Add something inside {title}" — is in the catalogue, unused.

### 4. Label them — **the application** for putting a label on, **fell back** for having one (#361)

`LabelPicker` puts a label on an entry and takes it off, and a collection starts with none. Creating
one is `labels.create` in the store, called by nothing.

```bash
curl -X POST … -d '{"name":"Shipped","color_token":"green"}' "$API/containers/<collection>/labels"
```

The same is true of a board's columns (#362), which the pass created the same way.

### 5. Order them — **the application**

`Move to the top` from the row menu, and the entry moved and said so: "F2-16 The interim ends is now
number 1 of 5." The keyboard path and the drag were exercised in F2-12's own pass and were not
repeated here.

### 6. Move one between collections — **refused, and the sentence was wrong** (#358)

`Move to another collection…` on an entry that sits *inside* another entry answers **"That
collection is not the one the chosen parent belongs to."** The reader chose no parent. The same
operation from the same menu, `Move out one level`, answers **200 and changes nothing**.

Reproduced with curl and no client involved: `POST /items/{id}:move` treats an explicit
`"target_parent_id": null` as if the field were absent, which is the one distinction
`PlacementController.go` builds a presence map to preserve. An entry with no parent moves correctly;
an entry with a parent cannot leave it.

**This is the pass's most valuable finding**, and it is a server defect that two of F2-12's menu
items sit on top of.

### 7. Complete a few — **the application**

The checkbox on the row. Both entries came back completed, and the history recorded it.

### 8. Find one by a word in its notes — **the application**, after **falling back** to write the note (#360)

`items.update` exists in the store and no screen calls it, so an entry's notes cannot be written in
the application at all — the text `POST /search` searches, and the text F2-15's history says
somebody edited.

With a note set by curl, the search found it: `marmalade` → "F2-13 The query language", announced as
"Entries found: 1."

**It found it only after the language picker was set to `en`.** The browser's locale is German, and
the query is read under the caller's language while the entry is indexed under its own — ADR-0034
working exactly as designed. It is worth writing down anyway: a workspace written in English and
read in a German browser answers "Nothing matches those words" until the reader changes a control
they have no reason to look at. That is a design consequence rather than a defect, and F3's search
work is where to decide whether it should be softened.

### 9. Archive what is finished — **the application**

`Archive` from the row menu. The row stayed where it was, said "Archived", and every write control on
it carried "This entry is archived, so nothing on it can be changed. Unarchive it to work on it
again." Which is I-W4 rather than a screen that hides things.

### 10. Look at what changed — **the application**, but not from the list (#364)

The history reads as the day went: "You archived this entry · You marked this entry as done · You
created this entry", each with its time in the reader's locale.

Reaching it from the list is not possible: `EntryList` passes no `href` to `TaskRow`, so a row is
not a link. The board's cards and the search results do link. The pass reached the history by
typing the address.

## What this says about R-08

The interim is over in the sense the risk meant: the day's work happened in the application, and
what it could not do is a list of named surfaces rather than a vague sense that the client is not
ready. Four writes exist in the stores and reach no screen — creating a hub or a collection, editing
an entry, making a label, making a column — so a workspace cannot be *started* in the application,
only worked in.

The one thing that is not a missing surface is #358, and it is the server's.

## What was left

| # | What | Why it could not be done in the application |
|---|---|---|
| #358 | Move an entry out of its parent, or to another collection | `:move` ignores an explicit null parent — a server defect |
| #359 | Create a hub or a collection | No surface; `containers.create` is unused |
| #360 | Edit an entry's title or notes | No surface; `items.update` is unused |
| #361 | Create or manage a label | No surface; `labels.create` and `remove` are unused |
| #362 | Create or manage a board column | No surface; four bucket writes are unused, and a dead control sits on each column |
| #363 | Tell the two "Add an entry" controls apart | One name, two meanings |
| #364 | Reach an entry from the list | `TaskRow` takes an `href` and the list passes none |
| #365 | Read a home screen that is true | It still says the application has not arrived |

The maturity stage is not decided here. #366 puts the question to the owner with this evidence and
without a recommendation; `lib/maturity.ts` is untouched.

## Walking it again

Next milestone, the same ten steps against that milestone's own backlog. What to compare is not the
number of issues but their **kind**: a surface that is filling in produces fewer "no way to do this"
rows each time, and one that is churning produces steps that worked last time and do not now.
