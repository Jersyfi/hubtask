# RT-8 — Rolling update under load

**2026-08-21, integration environment.** RT-8 asks whether a deployment across the N−1/N schema,
under load, refuses any request or loses any data
([observability-reliability.md §12](../architecture/observability-reliability.md)). This is the
first time it has been run against a cluster rather than intended.

It was run twice, and the first run is the more useful half: it failed, for a reason nothing else
in the pipeline could have found.

## How it was run

Load from [`test/resilience/rt8`](../../test/resilience/rt8/main.go): 8 clients, 40 requests a
second, writing items and reading them back through the public ingress
(`https://api.integration.hubtask.eu`), then asking for every identifier it had been given a `201`
for. The rate and the eight credentials are chosen to stay inside the tenant's rate budget, so that
the run measures the rollout rather than the rate limiter.

The rollout itself was `helm upgrade` with the arguments
[`deploy.yml`](../../.github/workflows/deploy.yml) uses, run by hand rather than by CI: the
workflow's values point at the environment's own database, and this run needed an empty one at
schema 9. That CI reaches the cluster with the same command is proven separately, by the run that
first installed this environment.

The database for the run was a second, empty database in the same PostgreSQL, so that nothing had
to be deleted to get a schema-9 starting point.

## What run 1 found

Two requests out of 14 334 were answered `502`, both inside the twenty seconds the rollout took
(seconds 90 and 95 of the run; the rollout ran from second 81 to 101). Everything before and after
was clean, and no data was lost.

The `502` did not come from Hubtask. The application's own counter has no `5xx` series at all in
either run — the series is only created when a `5xx` is served — and no pod restarted. A `502` is
what Traefik answers when it forwards to a backend that is no longer accepting connections. So the
application never saw those two requests.

**The cause.** On `SIGTERM` the process marked itself not ready and then waited a fixed two seconds
before closing its listener. Two seconds assumes that whatever routes traffic notices immediately,
and nothing does: removing a pod from the endpoint list and stopping the pod are two things
Kubernetes starts at the same moment and finishes independently. For the rest of that window the
ingress still held the endpoint, and the pod had already stopped answering.

This is worth stating plainly because of how nearly it went unnoticed. B-14's acceptance asks for
"the 5xx counter and pod restarts at zero", and both **were** zero in the failing run. The
application's counter cannot count a request the application never received, so the metric that was
supposed to answer the question was structurally incapable of seeing the fault. Only the client's
own view of what it asked for and what came back could.

**The fix.** The wait is a property of what sits in front of the process, not of the process, so it
became configuration — `HUBTASK_SHUTDOWN_DEREGISTER_SECONDS`, default 15
([deployment.md §6.1](../architecture/deployment.md)). Zero remains right for an installation with
nothing in front of it, which is why zero is allowed and only a negative value is refused.

## What run 2 proves, and what it does not

Run 2 repeated the load and the rollout with the fix in the **outgoing** version — which is the
side that matters, since the fault is in how a pod stops. Zero non-2xx across 9 530 requests, zero
transport failures, zero lost items.

It is not a full repeat: there is no migration after `0010` to roll across, so run 2 crossed no
schema boundary. The expand/contract half of RT-8 is answered by run 1, which did cross one and
lost nothing while doing it. Both halves are answered; neither run answers both.

Also not covered, and not claimed: a second node (there is one), a failover of the database (it is
a single pod), and any load beyond 40 requests a second — RT-6 is the test with a capacity target,
and it has not been run.

## Repeating it

The procedure is in [k8s/README.md](../../k8s/README.md). What made this run worth anything, and
what the next one should keep: the load has to write and then look for what it wrote, it has to
count transport failures as failures, and the numbers that decide have to come from the client.
The server's own metrics can only report the requests it received.
