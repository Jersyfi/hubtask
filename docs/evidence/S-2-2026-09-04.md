# S-2 — The master key rotation, drilled

**2026-09-04, a throwaway PostgreSQL 16 through Testcontainers.** S-2 asked where the master key
lives once somebody else operates the installation, and
[ADR-0045](../adr/ADR-0045-master-key-in-the-environment.md) answered it: the environment, with a
trigger rather than a review date. The decision alone would have left the more interesting half
untouched, because the ring has always been able to *accept* a key and never to *finish* with one.
This file records the run that separated what the rotation actually does today from what the
procedure claims.

The drill is [`test/integration/key_rotation_test.go`](../../test/integration/key_rotation_test.go),
so it is repeatable rather than an afternoon somebody remembers.

| | Value |
|---|---|
| Database | `postgres:16-alpine`, migrated by the suite's own fixtures |
| Store under test | `account_mfa` through `postgres.MfaRepository` — a real repository, not a fake |
| Crypto | `infrastructure/crypto.Envelope` over a real `Keyring`, `crypto/rand` for entropy |
| Rings exercised | `[k1]` → `[k2 k1]` → `[k2]` |
| Runtime | 2.7 s for both cases |

## What was proved

| Step | Result |
|---|---|
| A value sealed under `k1` and written through the repository | stored with `secret_key_id = k1` |
| The same row read back after the ring rolled forward to `[k2 k1]` | opens, and the plaintext matches |
| A value sealed after the rotation | names `k2`, with nothing rewritten |
| That value written and read back | stored with `secret_key_id = k2` |
| A `k1` row opened under a ring holding only `k2` | refused with an unavailability, not a corrupted read |

The third and fourth rows are the ones worth having. A rotation that only proved the cipher would
have proved nothing about *this* system: the key identifier is a column beside the ciphertext, and
the question is whether the stored pair survives the ring changing underneath it.

## What was not proved, and why it is in the file

**A completed rotation.** Nothing in the system rewraps a value sealed under an older key, so the
count of rows naming `k1` never reaches zero on its own and step 4 of the procedure has no safe
moment. That is not a gap this drill found by accident — ADR-0045 decides the shape of the re-seal
and [#368](https://github.com/Jersyfi/hubtask/issues/368) is the work — but a drill that stopped at
"the ring rolled forward" and called the rotation exercised would have been the kind of evidence
that makes a procedure look finished.

The last row above is what stands in for it: the system's answer to a key removed too early is a
refusal an operator can read. That is why [security.md §8.1](../architecture/security.md) ends by
counting rather than by waiting.
