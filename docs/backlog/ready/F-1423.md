## 3. Decisions

- [x] D1 The field is `held: boolean`, required in the response, true when the automatic removal
  keeps the deletion because a legal hold blocks a row of its batch — decided by: worker. Additive
  (no rename or removal), so not on the owner's list. Rejected: naming the hold (its reason is
  behind `READ_CONFIGURATION`, the trash is read by members); a nullable `purge_after` (a change of
  an existing field's type).
- [x] D2 Judged per batch with `lifecycle.Holds.Blocking` on each member, exactly as `Sweep` judges
  rows, via a new `Trash.BatchMembers(batchIDs)` read — decided by: worker. Only for the entries
  the reader may see (after the narrowing, in a second read-only transaction), so nothing about a
  hidden deletion is read on their behalf; one query per page, none when no hold is in force. The
  holds are read without the shared hold lock (the register's `List`), because this read may be
  served by a replica and decides nothing. Rejected: a SQL-side judgement (a second copy of
  `Blocking`); `LegalHolds.Active` (its lock).
- [x] D1a `held` says a hold keeps the deletion and nothing else: a deletion kept by the offline
  window is already in `purge_after`, and one kept because something below it stays for its own
  reason keeps counting down — decided by: worker; the last is the named gap beside the
  earlier-batch row.
- [x] D3 The web app says "Kept by a legal hold" instead of the countdown, and nothing about when —
  data-retention.md §4 gives a held entry no date — decided by: worker.
- [x] D4 The form: kinds LOCAL, S3, SFTP, WEBDAV (what this build speaks; the others are refused by
  name, check 2); an encryption choice defaulting to AES-256-GCM, and "none" only with an explicit
  acknowledgement that names the risk; SFTP's private key and its passphrase beside the password;
  S3's region — decided by: worker. The passphrase for archive encryption is not offered: the
  server refuses it today.
