## 3. Decisions

- [x] D1 The key is `(tenant_id, account_id, group_id, scope_type, scope_id, role)` with
  `NULLS NOT DISTINCT` — decided by: worker. Every column a grant is made of; `NULLS NOT DISTINCT`
  because exactly one of `account_id`/`group_id` is NULL in every row and `scope_id` is NULL at the
  tenant, so a plain unique index would refuse nothing. Rejected: `COALESCE` expressions (an
  expression index that `ON CONFLICT` and the reference-schema test must spell identically, for no
  gain on 16+); two partial indexes per subject kind (two objects for one rule).
- [x] D2 Of equal rows the migration keeps the oldest, by `created_at` then `id` (UUIDv7, time
  ordered) — decided by: worker. The rows differ in nothing but `id` and `created_at`; the oldest
  says truthfully since when the person has held the role, which is what an access review asks, and
  its `membership.granted` entry is the first one in the trail. Rejected: the newest (its date would
  understate how long access has existed).
- [x] D3 Removing a duplicate is not deleting user data — decided by: worker, not on the owner's
  list. The removed row is equal in every column but its identifier and creation time to the row
  kept, so no access, no fact about a person and nothing a person wrote is lost; the person's
  access is the same before and after. What stays behind: the `membership.granted` entry of a
  removed row names an identifier that no longer exists and has no `membership.revoked` partner; the
  trail is append-only and hash-chained, so the migration writes no entry and rewrites none, and the
  migration's header says how to read such an entry (the equal row kept is the grant in force). If
  PR #1415 lands first, a notification naming a removed row goes with it by its cascade; under
  #1415's own rule only the first of equal grants is news, which is the row kept.
- [x] D4 One migration, 0149, `NO TRANSACTION`: the dedupe in a `DO` block (its own transaction),
  then `DROP INDEX CONCURRENTLY IF EXISTS` and `CREATE UNIQUE INDEX CONCURRENTLY` — decided by:
  worker, following versioning-release.md §4 ("No blocking locks: `CREATE INDEX CONCURRENTLY`").
  A pod of the previous release can write an equal row between the dedupe and the moment the index
  enforces; the build then fails, the migration job fails and the previous release keeps serving. A
  re-run repeats the dedupe, drops the invalid index the failed build left (which `IF NOT EXISTS`
  would otherwise accept as done, 0004's caveat) and builds again: the migration heals on retry.
  Rejected: a plain `CREATE UNIQUE INDEX` with the dedupe in one transaction (atomic, but a blocking
  lock — a deviation from §4, which is the owner's); two migrations 0149/0150 (the second could not
  repeat the first's dedupe on retry, so a failed build would need an operator).
  **The one lock the dedupe takes:** under a migrator without superuser or BYPASSRLS, the policy it
  gives itself (`CREATE POLICY`, as 0019 and 0143) takes ACCESS EXCLUSIVE on `membership` until the
  `DO` block commits, and every authorisation reads `membership`. So the block sets
  `lock_timeout` (5 s) for itself: on a busy table it fails fast rather than queueing every request
  behind it, and the job is re-run (the retry above). Once granted the lock is held for one
  `DELETE` over a table bounded by people × scopes — milliseconds. Under a superuser or BYPASSRLS
  migrator no policy and no exclusive lock are taken, only the `DELETE`'s row locks. Rejected: a
  per-tenant dedupe under the existing tenant policy (the migrator cannot list the tenants either:
  `tenant` is FORCE-d to its own row). The block reports how many rows it removed (`RAISE NOTICE`,
  a count only — rule 10), so an operator can match them to the trail's entries left without a row.
- [x] D5 A repeated grant answers the membership already there and writes no second
  `membership.granted` entry — decided by: worker. Nothing was given, and an access review that
  reads two grants and one revocation would read access that is not there. The port's `Grant`
  returns the membership in force and whether it was written; the other writers (a newcomer's role,
  a new workspace's owner, a private hub's owner, a managed account) write their entry only when the
  row is new, which for them is always. Rejected: a second entry naming the existing row (a grant
  the trail cannot tell from a real one); refusing the repeat with a conflict (a retried or doubled
  request is not an error, and the issue asks for idempotence).
- [x] D6 The restore skips a membership equal to one the tenant holds under another `id` — decided
  by: worker. An archive taken before this release can carry equal rows, and MERGE can meet a row
  granted again after the archive was taken; failing the restore on the index would make such an
  archive unrestorable. The statement's source row is guarded by `NOT EXISTS` an equal row with a
  *different* `id` (`m.id <> r.id`; an overwrite of the same `id` is unaffected), so the row is
  neither inserted nor — under OVERWRITE, where `ON CONFLICT (id) DO UPDATE` would turn a row into
  another's equal and the index is no arbiter — updated, and the report counts it as skipped
  (backup-restore.md §8's existing outcome). Under REPLACE_TENANT the first equal row imported
  wins; the export orders memberships by `id` (`BackupExport.sql`, UUIDv7, time ordered), so that
  is the oldest, as D2. An archive of this release holds no equal rows. Rejected: letting
  `backup.row_conflicts` fail the restore; teaching the dry run the same question (a second
  statement for a case only old archives meet — the mismatch is named in the matrix).
- [x] D7 Documents: domain-model.md §3.2 gains the rule (a subject holds a role at a scope once; a
  repeated grant answers the membership there); `POST /memberships`'s description says so; the
  query comment is made true; `db/schema.sql` carries the index. No ADR: the rule follows from the
  model, no alternative architecture was chosen. No known trap added: the index holds it now.
