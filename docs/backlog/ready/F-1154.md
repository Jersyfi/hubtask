## 3. Decisions

- [x] D1 Seed at provisioning and at every session opened — decided by: worker, within
  multi-tenancy.md §2.1 (a write in the tenant seeds it). A session is a retained kind itself
  (`SESSION`), so the write that creates the first thing the sweep must age out is what asks for it.
  Rejected: seeding from every write of a retained kind (the change log and the outbox are written
  by nearly every request — one more statement on the hot path of every write, for a job that
  exists after the first); a migration that enqueues a sweep for every existing tenant (the migrator
  would have to read across the `FORCE`-d tenant table, and "nothing enumerates tenants" is the
  rule); seeding in the sweep's siblings (outbox dispatch) — a job seeding another job hides the
  reason. What stays unseeded: a workspace nobody ever signed into and nothing was trashed in,
  which has no session to age out either; its first trash or sign-in seeds it.
- [x] D2 The first run is one sweep interval after the seed, not at once — decided by: worker.
  `EnqueueJob` pulls a pending job forward to the earliest request; a seed at "now" would run the
  sweep at every sign-in. One interval later keeps the cadence the sweep already has and moves
  nothing that is pending. The interval reaches the identity and admin services as a value from
  the composition root (`cfg.Retention.Interval`), not a constant copied into them.
- [x] D3 One helper for the three seeding places (trash, provisioning, sessions) in
  `core/application/service/lifecycle`, replacing `work.scheduleRetention` — decided by: worker; the
  dedupe key and the kind are written once.
- [x] D4 data-retention.md §5 and the comments on `queue.KindRetentionSweep` and
  `LifecycleWriter.Queue` say what seeds it now — decided by: the correction rule (a document
  stating the system wrongly is corrected in the same pull request).
