# UX-08 — An activity directly under a task

**Task:** UX-08 · issue #1640 · `docs/backlog/milestone-UX.md`
**Checked against:** `origin/main` at `d5cf27338` on 2026-10-21
**Verdict:** ready

The rule is decided (#1627: a task may hold work packages and activities, also mixed;
`domain-model.md` §2, the `CHILDREN` row; ADR-0087 §3). The hierarchy, the roll-up, the progress
counts and the template checks already answer from the profile rows rather than from type names, so
the core of the task is **one data migration** on the system default plus the tests that pinned the
old ladder. Three other things need work. The client's wording assumed one child type. One control
on the touched screen offers what the server refuses (P-05). And the AI breakdown already proposes
activities directly under a task, which this task makes acceptable: now that they are accepted,
their notes reach a type that carries none (D8). "Dissolve this work package" is not part of the
task (D4, milestone-UX.md § UX-08).

## 3. Decisions

- [x] D1 An activity may sit directly under a task, also mixed with work packages — decided by:
  owner, 2026-10-20, #1627 → `domain-model.md` §2 (`CHILDREN` row), UC-WRK-03 check 1.
- [x] D2 The change is a migration on the system default, not code — decided by: `domain-model.md`
  §2 ("a new type … is a profile entry"), ADR-0006 and ADR-0087 §3; the migration's comment cites
  the rule's place, not the issue.
- [x] D3 Wording where a task holds two kinds — decided by: worker. The subtree heading names the
  child type only when exactly one is permitted. Otherwise it says *Under this entry*
  (`app.item.children`, existing). The subtree's end draws one add control per permitted type
  (*Add a work package*, *Add an activity*, `app.entries.add_typed`). Each opens the form with that
  kind chosen and no chooser, which is what `ux-inventory.md` E6 asks ("＋ activity and ＋ work
  package"). The row ＋ keeps one control. Its form keeps the kind chooser, with options labelled by
  `app.item.type_name` instead of the raw type. Rejected: a single "Add an entry" with a chooser at
  the subtree's end, which adds one more decision to the common case the inventory names. Also
  rejected: a menu on the row ＋, because UX-16 reworks the row's controls into the entry menu and
  would rebuild it there.
- [x] D4 **"Dissolve this work package" is not part of this task** — decided by: the coordinator,
  milestone-UX.md § UX-08 ("no check asks for it, and *Move out one level* on each activity reaches
  the same result"). After this task that path works and is predicted correctly (D5).
- [x] D5 *Move out one level* gets the server's verdict — decided by: worker, P-05 (broken when a
  button leads to a server refusal the screen could have known in advance). The destination is the
  grandparent, or the collection when the parent is top-level; `placementVerdict` (new,
  `capability.ts`) answers `items.parent_item_required` for a type that is not a root, and otherwise
  `childVerdict(grandparent type, row type, grandparent depth − 1)`. **The depth passed** is the
  grandparent's stored `depth` from the entry itself (1 at the top of a collection, as the server
  stores it), less one, because `childVerdict` takes the depth *below* the parent. It is not the
  list's row depth: in a subtree that starts at 0 for the root's children, whatever the root's own
  depth. Where the grandparent is the subtree's root, the root's own fields are used (`root` now
  carries `depth`). Where the grandparent is the root's parent, `items.find` is used. A grandparent
  not loaded on the device is `undetermined`, and the move is offered as before for the server to
  answer. Rejected: leaving it to UX-16, which moves the control and does not compute its reason.
- [x] D6 The jumble conversion's grown subtasks stay work packages under a task — decided by:
  worker. `under` serves `grow` alone (UC-JUM-05). A title an arrival implies is a piece of work
  rather than a single step, and choosing per title would be the conversion deciding what nobody
  proposed. Only its comment is corrected. The decomposition (UC-AI-04) is not `under`'s: it already
  names each node's type (D8).
- [x] D8 **A breakdown keeps a piece's notes only where its type carries notes** — decided by:
  worker, with the coordinator's instruction that the newly reachable refusal is fixed in this task.
  Of the two ways offered, the narrowing **at production** is chosen. The material for the
  `decompose` prompt now carries the hierarchy (profiles in force, roots from the system rows, as
  the template material already does). `keptTree` drops `notes` from a node whose type's profile
  lacks `NOTES`. So the stored proposal, the one a person reads and accepts, is exactly what
  accepting creates. This is `payloadFrom`'s stated principle ("a person reading a proposal should be
  reading what they could actually accept"). Dropping a field is not counted in `dropped_nodes`,
  whose contract is nodes of a template only. Rejected: omitting the notes when planting, which
  would show notes in the proposal and silently not write them. Also rejected: reporting the
  dropped field the way I-W6 reports references, which would need a contract field for a value the
  person never asked for. Without wired profiles (a build that never asks), the notes stay and the
  acceptance answers as today.
- [x] D7 `ux-inventory.md` rows — decided by: worker, confirmed by the coordinator. E6 "Children" is
  ticked by this task (its whole row is the subtree, whose add controls this task builds). E5 "Row
  trailing" bundles controls of UX-16 and others, so this task leaves it unticked. Its "＋ offers
  work package and activity" part is met here and named in the pull request.

Nothing stays open for the owner.
