## 3. Decisions

- [x] D1 Holds before erasures, before traffic; a hold released in the rewound period stays in
  force — decided by: owner, 2026-10-10, #1247 → backup-restore.md §8.5 step 5, data-protection.md §5.
- [x] D2 The holds are re-placed by the operator, as an installation-level use case under
  `admin:tenants` (a `hubctl admin` command over it), run against the recovered installation with
  traffic still shut out — the application runs, the ingress does not. Rejected: a database-level
  script (it would write past the application's audit and its tenant transaction, rule 3) —
  decided by: worker.
- [x] D3 A re-placed hold keeps its original id, scope, reason, placer and moment, so the record an
  auditor reads is the same hold rather than a copy; each one writes `lifecycle.hold_replaced` with
  the run's recovery point. Idempotent on the id — decided by: worker.
- [x] D4 A hold whose target the recovery removed is placed anyway and reported (§ 2) — decided by:
  worker; rejected: refusing it (`lifecycle.hold_target_not_found`), which would drop a hold the
  owner placed on something a later restore may bring back.
- [x] O1 **The source** — the end of the WAL archive: the operator recovers a second, temporary
  cluster to the end of the archive (as `cmd/restore-drill` does for RT-9), and every `legal_hold`
  row of the workspace there that the recovered database lacks is placed again with its original
  values, recorded as `lifecycle.hold_replaced`; one released in the rewound period goes back in
  force. Fallback where the end of the archive is unusable: the newest workspace archive that
  includes the audit trail, read for `lifecycle.hold_placed`, with the gap reported per workspace —
  decided by: owner, 2026-10-11, #1262 → backup-restore.md §8.5, data-protection.md §5.
- [x] D5 The temporary cluster is read by `hubctl` on the operator's side (`--from-cluster`), not
  by the server: a connection string to another database in a request body would be a credential
  over the API and a server that connects wherever it is told. The read runs through the transaction
  wrapper under the workspace's scope (rule 3), in a read-only transaction on a session that
  defaults to read-only, under a statement timeout and a deadline (rule 7); the query names the
  workspace itself as well as row level security, because the operator may connect to the temporary
  cluster as a role that bypasses it — decided by: worker; rejected: the server reading the cluster.
- [x] D6 The archive fallback is read by the server (`archive` in the operation's input, the
  target and the archive's path): an archive's members are encrypted under a key derived from the
  installation's master key, which `hubctl` never holds. The archive must be the workspace's own
  (its name, as for a restore's listing, BK-10). It reads the `lifecycle.hold_placed` entries of
  the trail across the chain back to its full archive, the `lifecycle.hold_released` entries to
  mark what was released, and the `legal_holds` file the newest archive carries whole: a row there
  is the same hold the entry describes, and it is there in an archive whose schedule leaves the
  trail out. The answer names the archive's moment, the start of the gap, and whether the trail was
  in it — decided by: worker; rejected: decrypting the archive in `hubctl` (it would need the master
  key outside the installation).

workspaces' states (the after-state's holds as the source), runs the use case through the registry
as the operator against the before-state, and reads the holds back as the app role: every hold of
