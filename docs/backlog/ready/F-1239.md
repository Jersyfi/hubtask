## 3. Decisions

- [x] D1 Holds before erasures, before traffic; a hold released in the rewound period stays in
  force — decided by: owner, 2026-10-10, #1247 → backup-restore.md §8.5 step 5, data-protection.md §5.
- [x] D2 The holds are re-placed by the operator, as an installation-level use case under
  `admin:tenants` (a `hubctl admin` command over it), run against the recovered installation with
  traffic still shut out — the application runs, the ingress does not. Rejected: a database-level
  script (it would write past the application's audit and its tenant transaction, rule 3) —
  decided by: worker.
- [x] D3 A re-placed hold keeps its original id, scope, reason, placer and moment, so the record an
  auditor reads is the same hold rather than a copy; each one writes `lifecycle.hold_replaced` with
  the run's recovery point. Idempotent on the id — decided by: worker.
- [x] D4 A hold whose target the recovery removed is placed anyway and reported (§ 2) — decided by:
  worker; rejected: refusing it (`lifecycle.hold_target_not_found`), which would drop a hold the
  owner placed on something a later restore may bring back.
- [ ] O1 **The source.** #1247 names "the audit export at the backup target"; § 1 shows it exists
  only for workspaces whose own schedule includes the audit trail, and only up to their last run.
  Proposal: **read the holds from the WAL archive itself** — the operator recovers a second,
  temporary cluster to the end of the archive (the moment of the loss), as `cmd/restore-drill`
  already does for RT-9, and the tool takes every `legal_hold` row from it that the recovered
  database lacks, released or not (released ones go back in force, D1). The audit trail of that
  same temporary cluster supplies nothing more. Fallback where the archive's end is unusable (the
  damage itself is in it, e.g. a destroyed table): the newest workspace archive with
  `include_audit`, read for `lifecycle.hold_placed` entries — the decided source, with its gap
  reported per workspace. Alternatives: (b) build only the decided source and state the gap in
  §8.5 and UC-BAK-08 — a workspace without an audited schedule then loses its holds silently;
  (c) make every hold placement write a copy to an object store outside the database at once —
  a new write path and a new dependency on the store at placement time. **Question for the owner:
  may the source be the WAL archive's end (with the archive as the fallback), instead of the audit
  export alone?** What waits: the source reader and the procedure text; D2–D4 and the use case do
  not depend on it.
