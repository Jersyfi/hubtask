## 3. Decisions

- [x] D1 The narrow scope is a second descriptor field, `AlsoScope`, read by `catalogue.Scopes()`;
  each admitted use case's own check changes to `ActorContext.RequireAnyScope(admin:tenants,
  admin:provisioning)`; the shared `InstanceWriter.authorize` keeps `admin:tenants` unless a caller
  names both — decided by: worker; a list beside the catalogue is what `Scopes()` exists to avoid,
  and the descriptor alone would admit nothing (rule 2: the check is the use case's).
- [x] D2 Admitted: `ProvisionTenant`, `ListTenants`, `ReadTenant`, `QueryTenants`, `MoveTenantPlan`,
  `SuspendTenant`, `ResumeTenant`, `RequestTenantDeletion`, `UpdateTenantQuotas` — decided by:
  UC-INS-06 check 6. `UpdateTenant` (the platform's reference) — decided by: worker, reading check 6's
  "provision" with multi-tenancy.md §4.3 ("the platform's own reference … changeable") and
  `Reference.go:49`: a platform re-provisioning a customer clears the reference first. Cancelling a
  deletion, the export and reading plans stay `admin:tenants`'s — check 6's "refused everything
  else"; UC-INS-08 check 7's "the same … cancellation" is read as multi-tenancy.md §5's "the operator
  calls a pending deletion off", which stays possible for the platform's request.
- [x] D3 The step-up is waived only for an actor of kind service account whose register row is a
  service account's (`operator_roster`, `kind = SERVICE_ACCOUNT`), never for the empty register's
  owner; a missing register keeps the step-up and an unreadable one refuses — decided by: worker;
  UC-INS-08 check 7 says "a registered operator", and the actor's kind alone is the permissive
  reading of `actorKind`.
- [x] D4 A refusal for want of either scope names `admin:provisioning`, the narrowest that would do —
  decided by: worker, api-guidelines.md §7.
- [x] D5 A raised session gains `admin:tenants` alone — decided by: worker; the hour is a person
  changing a switch, and the subset adds nothing.
- [x] D7 `hubctl` needs no new command — decided by: worker; a test pins the mint and the
  proof-less deletion.
- [x] D8 OAuth consent offers only what a session may carry (`catalogue.SessionScopes`), and a grant
  session's scopes are cut to the same set at authentication — decided by: worker; a finding fixed on
  this branch, test first, in its own commit and named in the pull request: a scope whose minting
  needs a proof and the register must not be reachable through a consent screen without either.
- [ ] O1 The token screen (Decision 16): the preview shows two options, but the same form mints
  tokens with no installation access, for oneself and for an ordinary service account. Proposal A: a
  third option "Nichts" ("Kein Zugriff auf die Steuerung der Installation."), preselected on one's
  own panel, "Nur Bereitstellung" preselected on a service account's (the preview); B: "Nichts"
  preselected everywhere, since the panel cannot know whether the service account is in the register
  — waiting on the owner: asked through the milestone's session on 2026-10-17; step 6 waits.
