## 3. Decisions

- [x] D1 **The restriction is a second `KeptOutSource`, without gates.** `RestrictionSource` answers
  every restricted person (D2) with reason `KeptOutRestricted` (`"RESTRICTED"`) and their names; it
  comes first in the source list, so a person both restricted and objecting reads as restricted.
  Unlike an objection it holds under `NOT_OFFERED`, alone in a workspace and whatever the position
  (Art. 18 is the controller's duty, not a choice the workspace can take away). Decided by PH-03 D5
  and the coordinator's brief; worker: the order.
- [x] D2 **Who is restricted.** One read, `RestrictedPeople`: accounts whose status is `RESTRICTED`,
  and accounts `ANONYMIZED` that are the subject of an erasure case with a pending `erasure_kept`
  row (`erased_at IS NULL`) — the person a narrow hold kept data of (§ 1). Each with display name,
  sign-in name and address (empty for the anonymised). Not every `ANONYMIZED` account
  (`ProcessingAllowed`'s reading): a former user's anonymised content is the workspace's
  (UC-PRV-03 *Goal*) and would leave every summary and every rule the day somebody leaves. Per
  person, not per row: while a hold keeps part of a former user's contributions, all of them stay
  out until the release — erring towards the restriction. A former user's content returns to AI
  and automation when the last pending `erasure_kept` row of their case is erased — the remainder
  of the last hold's release sets `erased_at`, and the next read no longer finds them. Accepted by
  the coordinator, 2026-10-12. Worker; rejected: per-row marking (a
  column on every kept table, a migration, and a second truth beside `erasure_kept`).
- [x] D3 **For a restriction, "their entries" includes what is assigned to them** (UC-PRV-04 check
  5). `KeptOut` gains `Excludes(createdBy, assignee shared.ID) bool`: the creator for every reason,
  the assignee for `RESTRICTED` only — an objection keeps out what a person *authored* (PH-03 D4),
  a restriction what is *about* them. Applied wherever PH-03 applies the creator: the item, thread
  and collection sources, `AiTranslate`, `Owed` and `Forget` (which take the assignees beside the
  creators). Worker.
- [x] D4 **The asker's refusal names their own reason.** `KeptOut.Refusal(accountID)` answers
  `ai.kept_out` for an objection and `ai.processing_restricted` (403) for a restriction — the person
  learns only their own state; PH-03's three call sites (`Ask.workable`, `SuggestFromJumbleEntry`,
  `AiTranslate`) and the producer use it. The automation's "not a failure" set gains the code.
  Worker; rejected: reusing `ai.kept_out`, whose words point to a switch that a restriction does
  not have.
- [x] D5 **"Out of automation" is a run about R, not only a run as R.** The engine reads the
  restricted set (D2) once per run, in the runner's transaction, before the conditions: a run whose
  `run_as` is restricted ends `SKIPPED` with `automation.run_as_restricted`; one whose triggering
  event's actor, or whose subject entry's creator or assignee, or whose subject intake's sender is
  restricted ends `SKIPPED` with `automation.subject_restricted`. Checked at start and at resume of
  a waiting run. A skip clears the failure streak like any non-failure, so a rule is never switched
  off over somebody's right, and runs again once the restriction is lifted. Decided by UC-PRV-04's
  *Goal* and *Story* ("rules do not act on their entries") and data-protection.md §4 ("excluded
  from automation"), which check 4's wording narrows; worker. Rejected: recording no run (as a
  private hub does) — the owner would see a rule that silently stopped (P-11); refusing to save a
  rule as a restricted person — writing a rule is the person's own act. Accepted by the
  coordinator, 2026-10-12: the skip and its code are visible in *What the rules did*.
- [x] D6 **Assigning under a rule.** A use case that puts a person on an entry asks the restricted
  set when `actor.RunsForRule` is set: `AssignWorkItem` and `AddMember` refuse
  `items.assignee_restricted` (422), which the engine records as `SKIPPED`, not failed;
  `CreateWorkItem`, `DuplicateWorkItem` and `InstantiateTemplate` make the entry unassigned, as
  automatic assignment does (UC-PRV-04 check 3). By hand nothing changes. Worker; rejected: the
  engine reading action parameters (it cannot see the assignee a template or a copy derives).
- [x] D7 **Vectors.** Restricting forgets R's vectors (created or assigned) in its own transaction;
  the erasure that keeps anything does the same in its main transaction; lifting and the remainder
  need nothing — the next `ai.embed` pass owes those entries again. Worker, after PH-03 D8.
- [x] D8 **Codes**: `ai.processing_restricted`, `automation.run_as_restricted`,
  `automation.subject_restricted`, `items.assignee_restricted`. `en` always; `de` for `ai.*` and
  `automation.*` (both families have German entries once PH-03 is merged); `items.*` stays English
  (no German entry exists).
- [x] D9 **No export is filtered** — decided by the owner, 2026-10-09, #1234 (Decision 7): proven
  by a test, nothing built.
- [x] D10 **No interface change.** The web app reads the manifest (already false for a kept person)
  and shows a run's code in the rule log; the profile's AI switch is left as PH-03 built it — the
  restriction is the controller's to tell the person (Art. 18(3)), not a setting. Worker. Issue
  #1227 was edited to the milestone's text by the coordinator, 2026-10-12.
- [x] D11 **#1160 stays outside** (§ 2(a)): not carried, not closed.
- [x] D12 **The rolling window** (§ 2(b) last row): accepted by the coordinator, 2026-10-12, named
  in the pull request.
