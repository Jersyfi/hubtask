## 3. Decisions

- [x] D1 Only an `ACTIVE` or `RESTRICTED` account is restricted or lifted; an invited, disabled or
  anonymised one is refused; an erasure under a hold keeps an invited or disabled account in its
  status, restricted through the kept record; an invitation the defect moved returns to `INVITED`
  when lifted — decided by: owner, 2026-10-20, decision #1607 option (a) → written in
  `data-protection.md` §4 and §4.1, `data-retention.md` §4 item 2, UC-PRV-04 *Where it ends*
  (Jersyfi/hubtask#1618, on `main` as `fb9df4331`). The first version of this record put it to the owner because it
  touches UC-PRV-04 check 1 and a retention safeguard (§ 5). `ACTIVE` → restrict and `RESTRICTED` →
  lift both stay; a retried restriction and lifting an unrestricted account are harmless, and
  refusing them (the issue's strict wording) would make a retry answer 409 — rejected.
- [x] D2 Where the rule lives — decided by: worker. A predicate `identity.AccountStatus.
  RestrictionApplies` beside `MayAct` and `ProcessingAllowed`, an allowlist, asked by the use case
  and by the erasure after reading the status under a row lock. The read is its own port,
  `privacy.AccountStatuses`, so the export's fakes of `Subjects` are untouched. Rejected: a guarded
  `UPDATE … AND status IN (…)` — it would put the rule in SQL and could not tell "no such account"
  from "wrong status" without a second read anyway.
- [x] D3 The refusal — decided by: owner (the code, 409, naming the status, #1607) and worker (the
  sentence: a `select` on the status, and what to do instead — a legal hold on the account).
- [x] D4 The hold is asked after the row lock — decided by: worker, the reviewer's race (§ 2(d)).
- [x] D5 An open invitation is told by its token — decided by: worker, within the owner's wording
  (#1607: an invitation "still carrying its unredeemed invitation"). Redeeming and accepting clear
  `redemption_token_hash` (`RedeemInvitation`, `AcceptInvitation`); the token is minted when the
  invitation mail is delivered (`MintRedemptionToken`, in the queue job), and only while `INVITED`
  (`SetRedemptionToken`). So an account still holding a token, whatever its status, was never
  accepted, and lifting gives back `INVITED` — also for an `ACTIVE` one the defect lifted straight
  from `INVITED`. The gap, stated in `data-protection.md` §4: an invitation restricted before its
  mail went out holds no token, and lifting makes it `ACTIVE`. Rejected: "never accepted" from
  missing password and identity — an account brought in from an export has no password either
  (`known-traps.md`), and turning a working person into an invitation would lock them out; a stored
  prior status (a migration for rows the token already identifies).
- [x] D6 The operation answers and audits the status it wrote, not one derived from `restricted` —
  decided by: worker; `Execute` returns it, and the contract's enum gains `INVITED`.
- [x] D7 What an erasure keeps is restricted by the kept record whatever the status — decided by:
  worker, from `data-retention.md` §4 item 2 ("restricted through the kept record whatever its
  status"). Both reads drop the status filter on the kept branch: only an account that became
  `ACTIVE` while kept (an accepted invitation) differs, and it is the one that must stay restricted.
- [x] D8 An erasure ends an invitation nobody accepted, with the credentials — decided by: worker,
  from `data-protection.md` §4.1 ("credentials … go whatever is kept"; a held invitation "neither
  signs in"). `RevokeCredentials` clears the token and sets the expiry to the erasure's moment, which
  `RedeemInvitation` and `AcceptInvitation` both refuse. Since the account stays `INVITED`, the
  queries that mint a token (`SetRedemptionToken`: a renewal, a queued invitation mail) and that
  activate one (`RedeemInvitation`, `AcceptInvitation`) also refuse an account an unerased kept
  record names, so it cannot be reopened. Not guarded: `ActivateFirstOwner`, which matches only the
  owner the first start inserted in the same transaction. A queued invitation mail for such an
  account is still sent, without a link, as for one accepted meanwhile.
- [x] D9 A restore leaves a kept account as it is — decided by: worker, from `data-retention.md` §4
  item 1. Before this task a held invited or disabled account was `RESTRICTED` and so protected;
  keeping its status must not lose that.
