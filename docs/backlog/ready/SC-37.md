## 3. Decisions

- [x] D1 Two use cases on the person's own account — `StartProviderConnect` (session, step-up, flow
  marked `connect`) and `CompleteProviderConnect` (the same session's flow, the exchange, the checks,
  `Connect`) — and the read `ListOwnIdentities` — decided by: worker; the provider step-up's shape,
  ADR-0078 §1 ("from the account's settings").
- [x] D2 The step-up is asked at the start, before the person leaves for the provider — decided by:
  worker; UC-ID-10 check 8 ("after a step-up and a fresh sign-in"), and a refusal after the trip
  would waste it. A provider-only account may need two trips (its own provider, then the new one).
- [x] D3 The new provider's sign-in must be fresh since the flow left (`ProviderProofFreshSince`), as
  SC-33's — decided by: identity.md §11, §16.1.
- [x] D4 Admission is `MayAdmitWithProof` (a verified address at a known mode), not the lists — decided
  by: identity.md §10.4 ("a member bringing their own proof … is not new"), which the `LINK` step and
  the link by mail already follow, and a connected identity's daily sign-in applies no admission at
  all (§ 1). The address need not equal the account's: that is the point of the task. Whether the
  lists should also bound connections is decision #1511 (identity.md §21 I-14); it does not block
  this task, and under its option (b) the three doors switch to `MayAdmit` in one change.
- [x] D5 An account without an address is refused — decided by: identity.md §4.1; such an account is
  defined as one no provider reaches, and the password door the workspace keeps open for it rests on
  that. Adding an address first (UC-ID-20 check 7) is its way.
- [x] D6 A provider already connected to the account is refused, not re-pointed — decided by:
  identity.md §11 ("never re-pointed"); there is no disconnect (#1507).
- [x] D7 The proof recorded is `SESSION`, a new `LinkProof` value written to the trail only (no
  pending credential carries it, so `auth_pending`'s CHECK is untouched) — decided by: worker.
- [x] D8 The ways in are read by `GET /accounts/me/identities` (provider id, name, `linked_at`), never
  the subject or the provider's address — decided by: worker, rule 10's spirit and P-01.
- [x] D9 The identity.md §21 open point the coordinator asked for ("whether a second factor or
  recovery codes changing is told", from SC-36's D9) lands in this pull request as I-13 — decided by:
  the coordinator, 2026-10-15.
- [x] D10 Nothing this task builds waits on the owner; identity.md §11 and §21 I-2 change with the build.
- [x] D11 identity.md §21 gains I-14, pointing at #1511 — decided by: the coordinator, 2026-10-15.

## 5. Review

Attacked on 2026-10-15 by the coordinator (a separate agent, no part in writing it), given this
record, the task and the repository. D1–D3 and D5–D8 approved; D2's two trips accepted. Findings
and what changed:

1. *D4: a connected identity signs in daily, so a connection that skips the provider's admission
   would bypass a workspace's restriction (a personal directory under DOMAINS, `/consumers`, a domain
   outside the list).* Checking the code showed that sign-in itself applies no admission to an
   identity already connected, and that the two existing connecting doors admit by
   `MayAdmitWithProof` (§ 1, two new rows). identity.md §10.4 decides that the lists bound
   newcomers only; SC-37 implements that documented rule (D4), and the question whether the lists
   should bound connections is decision #1511 with three readings, recorded as identity.md §21 I-14.
   The matrix gained a row per admission outcome, the last pinning today's rule.
