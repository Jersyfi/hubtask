## 3. Decisions

- [x] D1 The job trusts the case: `Exporter.workspaces` no longer asks the actor for
  `admin:tenants`. An installation-wide case reaches `IN_PROGRESS` only through the start, which
  checks the scope of the person who starts it, and recording it checked it too — decided by: the
  task text ("the job … does not ask its system actor for it again"). Rejected: a scope on the
  system actor (it would give every job the operator's scope).
- [x] D2 "One archive" is one location per case at the target: `hubtask-dsr-<case id>-<time>/`,
  holding one complete Hubtask archive per workspace under `<tenant id>/`, and the case's `archive`
  names that location. Each part stays the archive format the export already is (backup-restore.md
  §9: an export is a Hubtask archive), whose scope is one tenant — decided by: worker. Rejected: an
  archive scope spanning tenants (a format change for one use, and a "restorable" archive of several
  workspaces at once has no meaning); several unrelated archives (check 3 says one, and today they
  collide within a second).
- [x] D3 An installation-wide case names its location by the case's id, never the address, so the
  audit entries' `archive` field carries no personal data (rule 10). The tenant-scope name is
  unchanged — decided by: worker.
- [x] D4 In every workspace the person is looked up by address in that workspace's own transaction
  (`Accounts.FindByEmail`), and the archive part is filtered by that account id and the address;
  where no account is found (gone between the two reads), by the address alone, as today — decided
  by: the task text; worker for the fallback.
- [x] D5 The audit entry's actor stays the job's ("the installation"), and names the case; who
  started the case is on the case's own `dsr.started` entry in the operator's workspace — decided by:
  worker; audit.md §2's reading of a job's entries.
