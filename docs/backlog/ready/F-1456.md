# F-1456 — The doors through the boundary answer on a database the operator brings

**Task:** F-1456 · issue #1456 (finding) · milestone "CL — A clean slate" (no Delivers line)
**Checked against:** `origin/main` at `69952f71c` on 2026-10-15
**Verdict:** waiting on the owner

A finding fix, not a milestone task. The commits carry `Task: F-1456`. The issue asked for
verification first. **It is confirmed, and the problem is wider than the census.** On a database
whose owner is not a superuser and holds no `BYPASSRLS` — the arrangement ADR-0052 supports for
managed PostgreSQL — every `SECURITY DEFINER` function that reads across tenants answers nothing.
That includes `resolve_tenant`, which sign-in starts with.

## 1. Premise — what is true today

| Claim | True? | Evidence |
|---|---|---|
| The definer functions are owned by the migrator | true | on a managed-style database (`managedDatabase` in `test/integration/managed_postgres_test.go`), `pg_proc.proowner` is `hubtask_migrator` for all 24 `SECURITY DEFINER` functions in `public` |
| `FORCE ROW LEVEL SECURITY` binds the owner, and only a superuser or a `BYPASSRLS` role escapes it | true | PostgreSQL semantics; ADR-0052 "Context"; `0019`, `0143`, `0149` work around it for one statement each |
| Where the owner is not a superuser, a definer function reading a FORCE-d table outside a tenant context sees no rows | **confirmed** | probe (2026-10-15, not committed). The database was migrated as `hubtask_migrator` (`rolsuper=false`, `rolbypassrls=false`), and one tenant `probe` and one active account were inserted as the owner with the tenant set. Control: the owner with the tenant set reads 1 tenant row. As `hubtask_app` with no tenant set: `resolve_tenant('probe')` = **NULL**, `instance_census()` = **(0,0,0,0,0,0)**, `admin_tenants()` = **0 rows** |
| Compose, CI and the integration suite never see it | true | they migrate as the PostgreSQL superuser (`managed_postgres_test.go` header). The CloudNativePG chart grants the owner `BYPASSRLS` in `postInitSQL` (ADR-0052). Only a database the operator brings is affected |
| The managed-database tests prove the migrations and the application role's boundary, not the doors | true | `TestTheMigrationsApplyWithoutASuperuser` and `TestTheBoundaryHoldsOnADatabaseWithoutASuperuser` never call a definer function |
| A definer function called inside a tenant's transaction is not affected | true for its own tenant's rows | the owner's policies match `current_tenant_id()`; e.g. `purge_tenant_trail(current_tenant_id())` (`db/queries/Admin.sql:168`) deletes that tenant's trail |

## 3. Decisions

- [x] D1 The fix is an **explicit policy for the owner role, per table and per command** that a
  definer function needs across tenants. For example:
  `CREATE POLICY definer_read ON tenant FOR SELECT TO hubtask_migrator USING (true)`. The same is
  added on `account`, `membership`, `legal_hold`, `identity_provider` (and `UPDATE` there for
  `move_provider_offer`), `retention_policy` and `retention_rule`, as step 2's tests show is needed.
  It names the role as `CURRENT_USER` at migration time, not as a written name. The policy must name
  the functions' owner, which is whoever runs the migrations: the superuser on Compose and CI, the
  chart's owner role under CloudNativePG, and `hubtask_migrator` on a managed service.
  — decided by: worker, unless the coordinator judges it the owner's (see D3). Reason: it gives the
  owner on a managed database exactly what the owner already has on every other deployment (a
  superuser, or `BYPASSRLS` under CloudNativePG), and it gives it **only for the commands named**.
  It grants nothing to `hubtask_app` or any request, and nothing the owner could not already give
  itself: it owns the tables and can change their policies. The doors stay as narrow as they are:
  what `hubtask_app` reaches is still exactly the functions' answers.
  Rejected alternatives:
  - `BYPASSRLS` on the owner: a managed service cannot grant it (ADR-0052).
  - A third role owning the functions with its own policies: a new role the operator must create
    beforehand on a managed service, a new obligation in §2.1.1, and the same policies anyway.
  - Setting `app.tenant_id` inside each function: it cannot read across tenants, which is the
    functions' whole point.
  - `NO FORCE` on the tables: it would lift the boundary for the owner on every command, and it
    would touch SG-4's exception list.
- [x] D2 The rule goes into multi-tenancy.md §2.1 ("Doors through the boundary": the owner reads a
  table across tenants only through a named policy for the command a door needs), citing ADR-0052
  for the reasoning. SG-4's row in security.md gains a sentence only if its wording needs one. No
  ADR text changes, because a settled ADR keeps its text (`tools/checkpr/adr.go`) — decided by:
  worker after review finding 2.
- [ ] O1 **Waiting on the owner** (the coordinator takes it there): may the table owner hold a
  standing policy, bounded by no tenant, on the tenant tables the definer functions read across
  tenants? Without one — or `BYPASSRLS`, which a managed service cannot grant — those functions
  answer nothing on a database the operator brings (§ 1).

  **Why this is the owner's.** The suite holds the opposite stance in a test.
  `test/integration/membership_dedupe_migration_test.go:151-159` fails when any policy other than
  `tenant_isolation` remains on `membership`, with the message *"the migrator still reads every
  workspace"*. Migrations 0019, 0143 and 0149 give the migrator a policy for one statement and take
  it away again, for that reason. D1 needs a standing policy on `membership` (`is_operator` reads
  it), so that assertion would need an exception. That is a change to a test guarding the boundary,
  which the review's condition puts with the owner.

  **The options, as the owner would weigh them:**
  - (a) D1 as written: standing, command-scoped policies `TO CURRENT_USER` on tenant, account,
    membership, legal_hold, identity_provider, retention_policy and retention_rule, and the
    membership test's assertion narrowed to "no policy for any role but the owner".
    - Gains nobody anything the owner could not already give itself, because it owns the tables
      and their policies.
    - Every deployment but a managed one already runs so (superuser, or `BYPASSRLS` under
      CloudNativePG).
  - (b) A dedicated role, `NOLOGIN`, without `BYPASSRLS`, that owns the definer functions and alone
    holds the policies.
    - The migrator then reads nothing across tenants.
    - The membership assertion still needs an exception, now for that role.
    - The operator of a managed service may have to create the role beforehand: a new obligation in
      §2.1.1.
  - (c) Declare the doors unsupported on a database the operator brings, which means sign-in in
    multi mode, the control plane and installation-wide subject requests. In effect, that withdraws
    ADR-0052's promise.

  The worker's recommendation is (a): the smallest change, and the state every other deployment is
  already in.
## 4. Proof and steps

Proof: a new test in `test/integration/managed_postgres_test.go`. On `managedDatabase`, migrated
as the non-superuser owner, it inserts two tenants with accounts, a membership and an operator. As
`hubtask_app` with no tenant set, it then calls every cross-tenant door in § 1 and asserts the real
answers:
- `resolve_tenant` names each slug;
- the census counts 2 workspaces and the accounts;
- `admin_tenants` lists both;
- `is_operator` and the roster answer the register;
- `subject_tenants` finds the address in both;
- `installation_unset` is false;
- the provider offers are counted.

It fails on `main` with the probe's numbers. A second assertion repeats
`TestTheBoundaryHoldsOnADatabaseWithoutASuperuser`'s point for the new policies: `hubtask_app`
reading `tenant` and `account` directly with no tenant set still sees nothing.

Steps:
1. This record.
2. Once O1 is answered: the migration (policies per the chosen option), with the test, in one
   commit, so every commit stays green; the membership assertion changed as the answer allows.
3. multi-tenancy.md §2.1, and SG-4's row if needed (D2).
