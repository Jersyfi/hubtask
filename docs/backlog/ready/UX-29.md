# UX-29 — Entries honour their collection's structure

**Task:** UX-29 · issue #1670 · `docs/backlog/milestone-UX.md`
**Checked against:** `origin/main` at `5f2562f02` (UX-09, #1668, merged) on 2026-10-21
**Verdict:** ready

UX-09 built the structure: eight settings in layers, resolved per container
(`StructureResolver`), and served on every container read. Entries ignore it today: every item
writer asks the installation's profile for a type, never its collection. This task makes every
entry obey its collection's `levels` and `fields`. Narrowing hides and never deletes (#1620,
`domain-model.md` §2): values and levels the collection no longer offers stay stored, every read
returns them marked hidden, and writing them is refused. It proves UC-WRK-24 check 3.

UX-09's B1 moved its draft decisions D5, D7 and D8 here (the entry writers, the hidden mark,
moving and copying). Their wording did not survive into UX-09's final record, so they are decided
again below: D2, D3 and D5.

Known traps:

* *A port can be written and never called*: `ItemTypes` is called by the writers and reads of
  the same step.
* *A write outside `UnitOfWork.Within`*: the gate joins the writer's transaction; integration
  tests.
* *`Handler.Invoke` skips validation*: refusal tests go through `registry.Invoke` and the router.
* *A manifest declares what it does not answer*: `structure_enforced` lands in the last code step,
  tested against a refused write.
* *A capability test can ask itself*: literal capability lists in the assertions.
* *The integration tests share one database*: own tenants.
* *Coverage is enforced per package*: registry tests per writer group.
* *`locales/*.json` is grouped*: insert by hand.
* *Writer copies miss a late field*: the gate is set in each writer's literal in `main.go`.

**A trap of this task:** `historyForm(profile)` would turn a task's history compact under *List* if
it were given the collection's profile. It keeps the bound's profile; only the gate uses the
collection's (D2).

**Two writers at once** (a value write and a narrowing): the item writer reads the layers without
a lock (`LayerRead`), under READ COMMITTED, so it sees the structure as last committed when each
statement runs.

* If the narrowing commits first, the write is refused.
* If the write commits first, the value is stored and hidden a moment later — the state of a value
  written before the narrowing. Nothing is lost and nothing inconsistent is stored, so no row lock
  is taken (a share lock on the tenant row in every item write would serialise the workspace on
  one row).
* A widening racing a refused write: the client retries and succeeds.
* `MoveContainer` takes `LayerShared` on the destination hub before resolving, so a hub writer
  fanning out either sees the moved collection among its heirs or waits for it.

## 3. Decisions

- [x] D1 The rule — decided by: owner, #1620 → `domain-model.md` §2; the cut and the codes by the
  coordinator, #1670 (§ UX-29), and the review's resolution (coordinator, 2026-10-21).
- [x] D2 **The gate.** `core/domain/model/work/StructureEntries.go`:
  * `Offered` is a collection's structure in force over the bound.
  * `Offered.Profile(type)` is the bound's profile with capabilities ∩ `fields[type]`.
  * `Offered.Hidden(type, ancestorTypes)` answers `EntryHidden{Level, Capabilities}`. `Level` is
    true when the type, or any type on its ancestor chain, is not in `levels`; an activity under a
    task is offered when `levels` holds both, whatever happens to the work package. `Capabilities`
    lists the bound's capabilities of the type missing from `fields[type]`, in the bound's order.
  * `Offered.Require(type, ancestors, capability, path)` refuses the level first
    (`items.level_hidden`), then a value the bound carries and the structure hides
    (`items.capability_hidden`). A value the bound lacks keeps today's
    `items.capability_not_supported`.

  The application gains an `EntryGate` (the `StructureResolver` and `ItemTypes`). It resolves a
  collection's structure in the writer's transaction (`LayerRead`) and the entry's ancestor types
  in one statement. Every writer in § 2(b) asks it. A removal of a hidden value is refused like a
  write, except `RemoveMember` of somebody who lost sight of the collection.

  The three hierarchy builders (`CreateWorkItem.go:637`, `MoveWorkItem.go:688`,
  `DuplicateWorkItem.go:1052`) keep the bound's hierarchy for placement and depth, then ask the gate
  about the level. The history form keeps the bound's profile. Rejected: narrowing the `Hierarchy`
  per collection, which would answer `items.parent_type_invalid` for a hidden level and move the
  roots. — decided by: worker; the detail code by the coordinator.
- [x] D3 **The mark.** `WorkItem.hidden: {level: boolean, capabilities: Capability[]}`, optional in
  the contract, present on every item read and write answer outside sync. `capabilities` depends on
  the type and the collection, not on whether this entry holds a value. That makes it exactly what
  the writer refuses (P-05), lets the replica derive it from the structure alone, and needs no
  field-to-capability table on either side; counting hidden content is UX-11's. Reads go in batches:
  one resolution per distinct collection on the page, and one `ItemTypes` statement for every
  ancestor on it. Rejected: a mark per held value. — decided by: worker; the batching by the
  coordinator.
- [x] D4 **What "writing" covers.** A value write or removal, a create, a rename, completing or
  reopening, reordering, placing (move, copy root, stamp).

  It does not cover the lifecycle: trash, restore, archive, unarchive, retain, purge. Deleting
  "stays the lifecycle's use cases" (UC-WRK-24 *Where it ends*), and a subtree is trashed with its
  hidden children. Moderation deleting a comment is part of that lifecycle.

  The roll-up (I-W5) is unchanged: a hidden child cannot change its completion, so it never
  triggers one; its stored state still counts when a visible sibling triggers the roll-up, so a
  parent under `ROLLUP` with an open hidden child stays open — widening shows why. — decided by:
  worker; moderation by the coordinator.
- [x] D5 **Moving and copying keep what the destination hides** — a correction under #1620.

  Carried values are not new writes. Dropping them on a move or copy into a narrower collection
  would delete user data irrecoverably, which #1620 forbids. So every value the **bound** carries is
  kept and marked. What the installation's profile lacks is still dropped and reported as I-W6 says:
  that is not a structure, and no switch brings it back.

  The destination decides the level: the root must land on an offered level, descendants may be
  hidden, and a hidden entry may be moved out to a place that offers it (the way out without
  flattening). I-W6 gains the sentence (step 12). — decided by: coordinator (§ UX-29, the review
  resolution) and worker (the bound/structure split).
- [x] D6 **Templates.** A stamp creates new values, so they are writes. Which applies when:
  * **The structure hides a node's value** (notes, due date, assignee): the entry is created
    without it, and the value is reported in `dropped_references` — kind `NOTES`, `DUE_DATE` or
    `ASSIGNEE`, `id` the new entry's identifier (never content), code `items.capability_hidden`.
  * **The bound lacks it:** notes are refused whole as today (`NewWorkItem`); the due date, until
    now dropped silently (`InstantiateTemplate.go:309`), is reported with kind `DUE_DATE`, code
    `items.capability_not_supported`; the assignee as today.
  * **A node of a hidden level** refuses the stamp whole (`items.level_hidden`).

  Defining a template stays against the installation topology (UX-09 D12). — decided by:
  coordinator (§ UX-29, the review resolution) and worker.
- [x] D7 **Custom field definitions are unchanged.** A definition belongs to the collection's
  configuration, not to an entry; writing a value through it is gated by `CUSTOM_FIELDS` like any
  value. — decided by: coordinator (the smaller option).
- [x] D8 **Suggestions take the target's shape.**
  * The breakdown's material (`JumbleSource.go:170`) and the template draft's
    (`suggestion/Template.go:126`) describe the target collection's offered levels, with notes
    only where offered (UX-08's fix, from the installation to the collection).
  * A conversion's children (`under`) take the first child level of what the entry became that the
    target offers, in the system's order (work package, then activity); in *List* there are none.
  * Classification proposals offer labels, fields, the column and a due date only where the
    target offers `LABELS`, `CUSTOM_FIELDS`, `BUCKET` and `DUE_DATE`.
  * Notes the entry's collection hides are not sent to the provider.

  So what a person accepts is what the writer accepts. — decided by: coordinator (the jumble and
  field rows) and worker; UX-08's reason.
- [x] D9 **The client derives the mark.** Sync records carry no `hidden`: a narrowing would
  otherwise rewrite every entry of every inheriting collection. The push answer drops it too.

  Online, the server's reads carry the mark. Offline, `apps/webapp/src/lib/data/replica.ts` derives
  it as `storeFor` answers. The inputs are the container's `structure` from the replica and the
  bound — the profiles of `/meta/capabilities`, handed to the replica module by
  `capabilities.svelte.ts` when the manifest arrives (until then no mark is answered, as nothing is
  shown as available before the manifest). The sync engine stays without product knowledge.

  One table, `api/fixtures/hidden-entries.json` (bound, structure, entry chain → mark), is read by
