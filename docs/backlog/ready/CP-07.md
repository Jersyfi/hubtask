## 3. Decisions

- [x] D1 Add a chart value `restoreDrill.afterRelease` (default `true`, so production is unchanged).
  Integration sets it `false` and runs the drill only by its CronJob. — decided by: worker. ADR-0082
  says "the restore drill as a CronJob". A drill on every push to `main` would hold or time out every
  deploy. Rejected: `--no-hooks`, which would also drop the migration hook.
- [x] D2 Smaller in size, the same in shape:
  - one instance;
  - storage 4Gi;
  - requests 256Mi and limits 1Gi for both the instance and the drill's temporary cluster;
  - the operator at gate-pitr's pinned version.

  — decided by: worker, ADR-0082 "smaller in size". If 8 GB does not hold the instance, the temporary cluster, the operator and the workload at once, the larger node is the access holder's step, and the record of the first drill says which.
- [x] D3 **"A-12 real" is the recovery half.** A-12 has two halves.
  - The PITR half (`prometheus-rules-pitr.yaml`: `HubtaskArchiveGap`, `HubtaskArchiveBacklog`, `HubtaskBaseBackupStale`, `HubtaskNoRecoverabilityPoint`) reads the operator's series. It becomes real by scraping the database's metrics, and it is routed like every other alert.
  - The backup half (`HubtaskBackupStale`) reads the application's own backup runs per target. Integration runs none, so it stays routed to `muted` by alertname, with the reason in the values and the route.

  — decided by: ADR-0082's context, which says "alert A-12 real instead of muted" in the sentence about the database's shape that makes the recovery half possible. Reviewed by the coordinator, and named to the owner in the coordinator's report. Rejected: an application backup of the `operations` workspace to an installation target, which would need schedules to accept installation targets, kept tenant-only on purpose by CP-05.
- [x] D4 Object Lock is checked by the access holder in the Hetzner console before the bucket is
  created. With it, the bucket is created in compliance mode with 35 days, which equals
  `database.backup.retentionPolicy`, as `k8s/values.yaml:146-148` requires. Without it, the bucket is
  created without a lock, and the drill record says so; ADR-0082 already allows that ("checked before
  building"). The README carries the check as the rebuild's first step. — decided by: worker; the
  fact is only available with the account.
- [x] D5 The bucket's name and endpoint are configuration and live in `values.yaml`, because CI's
  deploy reads only that file. The keys are a Secret `hubtask-wal`, created by `bootstrap.sh` from
  two variables the holder exports on the host and never printed. — decided by: worker,
  `values.yaml`'s "names in the file, values on the host".
- [x] D6 The rebuild is destructive for integration's database. That is allowed: "its data is
  nobody's, the workspace is bootstrapped again" (ADR-0082). `bootstrap.sh` does not delete the old
  StatefulSet or its volume itself; it stops and the README names the two commands. Deleting a
  database is a step a person takes, not a side effect of an idempotent script. — decided by: worker.
- [x] D7 RT-8's second database comes from CloudNativePG's `Database` resource (`hubtask_rt8`,
  owner `hubtask_migrator`) with a script `deploy/integration/rt8-database.sh` that creates and
  drops it and its secret. Superuser access stays off. — decided by: worker; the operator manages
  databases declaratively since 1.25, and a superuser enabled for a test is a superuser left enabled.
