## 3. Decisions

- [x] D1 **The sign-in takes `identifier`.** `SignIn` gains `identifier` (string, 1–254); `email`
  stays as it is and is no longer required; exactly one of the two, else `422 auth.identifier_one` -
  a shape refusal, the same for everybody. The card and `hubctl` send `identifier`; every existing
  client keeps working. Not a breaking change: a request property that stops being required and an
  optional request property added are both compatible for every client that sends what it sent
  before (a compatibility check such as `oasdiff` reports them as information, not as breaking);
  `make gate-api-compat` (#1256) is not on `main` yet, so step 2 runs it from that branch's tool
  where it can and records the result in the pull request. Decided by worker. Rejected: dropping
  `format: email` from `email` - it changes the generated Go type a client compiles against;
  renaming `email` - the owner's (AGENTS.md).
- [x] D2 **One refusal, one ledger.** The identifier is trimmed, brought to NFKC and lower-cased; with
  `@` it is looked up as an address (`LookupAddress`), without as a sign-in name - one statement
  either way (`lower(email) = $address OR sign_in_name = $name`, one of them null), the decoy as
  today. Nothing about its shape is judged at sign-in: `ab` simply matches nothing. The ledger
  subject is `account:` + the normalised identifier, hashed as today, so a name and an address are
  the same kind of row; the IP class, the metric reasons and the auth rate-limit bucket are
  unchanged. Decided by T-02, identity.md §4.3 and the task; the form by worker.
- [x] D3 **The sign-in name.** NFKC, trimmed, lower-cased - an address's treatment
  (`emailAddress`) - and 3 to 32 characters counted after that. Refused: `@` (ADR-0074 §1), and
  whitespace and control characters (Unicode `Z*` and `C*`): a name on a printed slip that a child
  types back must read one way. Stored in its folded form, unique per workspace among accounts not
  deleted (partial unique index); the display name carries the person's own spelling. Decided by
  worker, within ADR-0074 §1; rejected: an ASCII-only alphabet (a family in Greek or Cyrillic would
  be refused its names).
- [x] D4 **The start password and its one showing.** Drawn through the `Entropy` port (rule 4): 80
  bits as four groups of four characters from 32 lower-case letters and digits without look-alikes
  (no `0 o 1 l i`), joined by `-`. Hashed with Argon2id as any password, `password_set_at` and
  `start_password_at` set to now, never judged by the rule (it is never kept). Answered once, as
  `start_password` in the 201, a `secret.Secret` until the adapter writes it. The web app shows it
  in `OneTimeSecret` (copy, acknowledgement) and beside it *Print*: a slip with the workspace's
  address, the sign-in name and the start password, drawn by a print style of its own in
  `apps/webapp` - the design-system component is not changed. Decided by worker. Rejected: a
  passphrase of words (a word list per language for one screen).
- [x] D5 **One use case creates and places.** `CreateManagedAccount`, `POST /accounts:create-managed`:
  `display_name`, `sign_in_name`, `role`, `scope_type`, `scope_id`. It asks `MANAGE_MEMBERS` at the
  workspace (an invitation's rule - check 1's "owner or administrator") and the setting (D6), then
  grants through `GrantMembership`'s own authorisation, step-up and audit at the scope, in one
  transaction with the account. The account is `ACTIVE`: there is nothing to redeem.
  `account.managed_created`, notice, the name `Sensitive` (as the address is in `account.invited`).
  The web app's form sits on *People* with "where": the workspace or a hub; a collection or an entry
  through the API. Decided by worker. Rejected: the invitation screen's two calls - a start password
  shown for an account whose grant then failed is an account nobody can find.
- [x] D6 **The setting governs creation only.** Switched off - here, or by a lock above - nothing new
  is created; the managed accounts already there keep signing in (P-16) and keep their data (P-03).
  The card's label follows whether the workspace **has** a managed account that is not deleted or
  anonymised (`sign_in_names` on `/auth/sign-in-rules`, an `EXISTS` in the workspace's own
  transaction), not the setting: a default-on setting would otherwise relabel every workspace's card
  (P-10, check 4 "elsewhere unchanged"). A host without a workspace answers `false`, byte for byte
  an undecided workspace (identity.md §3). Decided by worker.
- [x] D7 **The setting is a sign-in switch.** `managed_accounts` joins the sign-in rule's switches:
  product default on, "off" the stricter value, resolved by `Effective(instance, plan, workspace)`,
  tightened only, locked with its origin, so *Sign-in* settings shows value, source and lock beside
  it (check 8) and the installation's screen, `hubctl admin instance` and the instance file carry it
  through their generic `sign_in` map. A `PLAN` lock has no writer yet (ADR-0070 §3); the resolver
  and the screen already read it. Writing it takes the step-up every sign-in switch takes. Decided by
  ADR-0074 §7, identity.md §13 and §18; the placement by worker. Rejected: a workspace setting of
  its own outside the rule - a second place for the same three levels (P-06).
- [x] D8 **The first sign-in ends in the person's own password, after any factor.** The verdict owes
  `PASSWORD_CHANGE` while `start_password_at` is set. The pending credential remembers that a change
  is owed (`auth_pending.password_change_owed`, migration 0127), so a `TOTP` or `ENROLL` step that
  comes first answers `202 PASSWORD_CHANGE` on completion instead of the pair - which also fixes
  the finding of § 1 for every account (identity.md §4.2 already says a refused password meets the
  step). Every door that sets a password clears `start_password_at`. The rule's context words gain
  the sign-in name. Test first, own step. Decided by worker. Rejected: the change before the factor -
  `SetPasswordAndSignIn` would have to chain into `ENROLL`, a new path that ends near a session
  without the factor.
- [x] D9 **The creation's answer is never kept for a replay.** The idempotency middleware wraps every
  `POST` that carries the header, declared or not (`cmd/server/main.go:2350`), and keeps the answer
  in clear (§ 1); the start password must exist nowhere but its hash. So the contract declares no
  `Idempotency-Key` on the route, the handler marks its answer `Cache-Control: no-store`, and the
  middleware stores no body for any answer so marked, whichever route - the key is still reserved and completed with
  the status, so a repeat answers that status with no body instead of running twice. A lost answer
  is a `409` on the name at the next attempt, and the way out is PH-07's new start password. Test
  first, in step 5. The existing one-time credentials (access tokens and the other secrets shown once)
  are finding #1266; with this mechanism each needs only the header. Decided by worker (T-18).
- [ ] O1 **The password stays a way in for a sign-in name (proposed)** where the methods leave it out (P-16):
  before any lookup an identifier with `@` meets `auth.password_not_offered` as today, one without
  goes on; once the password proved right, an account that holds an address is refused the same way
  (PH-07's upgrade). The doors that know the account - the change step, the step-up's `PASSWORD`
  method, the deprecated factor-off proof - stay open for an account without an address. The card
  then shows a *Sign-in name* form beside the providers; the *Sign-in* settings' password switch says
  that people with a sign-in name keep their password. identity.md §4.1 and §17 gain the sentence.
  Decided by worker under P-16 and ADR-0077 §4 (a way stays open); rejected: refusing to switch the
  password off while a managed account exists - it would force a password on every address in a
  company that signs in through its directory (D4), and cannot hold against an installation lock.
  Waiting on the owner: decision issue #1268 - a deviation from identity.md §4.1's rule (the
  fallback of §17 its one exception); (a) this proposal, (b) refusing to switch the password off while
  a managed account exists, (c) a fallback per account. Step 9 and the card's row "password off and a
  managed account here" wait; nothing else depends on it.
- [x] D11 **What needs a mailbox says so.** (a) The sign-in card's *Forgot your password?* detour,
  where `sign_in_names`: one sentence for everyone - signing in with a sign-in name, there is no mail;
