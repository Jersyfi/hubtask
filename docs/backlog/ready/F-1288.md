## 3. Decisions

- [x] D1 The rule: an actor may grant a role only if the strongest role they hold along the scope's
  path is at least as strong (`identity.Role.AtLeast`), in addition to `MANAGE_MEMBERS` there. An
  owner gives any role; an administrator any but `OWNER`; `AUDITOR` stays grantable by an
  administrator (it is last in the order and carries nothing an administrator lacks) — decided by:
  worker, after #1288's proposal 1 and UC-ID-14 check 1 ("only roles the inviting person may give;
  an administrator is not offered *Owner*"); it follows the existing `run_as` ceiling
  (`automation.md` §2.1). Written in `domain-model.md` §3.2. Rejected: a fixed rule "only an owner
  grants `OWNER`" (it would leave a hub-scoped ceiling unstated, and the same question returns for
  any role added later).
- [x] D2 Where: a field `Grants identity.Role` on `access.Request`, decided in `access.Service`
  through a domain function `service.MayGrant`; the refusal is recorded like every refusal there —
  decided by: worker. Rule 2 and `TestTheRoleIsResolvedOnlyByTheAuthoriser`: the role is resolved by
  the authoriser only; a refusal audited in one place. Rejected: `RoleOf` in `GrantMembership`
  (a second refusal path with its own audit, and the authoriser interface of the identity package
  would grow for every fake).
- [x] D3 The refusal: `403 access.role_above_own` with the role as parameter, distinct from
  `access.not_permitted` because the permission *is* held — decided by: worker. The step-up comes
  after it.
- [x] D4 How the client learns the set: an additive field `grantable_roles` on `MembershipPage`, the
  roles the caller may grant **at that scope**, strongest first, `[]` where none — decided by:
  worker (#1288 proposal 2 offers this or the manifest). The ceiling depends on the scope, and the
  manifest is per actor, not per scope; the list is what both screens already read for the scope
  they grant at. A token without `members:write` gets `[]`, since every grant would be refused.
  Additive, so within what a worker decides (AGENTS.md).
- [x] D5 Out of scope, reported as findings rather than fixed here: (a) an administrator may revoke
  an `OWNER` membership (after a step-up) — whether a revocation has the same ceiling is a product
  question the issue did not raise; (b) an administrator may add themselves to a group that holds
  `OWNER` (group members are changed with `MANAGE_MEMBERS` on the workspace) — a second escalation
  path, wider than this fix — decided by: worker. The pull request says plainly that the escalation
  #1288 names is narrowed, not closed, while (b) is open.
- [x] D7 The grant and its list ask along one path: `ListMemberships` asks `GrantableRoles` on
  `pathTo(scope)`, the path `GrantMembership` authorises on — decided by: worker (review finding 2).
  Whether that short path (`[workspace, entry]`) judges a private hub at an entry correctly is a
  question about the existing grant, not this fix; reported as a finding if it does not.
- [x] D6 Documents: `domain-model.md` §3.2 (the rule) and its authorisation table row for
  Identity & tenancy; `api/openapi.yaml` (the grant's refusal, the new field); UC-ID-14 *Today*
  loses check 1 and `checked_by` gains the tests. No ADR: a consequence of the existing role order,
  not a new architectural choice — decided by: worker.
