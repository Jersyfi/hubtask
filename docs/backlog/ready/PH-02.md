## 3. Decisions

- [x] D1 Semantics: once; only while open and before the original deadline; at most three months after receipt; reason `COMPLEXITY` or `NUMBER_OF_REQUESTS`; informed date required; Hubtask never writes to the person — decided by data-protection.md §4.1, UC-PRV-01 *Where it ends*.
- [x] D2 Storage: `due_at` stays the deadline in force and takes the extended date; new nullable `original_due_at` (also the "once" marker), `extension_reason`, `informed_on` (`date`), a CHECK that all three are set or none, and one on the reason's values — decided by worker: every reader (list order, cursor, `DueBefore`, the overdue count, `dsr_open_idx`, `standingOf`, A-19) follows unchanged, and an old pod in a rolling update reads the right deadline and writes none of the new columns (`Privacy.sql:33-42`). Rejected: a separate `extended_due_at` read through `COALESCE` in four queries and a new index.
- [x] D3 "Three months after receipt" is a calendar period in the workspace's own zone (`Workspaces.Find`, falling back to UTC for an unknown zone as `InstantiateTemplate.go:545-549` does): the receipt's date plus three months, the day clamped to the last day of that month, and the extended deadline must lie before the start of the following day (Reg. 1182/71 Art. 3(2)(c)); it must also be later than the current deadline. The response carries `extendable_until` for a case that can be extended, so no client repeats the arithmetic — decided by worker. Rejected: `AddDate(0,3,0)` (30 Nov → 2 Mar, past 28 Feb); the same UTC clock time (lenient by hours where a clamp collapses, e.g. received 31 Jan 00:30 CET, and by days behind UTC around 28 Feb/1 Mar); 90 days. A zone changed since receipt: today's zone counts.
- [x] D4 `informed_on` is a calendar date: a plain string in the descriptor (no registry format exists), `format: date` in the contract, parsed in `invoke` like `anchor_date`; refused when malformed (`privacy.informed_on_invalid`) or before the day of receipt or after today, both in the workspace's zone (`privacy.informed_on_out_of_range`) — decided by worker: §4.1 names a date; a date-time is invented precision.
- [x] D5 Its own use case `ExtendDataSubjectRequest`, `POST /privacy/requests/{requestId}:extend` with `Idempotency-Key`, `Destructive: false` — decided by worker: api-guidelines.md §2 "Actions use the suffix pattern" (`:62`); folded into the update it would inherit `Destructive: true` (`Requests.go:668`) and an agent would need `agent:destructive` (`core/application/usecase/Registry.go:245-283`) to move a date. (The earlier record's reason — one descriptor, one action — was wrong: the update writes three actions, `Requests.go:272-282`.)
- [x] D6 Refusals: the descriptor declares `due_at`, `reason`, `informed_on` required and the reason as an enum, so a missing field answers `usecase.field_required` and an unknown reason `usecase.field_not_in_enum` at REST, MCP and automation (`Input.go:296-303,335-341`); the tests assert those. New codes: `privacy.already_extended`, `privacy.extension_after_deadline`, `privacy.extension_too_long` (param `latest`), `privacy.extension_not_later`, `privacy.extension_reason_invalid` (domain guard for callers below the registry), `privacy.informed_on_invalid`, `privacy.informed_on_out_of_range`; a closed case reuses `privacy.request_closed` — decided by worker.
- [x] D7 Two writers: one conditional `UPDATE … WHERE id AND original_due_at IS NULL AND status IN open AND due_at > $now`, `$now` the `Clock` value; zero rows → re-read in the same transaction and answer what is true now (not found, closed, already extended, after deadline).
