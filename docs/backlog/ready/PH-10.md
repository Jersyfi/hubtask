## 3. Decisions

- [x] D1 **Any hold in force stops both acts.** A deletion request is refused, a pending workspace
  stays pending until the last hold is lifted, `REPLACE_TENANT` is refused, and one that runs keeps
  the workspace's holds — decided by the owner, 2026-10-09, decision #1233 (a) → data-protection.md
  §5, backup-restore.md §8.2, multi-tenancy.md §5, data-retention.md §4, UC-LIF-06 check 3, milestone
  decision 6 (pull request #1236). Every scope counts, `ACCOUNT` included: a workspace's deletion
  destroys a person's contributions as surely as a hub's.
- [x] D2 **The refusal.** `lifecycle.legal_hold`, 409 — the code UC-LIF-06 check 3 names. The two
  workspace-wide acts pass `scope: WORKSPACE`, never the hold's own scope: the operator who asks for
  a deletion must not learn that a person or one entry is under a hold (P-01), and the owner's
  replace is refused by every hold alike. The `en` text gains a `select` on `WORKSPACE` ("a legal
  hold is in force in this workspace; it cannot be deleted or reset to a backup until every hold is
  released") that names nobody to ask, since the operator cannot know who placed it (P-11); the
  purge's sentence stays as it is. Asked before the typed name and the step-up, so a refusal never
  burns a proof (the precedent at `Deletion.go:89-90`). Decided by worker. Rejected: the oldest
  hold's scope, as the purge passes it — it tells the operator more than D10 allows.
- [x] D3 **The grace job under a hold.** The guard reads the holds in its read-only transaction
  before any byte is removed. Under a hold the pass removes nothing and returns `Repeat` with a day,
  so the deletion follows within a day of the last hold's release, whatever lifted it. The final
  transaction reads them again before the fall; after D4 no hold can arrive between the guard and
  the fall, so that read defends an impossible case — and if it ever fires, the fall is rolled back
  as `admin.tenant_leaving` is today, with the bytes already gone. A pending workspace whose deadline
  lies ahead repeats until the deadline instead of finishing — otherwise a second request folded into
  the waiting row (`Job.sql:32-34` keeps the earlier `run_at`) would run early, find the deadline
  ahead and end the only job (relevant once SC-08's *Cancel deletion* exists). No journal entry per
  pass: an entry per retry puts noise where evidence lives (`Lifecycle.go`'s precedent); the hold's
  own trail and the operator's listing (D10) say why the workspace stands. Decided by worker.
  Rejected: finishing the job and letting the release seed a new one — no release can reach a
  pending workspace (§ 1).
- [x] D4 **A pending workspace under a hold: prevented where possible, and its exit.** Placing a
  hold reads the workspace's status after taking PH-01's exclusive lock and refuses
  `access.tenant_pending_deletion` (403) in a pending workspace, which closes the race of § 1; a
  held pending workspace then arises only from an older binary during a rolling update or from a
  workspace already pending with a hold when this ships. Access stays blocked (multi-tenancy.md §5),
  so its owner cannot release the hold while it is pending; ADR-0077 §4 governs signing in and is not
  touched, the lockout comes from the operator's own request, and the data stays reachable through
  the operator's export in every state (`Export.go:73`). The way back is SC-08's *Cancel deletion*
  (#1064, where this is written down), then the release, then a new request; #1236's UC-LIF-06
  *Where it ends* says so. Decided by multi-tenancy.md §5 and decision #1233; no deviation, no
  question; the interim is named to the owner in the pull request.
- [x] D5 **A rehearsal stays possible.** Only a `REPLACE_TENANT` with `dry_run: false` is refused;
  the rehearsal writes nothing and keeps UC-BAK-05 check 1 ("any mode can be rehearsed") as
  written. The screen then offers no real run (D11). Decided by worker. Rejected: refusing the
  rehearsal too — it changes UC-BAK-05 check 1 for no protection.
- [x] D6 **Asked twice.** `StartRestore` refuses where the caller can read it; the restore job asks
  again inside the emptying transaction, under PH-01's shared lock, before anything is emptied, and
  fails the run with `lifecycle.legal_hold`. The run stays `FAILED`: the runner's retry of the job
  finds a closed run and neither empties nor reopens it. The safety copy taken before stays — the
  way back, also for the one gap #1241 leaves (a death between the emptying and the first recorded
  batch, then a hold: the resumed attempt would empty again, is refused, and leaves the workspace
  emptied). Decided by worker (known trap "read-then-write without a lock").
- [x] D7 **No restore into a living workspace writes a hold.** `REPLACE_TENANT` does not empty
  `legal_hold`; `REPLACE_TENANT`, `MERGE` under every rule and `SELECTIVE` write none of the
  archive's holds and count them as skipped in the report. `NEW_TENANT` brings them along as today.
  A hold is an obligation on the data it covers, and a copy is that data again: a test copy or a
  forensic copy of held data is held data, and the provider-migration path (#1074) must not arrive
  without the obligations it carries. That the copy may carry a hold released in the source since is
  the archive's state at its moment, which a new workspace takes whole; its owner releases it there.
  Decided by worker; data-retention.md §4 and backup-restore.md §8.2 say it as #1236 corrects them.
  Rejected: `REPLACE_TENANT` only — a merge with `overwrite` would re-open a released hold and wipe
  its release (UC-LIF-06 check 7); dropping holds in `NEW_TENANT` — a copy would shed an obligation.
- [x] D8 **A resumed replace (#1238)** is fixed by pull request #1241 — the workspace is emptied
  only while the run has no recorded progress. This task takes that result and builds on it (D6);
  it adds no migration for it. Decided by the coordinator's split.
- [x] D9 **Finding: the import drops a hold's release reason.** `ImportLegalHold` gains
  `released_reason`. Test first. Decided by worker.
- [x] D10 **The operator sees that a hold stands.** `admin_tenants()` answers `legal_hold`
  (migration 0121, the 0118 precedent), `AdminTenant` carries it, `ListTenants` outputs it. A
  boolean only — no scope, count or reason: the operator needs to know the deletion cannot proceed,
  not what the workspace is preserving (P-01). The console leaves *Delete* out for a held workspace
  and says why; a pending one says its deletion waits on a hold; `hubctl admin tenant ls` marks both.
  Decided by worker (P-05 "broken when", P-08, P-11). Rejected: the refusal alone (P-05).
- [x] D11 **The restore screen.** *Replace* is offered only where the manifest grants
  `DELETE_CONTAINER` (`permissionVerdict`) — a finding, own commit — and its real run only while no
  hold is in force, read from the holds list (`ListLegalHolds`, `STRUCTURE`, which every owner
  holds). Decided by worker (P-05).
- [x] D12 **UC-BAK-05 check 5 and UC-BAK-06 check 4** are amended in #1236 (`decision #1233` for
  the holds; a correction under data-retention.md §4 item 2 for the restriction), where AGENTS.md
  puts an owner's answer. This task makes them true and moves their *Today*. The milestone's PH-10
  text lives only on PH-01's branch; it is corrected in step 10 once #1211 has landed ("as the owner
  decides" → the answer), which records progress and decides nothing.
- [x] D13 **Outside this task.** Point-in-time recovery is #1239, bounded in UC-LIF-06's *Where it
  ends* by #1236. Decided by worker (AGENTS.md, "Working rules").
- [x] D14 **Order.** The steps that touch no file of PH-01 (#1211) — 2, 3, 4 and 9 — are built
  first, on `main` as it is; the rest waits for #1211: the lock of its D7 is what makes the
  two-writer rows hold, the `Active` port it changes is the one read here, `LegalHolds.go`,
  `Lifecycle.sql` and the repository port are shared files, and migration 0121 must follow its
  0120. #1236 and #1241 are on `main`. Decided by worker, with the owner's word to continue
  (2026-10-09).
- [x] D15 **No restore lifts a restriction (#1240).** A restore into a living workspace keeps a
  live `RESTRICTED` status: `ImportAccount` keeps the live `status` when it is `RESTRICTED`, and
  `REPLACE_TENANT` keeps a restricted account's row out of the emptying, so the archive's row meets
  it and leaves its status (data-retention.md §4 item 2: a restricted object is neither deleted nor
  changed). It blocks UC-PRV-03 check 10 in `Delivers` under PH-01 D4, so it belongs to the
  milestone (`docs/backlog/README.md`), and it sits beside D7. Test first, own step. Decided by
  worker.
