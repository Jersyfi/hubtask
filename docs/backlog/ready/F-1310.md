## 3. Decisions

- [x] D1 Restrict the setting: GitHub-owned actions, the listed third-party repositories as
  `owner/repo@*`, no verified creators, SHA pinning required — decided by: owner, 2026-10-13 (comment
  on #1310) → written in ci-cd.md §4 (step 4). Applied by the coordinator through the API, not by
  this pull request.
- [x] D2 The list lives in `.github/actions-allowlist.txt`, one `owner/repo` per line, `#` comments,
  sorted — decided by: worker. Under `.github/` beside what it governs, read by the `ci` filter; a
  plain file a test reads in two lines and an owner reads at a glance. `@*` is the setting's form,
  not the file's: the version is fixed by the SHA in the workflow and the pin gates, and `@*` lets
  Dependabot's bumps pass without touching the setting. Rejected: listing `owner/repo@<sha>` (every
  bump would need the owner to change the setting before its pull request can go green); a YAML file
  (nothing to structure).
- [x] D3 The probe is a `ci.yml` job `actions-allowed` that needs `changes`, runs when `ci` is true
  (`.github/**`, and always on `main`), has one `run:` step and, as `if: ${{ false }}` steps, every
  `uses:` of every other workflow, and feeds `ci-required` — decided by: worker. It fits ci-cd.md §1
  as `ci-required` does: it holds no logic to reproduce; what it checks is GitHub's own set-up
  against the repository setting, which no `make` target can ask locally. So in `tools/cilocal` it
  is CI only, with that reason, like `secrets` and `dependencies`. Its `run:` step only says what
  set-up proved. Rejected: a `make` target asking the API for the setting (reading
  `actions/permissions/selected-actions` needs the administration right, which `GITHUB_TOKEN` and a
  contributor do not hold); running the probe in the nightly (red after the merge, the failure this
  job exists to move onto the pull request).
- [x] D4 Nested actions are declared, not discovered: an entry no workflow uses directly carries
  `# nested in <owner/repo>`, and the test accepts it only when that parent is listed and used
  directly — decided by: worker. Honest about what each side proves: the test proves the file and
  the workflows agree; the probe job proves the setting allows everything set-up resolves, nested
  ones included — the harmful direction, caught on the bump's own pull request. What stays unseen
  is a nested entry that stopped being nested: one owner-approved repository too many, removed when
  noticed. Rejected: resolving composite actions over the network in the offline test (the local
  gates stay offline, `check-action-pins.sh` header); extending the nightly pin script to read each
  pinned `action.yml` (possible later; not needed to close the finding).
- [x] D5 The probe job's `uses:` set equals the set of `uses:` (`owner/repo[/path]@sha`) of every
  other job of every workflow, checked by `test/architecture` — decided by: worker. A Dependabot
  grouped bump updates every occurrence, the probe's included, so it stays consistent; a hand edit
  to one side is red. Comparing with the pin, not only the repository, means the probe resolves the
  same commits the real jobs will.
- [x] D6 Documents: ci-cd.md §4 (what is true: the file, the setting, SHA pinning required, the
  probe job, how to add an action), §3's job table (the new job), §3.1's `ci` row unchanged (it
  already says "Everything"); known-traps.md gains *a composite action nests actions the allowlist
  must name* only if no gate holds it — the probe job holds it, so no trap is added; the
  existing *local composite action* trap stays. No ADR: ADR-0022 already decided the allowlist;
  this applies it — decided by: worker.
