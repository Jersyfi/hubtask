## 3. Decisions

- [x] D1 `PasswordHasher.NeedsRehash(stored string) bool` on the port; the Argon2id adapter answers
  true when any of the stored m, t, p or key length is lower than the build's, false for an
  unreadable hash — decided by: worker. "Lower", not "differ": during a rolling update (rule 12)
  an older and a newer build serve at once, and "differ" would have each rewrite the other's hashes
  on every sign-in. A cost lowered on purpose therefore reaches a hash only when the password is
  next set — written in identity.md §5.3. A change that raises one parameter and lowers another
  would still flip during the overlap; the comment on the constants says to avoid it. An unreadable
  hash is `Verify`'s error to report; rehashing it would hide the defect.
- [x] D2 The rehash runs in `SignIn.Execute` after the password proved right and after the
  password-offered, account and workspace checks, before the second step is decided — decided by:
  worker. Only a caller who would be let in gets the extra work; a challenged sign-in has still
  proved the password.
- [x] D3 Hash outside any transaction; write in its own `UnitOfWork.Within` as a compare-and-set
  (`RehashPassword :execrows`: `UPDATE account SET password_hash = new WHERE id = $id AND
  password_hash = $old AND deleted_at IS NULL`, tenant by RLS as every statement of
  `Session.sql`) — decided by: worker (coordinator's guidance). Deviates from the issue's "in the
  same transaction", which cannot be built: verification is outside every transaction for T-17's
  reason, and holding one across a second Argon2id would be worse. Rejected: a background job (it
  would need the plaintext password in the queue).
- [x] D4 The write sets `password_hash` and `updated_at`, nothing else: not `password_set_at` or
  `start_password_at` (the password's age, the rotation cutoff and the start password's mark are
  about the password, which did not change), not `account_password_history` (the same password),
  not `version` (bumping it would refuse a conditional profile edit racing a sign-in for nothing).
  `updated_at` moves because the incremental backup selects account rows by it
  (`db/queries/BackupExport.sql`, `ExportAccounts`): a row that changed without it would leave the
  old, cheaper hash in the delta chain and a restore would undo the upgrade — decided by: worker.
- [x] D5 No audit entry — decided by: worker. The credential did not change; the trail records the
  sign-in. The counter is the operator's view of the upgrade's progress.
- [x] D6 Scope: sign-in only. Step-up, disabling a factor and connecting a provider verify a
  password too, but each follows a sign-in of the same person or is rare, and sharing the code would
  add the write to three more use cases for no practical gain — decided by: worker. Named in the
  pull request; a person who signs in only through a provider keeps the old cost until a password
  sign-in, which is acceptable: their password is not their way in.
- [x] D7 A failed rehash (hash or write) logs a warning carrying only the error and does not fail
  the sign-in; the write runs detached from the request's cancellation under its own short
  deadline, as `recordFailure` does, so a client that disconnects once it has its answer does not
  take the upgrade with it — decided by: worker. The old hash still verifies; refusing a proven password over
  upkeep would be a self-inflicted outage.
- [x] D8 The metric `hubtask_auth_password_rehashed_total`, no label, counted only when a row was
  written, through a new `AuthSignals.PasswordRehashed` — decided by: worker, following #1404's
  pattern; the name is SI-18's.

Nothing on the owner's list: no API field, no dependency, no use case's *Goal*/*How to check*/
*Where it ends*, no security gate changed (the cost itself is unchanged), no user data deleted.

## 4. Proof and steps

No use case check is carried. The proofs:
* `infrastructure/crypto/Password_test.go`: a hash written by `Hash` needs no rehash; a hash under
  lower parameters (the existing `cheapHash`) does; a hash with a different key length does; an
  unreadable one does not.
* `core/application/service/identity`: a sign-in against an old-cost hash stores a new hash
  (compare-and-set against the old) and counts once; a current hash writes and counts nothing; a
  challenged sign-in rehashes; a suspended account does not; a failing store does not fail the
  sign-in and counts nothing; a wrong password rehashes nothing.
* `test/integration`: `RehashPassword` writes only when the old hash matches, leaves
  `password_set_at` and the history alone, and matches nothing under another tenant (SG-3); and
  `SignIn.Execute` with the real Argon2id adapter against PostgreSQL turns a cheap hash into one at
  the build's cost — a real transaction through `appPool` (the application's role under RLS, via
  `realWriter`); the cheap hash is seeded and the row read back through `adminPool` only.
