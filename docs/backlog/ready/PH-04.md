## 3. Decisions

- [x] D1 **Privacy is resolved by the authoriser from storage, not carried by the path.** The domain
  rule: `EffectiveRole` and `Allows` take whether the path runs through a private hub, and then a
  `TENANT` membership is not on the path — nothing else sits above a hub. `access.Service` asks a
  new port method, `Memberships.PrivateHubOn(scopes)` (one statement: a hub, a collection's hub, an
  entry's collection's hub), in the read-only transaction of `Along`, and only when `Along` returned
  a `TENANT` row. Every entry point (`Authorize`, `Permits`, `ReachInto`, `Permitted`, `CanSee`,
  `RoleAlong`, and `Administrators` for the warnings) goes through it; the automation service's own
  resolution (`Rules.go:635-664`, `Check.go:283`) moves into `access`. Decided by worker:
  ADR-0073's "one rule in one place" — the eleven hand-built paths cannot forget it, and a path
  without its hub is still judged right. A membership below the hub — on a collection in it or one entry
  in it — still grants what it grants today (ADR-0073 §1: "on the hub itself, or below it"); the
  domain table covers both. Rejected: a `private` flag on `identity.Scope` set by every
  path builder (some sixty call sites; one forgotten builder leaks silently); a row-level policy per
  hub (rule 2).
- [x] D2 **Creating one's own private hub.** `CreateContainer` with `type: HUB, private: true` asks
  no `STRUCTURE`: a person (`USER` account) holding any role anywhere in the workspace, and
  `containers:write`; the creator is granted `OWNER` on the new hub in the same transaction
  (owner-member, ADR-0073 §2), audited as a grant. "Where the workspace allows it" is always until
  PH-05's setting — accepted by the coordinator, 2026-10-10. Decided by worker for the rest: check 1
  says "whatever their role". Rejected: requiring a workspace role (a child holding a role on one hub
  only, UC-ID-15, could not have one).
- [x] D3 **Marking and unmarking.** `UpdateContainer` accepts `private` on a hub. `true` needs both
  the right to create hubs (`STRUCTURE` at the workspace) **and** an `OWNER` membership held on the
  hub itself — ADR-0073 §2 read literally: "a person who may already create hubs may also mark an
  existing hub they own private". `false` needs an `OWNER` membership on the hub itself. A role held
  only at the workspace counts for neither, so the creator of a hub owns it only if granted `OWNER`
  there. The change is `container.policies_updated` with `private` in the `changeSet`. A person
  without `STRUCTURE` gets a private hub by creating a new one (D2). Decided by ADR-0073 §2, the
  coordinator's review of 2026-10-10. Rejected: "creator or `OWNER`" or'ed with `STRUCTURE` (the
  first draft — wider than the ADR); anybody with `STRUCTURE` (one administrator could take a shared
  hub away from everybody).
- [x] D4 **Automation.** Rule matching (`MatchRules.covers`) keeps an event of a private hub only for
  a rule whose `run_as` reaches the hub (`access.Permits` for `run_as`, `READ`), so no condition
  reads and no action sends its content; asked again when the run starts. Decided by ADR-0073 §1.
- [x] D5 **Webhooks and trigger polling** carry an event of a private hub only when the
  subscription's creator (for a poll, the caller) reaches the hub, through `access.Permits`.
  Decided by worker, accepted by the coordinator on 2026-10-10. Rejected: dropping every private
  hub's events (a member could not connect their own hub, P-08); delivering them all (an
  administrator would read titles through a subscription). The installation's message bus
  (`integration/BusFanOut.go`) publishes every event as today: it is the operator's
  infrastructure, as the database is (*Where it ends*, "not encryption").
- [x] D6 **Notifications ask the recipient's reach.** Every recorder of a notification about an
  entry drops a recipient who cannot read it (`access.CanSee`), as `FireReminders` already does:
  comment, assignment, member added, retention warning. Decided by worker: the mail may carry the
  title (`include_title`).
- [x] D7 **No group inside a private hub.** A group's members are changed by whoever holds
  `MANAGE_MEMBERS` at the workspace, so a group granted on a private hub would be a door the
  administrators hold the key to. Granting a group a role on a private hub or below is refused
  (`memberships.group_in_private_hub`, 422); marking a hub private while a group holds a role on it
  or below is refused (`containers.private_hub_has_groups`, 409). Both lock the hub row. Decided by
  worker, accepted by the coordinator on 2026-10-10: it only refuses something on a private hub,
  which did not exist before, so nothing existing changes behaviour; written into identity.md beside
  the private-hub rule (step 16), not only here. It keeps check 2 as written. Rejected: ignoring
  group grants under a private hub (a grant
  stored that does nothing).
- [x] D8 **Turning private revokes on devices.** Marking a hub private writes `ACCESS_REVOKED` for
  every account that read it and no longer does (`Revocations.AfterHubMadePrivate`, asked of the
  request-time resolution), in the same transaction. Decided by worker, accepted by the coordinator;
  offline-sync.md §6 gains the case.
- [x] D9 **The last member.** A member is a non-anonymised account holding a role on the hub or below
  it (groups are excluded by D7). After `RevokeMembership`, and after an erasure anonymises or
  deletes an account (asked before the cascade), the same transaction asks whether a private hub it
  touched has no member left; if so the hub is trashed by the system with the ordinary grace
  (`container.deleted`, reason `private_hub_orphaned`, actor `SYSTEM`) and every workspace `OWNER`
  — UC-ID-16 check 6's "the owner is told" — is mailed (category `MEMBERSHIP`, reason `notification.private_hub_trashed`, the former member as
  actor, no subject, no name). The per-tenant retention pass does the same for a private hub without
  a member that a path missed. The workspace owner cannot restore it from the trash (they do not
  reach it); taking it over is PH-05's emergency access, letting it go is the purge — ADR-0073 §5.
  Decided by worker. Rejected: a new notification category (PH-05 adds one for the access;
  `MEMBERSHIP` fits this); the pass alone (a day with a hub nobody can reach).
- [x] D10 **What administrators see.** New `ListPrivateHubs` (`GET /private-hubs`): per private hub
  its id, its owners (accounts holding `OWNER` on it), counts of collections and entries, attachment
  bytes, `created_at`, and `trashed_at` and `purge_on` while trashed — no name, no description, no
  content. `MANAGE_MEMBERS` at the workspace (ADR-0073 §3: "storage, a person leaving"). The
  administration shows it as its own row under *Workspace*, present only where a private hub exists.
  Decided by worker. Rejected: rows in the quota screen (quotas are workspace numbers against
  limits); `READ_CONFIGURATION` (an auditor reads configuration, not people's hubs).
- [x] D11 **The archive carries the mark.** `ImportContainer` writes `coalesce(r.private, false)` — an
  older archive's hub is shared, as it was — in every mode; a `container` round trip is added. The
  missing `deleted_by_*` (side finding b) is fixed first, in its own commit. tenant-export.md §6
  names the field. Decided by tenant-export.md §11 (additive, format 1).
- [x] D12 **Nothing in D1.** `Workspace.private_hubs_offered` is true where private hubs are allowed
  (always until PH-05) and the workspace holds more than one `USER` account that is not anonymised;
  the web app offers *Private* only then. The server still accepts `private: true` in a one-person
  workspace (harmless; a screen's choice does not narrow the API). Decided by worker (P-05, P-10).
- [x] D13 **Side finding a.** A collection rule's path is `ContainerScopes` of its collection
  (tenant, hub, collection); test first, own commit. Decided by domain-model.md §3.2.
- [x] D14 **The gate.** (1) `test/architecture`: `service.EffectiveRole`, `service.Allows` and
  `Memberships.Along` are called only inside `core/application/service/access` (the workspace-only
  read of `identity/TwoStep.go:224` moves there too). (2) `test/security/private_hub_test.go`: one
  table, one row per reader — every catalogued read over containers, entries, comments, activity,
  attachments, members, views, trash, search, query, suggestions, duplicates, the retention
  preview; the calendar feed; sync snapshot and stream; rule matching; webhook delivery and polling;
  notifications — each run as a workspace `ADMIN` without a role on the hub (absent or not found),
  as a hub member (present) and as another workspace's owner (not found), against PostgreSQL as the
  app role. (3) An architecture test: every catalogued reading use case of the work, media,
  suggestion, lifecycle, identity (memberships) and integration packages is a row of that table or on
  an exemption list with its reason, like `test/architecture/activity_test.go`. Decided by worker
  (the task's "a gate test lists them").
- [x] D15 **Rolling update.** Migration 0123 adds `container.private boolean NOT NULL DEFAULT false`
  with `CHECK (NOT private OR type = 'HUB')` — metadata only, safe beside the old binary (0122 is
  taken by the fix of #1232 on its branch, checked with the remote branches on 2026-10-10). During a
  rolling update an old pod still lets workspace-level roles read a private hub created or marked
  on a new pod, for the minutes of the rollout; no private hub exists before the release, so the
  window concerns only hubs made private during the rollout. Single-pod deployments have no window.
  Written in the migration's comment and in the pull request's *Impact*; the release notes are
  generated from the pull request titles (`release.yml`, `generate_release_notes`), so there is no
  upgrade-notes file to carry it. Decided by worker, accepted by the coordinator on 2026-10-10.
  Rejected: writing the flag one release after the column (a release's delay for minutes of exposure
  an operator avoids by rolling one replica).
- [x] D16 **Codes.** New: `containers.private_only_hubs`, `containers.private_hub_has_groups`,
  `memberships.group_in_private_hub`, `notification.private_hub_trashed`, and the `app.*` texts of
  the dialog, the confirmation and the administration's list. `en` always; `de` for every `app.*`
  text and the three refusals (their families are translated). Decided by worker.
- [x] D17 **Beside PH-05 and the other lanes.** PH-05 builds the emergency access into D1's
  resolution (an open access counts as a membership on the hub for its hour) and the setting into
  `private_hubs_offered` and D2's check; neither is made harder here. The migration number is taken
  from `origin/main` right before the file is written. Decided by worker.
- [x] D18 **The audit trail stays whole.** An administrator reading the trail sees acts in a private
  hub as every act — actor, action, target id, never a name or content (rule 10, audit.md §4).
  Decided by audit.md §5 (the trail is the workspace's evidence); written into audit.md.

Nothing is open for the owner: ADR-0073 decided the shape, and D2–D18 change no *Goal*, *How to
check* or *Where it ends*.
