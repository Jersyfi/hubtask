## 3. Decisions

- [x] D1 **One use case renews.** `IssueStartPassword`, `POST /accounts/{accountId}:issue-start-password`,
  input `account_id`, `step_up_token`. Order: authorise (`MANAGE_MEMBERS` at the workspace), refuse
  a rule's act, read the account and refuse one that is not managed (`409 accounts.not_managed`) -
  **before** the step-up is demanded, so a refused target does not burn the proof - then the step-up,
  then draw outside the transaction (PH-06's reasoning), then one transaction. "Managed" is
  `OnlyThePasswordReaches` (a sign-in name and no address). Decided by ADR-0074 §4; the shape by
  worker. Rejected: a flag on `PATCH /accounts/{id}` - a credential is not a field of an account.
- [x] D2 **The answer is the creation's.** `StartPasswordIssued`: `account` (with `sign_in_name`, which
  the slip prints) and `start_password`, `no-store`, the shown-once header, no `Idempotency-Key`.
  The web app reuses PH-06's `OneTimeSecret` and print slip. Decided by worker (PH-06 D4, D9).
- [x] D3 **What ends.** In the renewal's transaction: the hash replaced through a conditional update
  that also sets `password_set_at` and `start_password_at` to now (`WHERE ... sign_in_name IS NOT
  NULL AND email IS NULL`; zero rows is `409 accounts.not_managed`, the race with a confirmation);
  every session of the account (`RevokeAll`, grant sessions included); every unspent pending
  credential of the account (a new statement - a `PASSWORD` credential won with the old start
  password would otherwise set a password after the renewal). Personal access tokens stay, as a
  password change leaves them (identity.md §6): the renewal answers a forgotten password, not a
  stolen token. The second factor and the recovery codes stay (check 5). The start password goes
  into no history: it is not the person's. The attempt ledger is untouched: a guesser must not reset
  it through an administrator, and its delay ends on its own within fifteen minutes. Decided by
  worker within ADR-0074 §4.
- [x] D4 **No owner rule beyond the step-up.** An administrator may renew a managed account that holds
  `OWNER`: an administrator may already grant `OWNER` behind a step-up (`Membership.go:108`), so this
  gives no reach the grant does not, and the trail records it. Decided by worker; rejected: an
  `OWNER`-only renewal for an owner - a rule the grant itself does not have.
- [x] D5 **The renewal through MCP; refused for a rule.** As PH-06 D13: an agent's credential under
  `members:write` receives the start password; a rule's run reads no answer, so
  `403 accounts.managed_needs_a_person`. Decided by worker (PH-06 D13).
- [x] D6 **The pending address lives on the pending credential.** `RequestAddress` writes an
  `auth_pending` row, purpose `ADDRESS`, holding the address, its token minted at delivery (the
  reset's discipline: the queue's payload carries the row's identifier, never the address or a
  token), expiring after 24 hours - a family checks mail less often than a reset waits; a new
  request spends the earlier ones. Nothing changes on the account until the confirmation. The row is
  swept after expiry; an erasure (anonymise) deletes the account's pending rows; a deletion cascades.
  Migration 0131: `auth_pending.address text` (at most 254), `token_hash` without `NOT NULL` (an
  `ADDRESS` row waits for its mail), the purpose check widened by `ADDRESS`, and
  `(purpose = 'ADDRESS') = (address IS NOT NULL)`. The data catalogue gains the row. Decided by
  worker; rejected: `account.pending_email` - an address nobody confirmed would sit on the account
  with no end.
- [x] D7 **A bound on mail to a typed address.** A managed person types any address; ten minutes
  between two requests for one account (`429 accounts.address_requested_recently`,
  `retry_after_seconds`), read from the newest `ADDRESS` row in the writing statement, and the
  queue's dedupe per account. The mail names the workspace and says to ignore it if unexpected.
  Decided by worker (T-18's neighbour: a mail cannon).
- [x] D8 **Nothing is told at the request.** An address another account already holds is accepted
  and mailed like any; the confirmation answers `409 accounts.address_taken` to whoever holds the
  mailbox - their own fact. Otherwise a managed person could probe which addresses have accounts
  here, which `AccountSummary` deliberately withholds. Decided by worker.
- [x] D9 **`AccountSummary.managed`.** True for a sign-in name and no address, computed on the server
  from the row; the People view offers *New start password* and *Add an address* exactly where it is
  true and the viewer holds `MANAGE_MEMBERS` at the workspace (P-05). Answered to every member, who
  already learn as much from `has_address`. Decided by worker; rejected: deriving it from
  `has_address` - an anonymised account has no address either.
- [x] D10 **Finding #1274: the refusal names the account's kind.** `PasswordViolation` carries the
  code of its sentence: for `context_words`, `auth.password_rule.context_words_name` where the
  context has a sign-in name and no address, `context_words` otherwise; the rule id stays
  `context_words` (`/auth/password:check` answers ids, and the client already picks the sentence).
  Test first, own commit; closed from this pull request. Decided by worker.
- [x] D11 **Outside this task.** Changing the address of an account that has one (no route exists
  for anybody; not asked by UC-ID-20); removing a sign-in name after the upgrade ("the sign-in name
  stays", ADR-0074 §6); `hubctl` commands (#1267). Decided by worker.
- [x] D12 **The confirmation is public and proves the mailbox only.** `POST /auth/address:confirm`,
  `token`; the link `<base>/confirm-address#token=…` (fragment, removed from history, identity.md
  §14.4); it signs nobody in. One refusal for unknown, spent, expired, superseded and foreign links;
  the route sits in the auth routes' rate-limit bucket, as the reset's completion does, and records
  no failure (`Reset.go` counts none: a 32-byte token is not guessed). The confirming write is conditional on the
  account still being managed and not anonymised; the address is stored as confirmed and is then
  the account's for reset and notifications. Decided by worker within ADR-0074 §6.
- [ ] O1 **Adding an address where the password is switched off** - waiting on the owner: a decision
  issue the coordinator opens. *The new fact:* milestone PH Decision 11 (#1268) refuses the password,
  once proved, to an account found by name that **holds an address**. So in a workspace whose
  methods leave the password out, confirming an address takes the person's only way in: from then on
  the password is refused, and a provider admits them only if it knows that address (identity.md
  §11's connect link needs the provider to vouch for the same address). *Example:* a D4 company
  signs in through its directory only; Jonas, a warehouse worker, has a managed account; he adds his
  private address, confirms it, and the next morning he cannot sign in - the directory does not know
  his private address, and the administrator can no longer renew (the account is not managed any
  more). *Proposal (a):* refuse adding an address while the resolved methods leave the password out
  (`409 accounts.address_needs_password`), the action absent on *People* and the profile with that
  reason; a managed account there stays managed and keeps its password door (Decision 11). Effect:
  users in such a workspace cannot upgrade (they lose nothing); administrators see why; operators
  unaffected; D4 only, D2/D3/D5/D6 unchanged. *Alternatives:* (b) allow it and warn on the
  confirmation screen that the password stops working here - a locked-out person whose only way
  back is removal and a new account (P-16); (c) keep the password door for every account with a
  sign-in name, address or not - changes Decision 11. *Question:* may a managed account add an
  address in a workspace whose methods leave the password out - (a) no, (b) yes with a warning, or
  (c) yes, and its sign-in name keeps the password? *What waits:* step 5's branch for this case and
  its row in § 2(b); every other step proceeds.
