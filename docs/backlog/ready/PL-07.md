## 3. Decisions

- [x] D1 What the events are and what they carry — decided by: multi-tenancy.md §4.3 and UC-INS-14
  checks 2 and 3 (the owner, #1551); worker for the shape: `data.workspace` = `{id,
  external_reference, status, plan, version}` on every event, plus `previous_plan`, `purge_after`,
  `quota` and `limit`, `budget` and `day`, `export_id` where the event has one. No slug, display name
  or account: a slug is often a family's name (rule 10). A cancelled deletion is an event of its own:
  the status leaves `PENDING_DELETION`, and a receiver keeping the newest state must learn it.
- [x] D2 The order: an event's number is drawn from a sequence while its transaction holds an
  installation-wide transaction-level advisory lock, taken just before the event row is written, so
  a later number can never commit before an earlier one; the feed reads numbers after the cursor
  — decided by: worker. Rejected: the outbox's time horizon (it guesses a lag and loses an event
  whose transaction outlives it); transaction ids with `pg_snapshot_xmin` (a dump restored into a new
  cluster restarts them, and every cursor would skip what follows). Cost: transactions that write an
  event serialise from that write to their commit — control-plane changes, a crossing, an owner
  change, a finished export; a deadlock between two of them is the database's to break and fails
  one change, which its caller repeats. The cursor carries the last event's moment, so the 410 is
  decided without a read. multi-tenancy.md §4.3 is corrected to say this.
- [x] D3 The window is 30 days, a cursor older than it answers 410; the purge sets the reference to
  `null` in the workspace's kept events and the `deleted` event carries none — decided by:
  multi-tenancy.md §4.3 ("removed at the purge") for the reference; worker for the 30 days: long
  enough for a platform down over a holiday, short enough not to keep identifiers longer than the
  deliveries already do. The platform knows the workspace's id from provisioning. Not a deviation:
  the reference leaves with the workspace, as the data catalogue says.
- [x] D4 The version is `tenant.version` as the change leaves it; an event that changes nothing on
  the row (owner, limit, budget, export) carries the version as it stands; `deleted` carries the
  last version + 1 — decided by: worker; UC-INS-14 check 2 asks for a version that only grows so a
  receiver keeps the newest *state*, and the row's version is that state's. Raising the row for an
  event that is not its state would refuse a platform's move in flight with `version_conflict`
  where nothing it moves has changed.
- [x] D5 Single mode writes no event and offers no use case — decided by: UC-INS-14 check 7.
- [x] D6 "Limit reached" is written after the refused transaction ends, in a transaction of its
  own on a detached context bounded by its own timeout, once until a create of that quota is
  admitted again (a `quota_reached` row; the admitted path reads whether one exists and removes it
  only then) — decided by: worker. The refusal's own transaction rolls the write back (known trap);
  a second transaction beside it can wait on a lock the first holds; an event at the admitted path's
  exact wall never fires for storage. The work is held in the context, as `access.HoldRefusals`
  holds a refusal, and run by the postgres unit of work when its outermost transaction ends
  (`persistence.Afterwards`, a helper beside the port, not a method on it: no fake changes); without
  a holder — a test's fake — it runs at once. The quotas are the four capacity quotas; PL-04's
  people limit emits it when it is checked through the same `check`.
- [x] D7 "AI budget spent": after the increment the metering reads the day's total, and when that
  reaches the budget, `quota_reached` for the budget and the day is inserted (`ON CONFLICT DO
  NOTHING`) and the event written only if the insert took — once the metering's transaction has
  ended, in a transaction of its own (`persistence.After`), so an answered AI call stays metered
  whatever becomes of telling it — decided by: worker; two meterings at once cross it once through
  the unique row, and `Meter.Add`, which PL-08 changes at the same time, keeps its signature.
- [x] D8 An owner changed is an OWNER grant or revocation at the workspace scope, direct or through
  a group (`GrantMembership`, `RevokeMembership`, `UpdateGroup`, `DeleteGroup`) — decided by: worker.
  An erasure that takes an owner's memberships writes none: an erasure is the person's right and
  goes with the last-owner rule that already refuses it for the last owner; the platform reads the
  workspace if it needs more. A restore writes none (D13).
- [x] D9 An installation subscription takes every installation event (no type list, filter or
  scope), is `ACTIVE` or `PAUSED`, never `DISABLED`; its dead letters are counted from the delivery
  rows, so the count, the screen and A-21 agree with what can be redelivered, for the deliveries'
  30 days; no consecutive-failure counter (nothing would read it); the secret rotates as a
  workspace subscription's does; no test send (a redelivery is the deliberate send) — decided by:
  multi-tenancy.md §4.3 (never switched off); worker for the rest.
- [x] D10 Deliveries are rows written in the event's transaction for each active subscription and
  queued as installation jobs (no tenant), so a delivery leaves within the job wake-up of the commit
  — decided by: worker; the outbox dispatcher is per workspace, and an installation dispatcher would
  be a second hop for the same rows. A finished export writes its event in a transaction it opens
  after the archive is written, keyed by the export (`dedupe_key`, unique), so a repeated job writes
  it once.
- [x] D11 The instance file declares `platform_subscriptions: [{target_url, secret_file}]`; a
  changed secret file rotates — decided by: worker; the file keeps no credential, and `seed`/
  `enforce` behave as for plans.
- [x] D12 The operator is told by A-21 (`HubtaskPlatformDeadLetters`, a ticket, its runbook) over
  the gauge of waiting dead letters, and on the screen — decided by: the task text ("an alert"); a
  counter's `increase()` would resolve while dead letters still wait; no product notice to
  operators exists, and building one is not this task's.
- [x] D13 A restore writes no event: a restore in place keeps the archive's version, and a restore
  into a new workspace (`NEW_TENANT`) is not told as `created` — decided by: worker; a restore is the
  operator's recovery, the platform re-reads the workspace after it, and telling it is the backup
  area's change: the `finding` issue #1583 names both.
- [x] D14 A subscription's create, target change and rotation demand a step-up — decided by:
  worker, as an installation backup target does: every workspace's reference goes to that address.
  Removal and pause do not: they send less.

No question on the owner's list is decided here: nothing is renamed or removed in the contract, no
dependency is added, no retention safeguard or security gate changes, the reference leaves at the
purge as the documents say, and nothing deletes user data (the sweep removes events and deliveries
after 30 days, which § 2(c) 13 and the data catalogue state).
