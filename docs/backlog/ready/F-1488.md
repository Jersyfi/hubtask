## 3. Decisions

- [x] D1 Read past, as the trash pass does: each phase pages with `skip` until it holds a batch it
  can act on, or a page comes back short. What it reads past: a legal hold, a non-matching
  condition, an entry only the loosest cutoff caught (phase one, chains); a hold or a retained
  descendant (phase two) — decided by: worker; #1468's shape. Rejected: a persistent cursor per
  kind (a migration and state to keep right for a problem paging solves).
- [x] D2 No read budget per pass. A tenant with many old entries a condition excludes pays for
  reading them on every pass — and for one entry read per candidate where the condition names
  `item` — but a budget would bring the starvation back past it, and removing what is past its
  period is the duty (§5 "Completeness"); the trash pass made the same choice — decided by: worker.
  Rejected: a budget of N batches (bounded cost, unbounded starvation behind N × batch).
- [x] D3 `Matched` keeps counting every row read that matched its rule; rows read past for a hold or
  a descendant are `Held` (F-1479), so a pass that read to the end with less than a batch to act on
  is `Exhausted` — decided by: worker.
- [x] D5 The deadline bounds the read-past. A pass runs inside the job's deadline
  (`HUBTASK_JOB_TIMEOUT`, 60 s by default, `presentation/worker/Runner.go`), and the pages are read
  under it (rule 7). A pass the deadline stops mid-read fails and rolls back; the next one starts at
  skip 0, so a workspace whose prefix of rows the pass cannot act on takes longer than the deadline
  to read is starved again. **Measured** (Testcontainers, 10,000 entries, this machine): held by a
  legal hold, 316 ms per 1,000 as first built — an update per held row — and after step 6, 106 ms
  on the first pass and 74 ms on later ones (about 800,000 held entries per 60 s); excluded by a
  condition naming `item`, 210–300 ms per 1,000, one entry read per candidate (about
  200,000–280,000 per 60 s). The second is within reach of a large, long-lived workspace, so it is
  finding #1497 (read a page's entries in one statement; a cursor across passes), not built here —
  decided by: worker, on the review's condition.
- [x] D8 The blocks of a page are written in one statement per rule and reason, and a row that
  already names its block is not written again (`BlockItemsForRetention` gains an
  `IS DISTINCT FROM` guard): reading past held rows on every pass must not cost a row version per
  held entry per pass — decided by: worker, from D5's measurement.
- [x] D6 The cost is visible: a counter `hubtask_retention_read_total{data_kind}` counts every row a
  pass read, beside `…_deleted_total` and `…_blocked_total`, so read against deleted shows what the
  read-past costs. The label is the closed set of data kinds; no identifier and no user content
  (rule 10, observability-reliability.md §3.2) — decided by: worker, on the review's condition.
- [x] D7 The preview keeps reading the first page: its count is `CountDue` over everything due,
  and its samples are the oldest due entries, held ones among them. data-retention.md §5's preview
  line says so, so the samples are not read as "everything due" — decided by: worker.
- [x] D4 data-retention.md §5 says, beside "1,000 objects per transaction", that a pass reads past
  what it cannot act on to reach a full batch — decided by: worker; a statement of what the system
  does, no rule changes.
