## 3. Decisions

- [x] D1 Count and re-seal rather than only document the wait — decided by: worker. The issue offers
  three ways; counting makes the census true (P-11, check 1) and re-sealing makes step 4 reachable
  without waiting up to the ladder's length (check 2). Rejected: documenting the wait (it is what
  §8.1 says today and leaves both checks unmet).
- [x] D2 A store of its own, `automation_http_job`, with the words "header secrets of pending HTTP
  calls" — decided by: worker. The operator must be able to tell a value that will drain by itself
  from one a rule keeps; counting it as `automation_rule` would be a wrong statement for a direct
  call. A new enum value in a response is compatible (api-guidelines.md §1 item 2).
- [x] D3 The purpose is checked against the two shapes a job can legitimately carry and rewrapped
  under the one it names: the request's — exactly `automation.http:<the payload's request_id>`, any
  other id skipped — or a rule's, `automation.rule.http:<a valid id>`, the id taken from the stored
  purpose itself because the payload names no rule. Anything else is skipped and counted, and so are
  the envelope's refusals `crypto.not_authentic` and `crypto.ciphertext_malformed` besides
  `crypto.unknown_key`, because the document may be caller-shaped (§ 1) — decided by: worker. What
  protects the value is that the purpose is bound into the encryption: a rewrap under a purpose the
  ciphertext was not sealed for fails, so the shape check narrows what the round attempts and widens
  nothing. Rejected: failing the round on those refusals (one member's malformed call would stop the
  workspace's rotation until the job dead-letters).
- [x] D4 Only `PENDING` and `RUNNING` jobs — decided by: worker, from § 1: no other state is ever run
  again. Rejected: counting dead letters (they would hold the census above zero for ever).
- [x] D5 The statements live in `db/queries/Sealing.sql` (census branch) and `db/queries/Job.sql`
  (list and rewrap), the port `CallSealings` beside `RuleSealings` in
  `core/application/repository/automation`, implemented by the job repository; the re-sealer
  `CallResealer` in `core/application/service/automation` beside `RuleResealer`, run after it in the
  round — decided by: worker. The service owning the purpose re-seals (sealing package comment).
- [x] D6 Documents: security.md §8.1 (the wait sentence goes; "What a round touches" names the
  pending call), the sealing package comments and `Sealing.sql`'s header, the contract's
  description — decided by: worker. No ADR: ADR-0045 already decided that every sealed place is
  counted and re-sealed; this adds the place it missed.
- [x] D7 That a caller can hand a sealed document into a direct call or a rule is a separate
  finding, reported to the coordinator rather than fixed here — decided by: worker. Refusing the
  input changes what an API caller may send (a contract question of its own) and is not needed for
  the census or the round to be right, which D3 makes robust against it.
