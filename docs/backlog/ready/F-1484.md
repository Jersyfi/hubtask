## 1. Premise — what is true today

| Claim | True? | Evidence |
|---|---|---|

## 3. Decisions

- [ ] O1 **Does one rule's failing condition stop only that rule, or the whole pass?** — waiting on
  the owner (a deviation from data-retention.md §2's rule; AGENTS.md, "What you do not decide
  yourself"). Proposal: *only that rule, for this pass*. The rule's entries are left as they are —
  neither announced nor removed, which is still "not defaulting either way" — and every other rule,
  phase two of entries already marked, and the trash go on. Today one rule with
  `item.labels[0] == 'x'` and one unlabelled entry stops every deletion in the workspace, the trash
  included, until somebody edits the rule; under the proposal it stops only itself. D1–D7 alike (one
  engine). Alternative: keep "stops the pass" and only surface it (O2) — honest, and one bad rule
  still blocks the workspace's whole deletion duty.
- [ ] O2 **What does an administrator see of a rule that failed?** — waiting on the owner (a change
  to what an administrator observes; a new check for UC-LIF-04). Proposal: the rule carries
  `last_failure: {code, at}` (`RetentionPolicy`, additive; read-only), set by the pass that failed and
  cleared by the next pass that evaluates the rule without failing; the retention screen shows it on
  the rule with the code's sentence; UC-LIF-04 gains the check "a rule whose condition fails is shown
  as failing, with the reason, and the other rules go on". Storage: two columns on the rule, a
  forward-only migration, written in its own transaction so the failure outlives the pass's rollback.
  Alternatives: a notification to the rule's `notify` recipients (a new notification kind — larger,
  and a rule that fails hourly would need its own throttle); the operator's alert only (today).

  and is noted for F-1471's record readers there — decided by: worker; a wrong statement, not a
