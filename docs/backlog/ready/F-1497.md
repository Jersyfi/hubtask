## 3. Decisions

- [x] D1 Both parts of the issue. Part 1: a page's entries are read in one statement, the first
  time a condition on that page asks for `item` (`Items.FindMany`, the same columns as `Find`), and
  each candidate's condition reads its entry from that page. Part 2: a cursor per reader across
  passes. Part 1 alone only moves the size at which a workspace starves (about ×2); part 2 alone
  ends the starvation at any size - decided by: worker; the issue's proposal.
- [x] D2 A read budget per reader and pass, counted in rows: 10 × the batch (10,000 by default).
  A reader stops at a full batch, the end of its rows, or its budget, whichever comes first, and
  stores where it stopped. Without the budget a cursor would roll back with the deadline and help
  nothing. Rows, not time: deterministic, testable with the fake `Marking`, and no clock reading in
  the loop (rule 4); worst measured case 3 s per reader, with three readers plus one per chained
  rule well inside 60 s - decided by: worker. Rejected: a budget from `ctx.Deadline()` (adapts to
  the operator's setting, but a fake clock does not advance while a test reads, and a slow database
  page would still overrun); F-1488's D2 rejected a budget only because without a cursor it brought
  the starvation back - the cursor removes that reason, and data-retention.md §5 will say so.
- [x] D3 The cursor is a row of a new table `retention_cursor` (tenant, reader, last anchor, last
  identifier), the reader being phase one of a kind, a chain's second stage (by rule, removed with
  the rule by `ON DELETE CASCADE`) or phase two. Keyset rather than `OFFSET`: `(anchor, id) >
  (after_at, after_id)` on the order the statements already use, so a page costs a page, and an
  entry marked or removed between passes moves no position. No foreign key to `work_item`: a
  cursor is a position, and a removed entry must not remove it. A tenant table like any other:
  `tenant_id`, row level security with `FORCE` and the `tenant_isolation` policy, no exception
  entry, and a cross-tenant negative test. It holds identifiers and a moment only, never user
  content (rule 10) - decided by: worker; the tenant shape by the review. Rejected:
  columns on `retention_run` (a log, read for the last successful run - mixes bookkeeping with
  state) and the job's payload (`queue.Result` cannot rewrite a payload).
- [x] D4 Reaching the end of the rows clears the cursor. A pass is `Exhausted` only if no reader
  stopped at its budget and every reader that reached the end had begun at the start; otherwise the
  job comes back after `Continuation` (5 s). So a full cycle over the workspace's rows runs back to
  back, and then the hourly interval applies - a workspace of permanently held entries is read once
  an hour, in budget-sized passes, as F-1488 reads it today in one - decided by: worker. Rejected:
  wrapping inside the same pass (a second leg `(anchor, id) <= cursor`; more code for 5 s).
- [x] D5 The position is the last row the reader judged, not the last row on the page: a reader that
  stops at a full batch mid-page leaves the rest of the page for the next pass - decided by: worker.
- [x] D6 The preview (`RetentionRules.assess`) reads from the start and never moves a cursor: it
  answers the oldest due entries, as data-retention.md §5 says - decided by: worker; unchanged
  behaviour.
- [x] D7 The trash pass keeps its `OFFSET` read-past: it reads past a hold or the offline window
  only, with no entry read, about 800,000 rows per deadline (F-1488 D5) - a workspace with that many
  held entries in its trash is not in sight. data-retention.md §5 states the bound; a cursor for it
  is a follow-up the day it is not - decided by: worker. Rejected: the same cursor for the trash in
  this task (a second shape of reader and its tests for a case nobody has).
- [x] D8 No index on the anchors in this task. Keyset removes `OFFSET`'s re-reading; step 6
  measures the page cost at 10,000 and 100,000 entries, and if a page is still a scan that grows with
  the workspace, an index on `work_item (tenant_id, <anchor>, id)` is a `finding` issue (an index on
  the largest table, built `CONCURRENTLY`, is its own review). The measurement is written into
  this record (§ 4 step 6) and into data-retention.md §5's bound, not only into a finding -
  decided by: worker; where it is written by the review.
- [x] D9 data-retention.md §5 says: each reader reads at most a budget per pass and continues where
  the last pass stopped; every due entry is reached within ceil(N / budget) passes; the trash pass's
  bound (D7). data-protection.md's table gains `retention_cursor` (no content, goes with the
  tenant, not in an archive) - decided by: worker; statements of what the system does.
