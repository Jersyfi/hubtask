## 3. Decisions

- [x] D1 The rule — decided by: owner, 2026-10-07, #1174 option B → `identity.md` §18, milestone SC
  Decision 10.
- [x] D2 "Locked to providers" is a lock on the methods whose value leaves out the password (`[OIDC]`)
  — decided by: worker, from `identity.md` §18, which names the two cases apart: locked *with the
  password among them* opens the password everywhere; locked *to providers* mandates. A lock with
  `[PASSWORD, OIDC]` mandates nothing: an operator who keeps the password everywhere has not asked
  for single sign-on everywhere. Rejected: any lock that contains `OIDC` — it would switch a
  provider on in workspaces whose people sign in by password today, unasked. One sentence in §18.
- [x] D3 Read, never written — decided by: worker, as every other offer reading (§17.1 "no job
  runs", ADR-0076 §2). `offeredHere` gains the mandate; the workspace's own switch is left as it
  is, so lifting the lock returns each workspace to its own choice at once. Where that leaves no
  way in, the fallback opens (§17.1). Rejected: writing the switch into every workspace — a job, a
  second truth, and a lift that could not be undone. One sentence in §18.
- [x] D4 One reading for every door — decided by: worker. The readers that today take the
  workspace's settings take a small value read in the same transaction (the settings and whether
  the installation's methods are locked to providers), from one helper; the instance level is read
  in the ambient transaction (`instance_setting` has no policy). The predicate lives in the domain:
  `EffectivePolicy.LockedToProviders()` and `IdentityProvider.MandatedHere(lockedToProviders)`
  (installation row, `INVITED_ONLY`). Rejected: one more argument per caller computed separately
  — nine readers, nine chances to drift.
- [x] D5 The count and the removal under the mandate — decided by: worker. Migration **0133**
  replaces `count_provider_offers`: a mandated row counts every live workspace. So the operator's
  list, *Withdraw now*'s confirmation and the removal guard stay true by construction, in the
  statement that writes (known trap: read-then-write). The SQL predicate repeats the domain's
  (`sign_in.methods` locked, `?'OIDC'`, not `?'PASSWORD'`; the row `tenant_id IS NULL`,
  `provisioning = 'INVITED_ONLY'`); an integration test holds both to the same table of lock
  shapes. Rejected: overriding the count in the service — the removal guard is in SQL and would
  still delete every connection of a mandated provider no workspace switched on.
- [x] D6 The workspace screen keeps the switch, on and disabled with "Set by the installation" —
  decided by: worker. The task says "removes the workspace's switch"; UC-ID-12 checks 4 and 6 say
  a locked rule shows its value and cannot be changed, and every way in has its switch. A disabled
  switch with its reason is both (and is how every other locked rule is drawn). Not a change to
  what a person observes in the check (UC-INS-11 check 4: "shows it as set by the installation").
- [x] D7 The field — decided by: worker. `installation_lock` (`TURNS_ON` / `LEAVES_TO_WORKSPACE` /
  `NONE`) on installation rows of both projections, absent on a workspace's own row. One enum rather
  than a boolean, because the operator's screen must say which applies to *every* row (check 4) and
  the client must not re-derive the lock rule (P-05). `NONE` for an ended offer.
- [x] D8 The refusal — decided by: worker. `identity_provider.mandated`, 422 (`ErrValidation`, as
  `auth.policy_locked`), with `origin`. A new code rather than `auth.policy_locked`: that one
  points at a field of the sign-in policy, this one at a provider. `offered=true` on a mandated row
  is accepted and stored (the workspace's own choice, kept when the lock lifts).
- [x] D9 No audit entry per workspace when the mandate takes effect — decided by: worker. The lock
  is journalled where it is set; a per-workspace entry would need a job (D3).
- [x] D10 Side finding, not this task: `anotherWayIn` reads the workspace's own methods
  (`onlyProviderMethods`, `IdentityProviderOffer.go:213-224`), not the resolved ones; under an
  installation lock to providers it counts a password that is not a way in. The fallback catches
  what it lets through, so nobody is locked out. Confirmed with a test at the build, then a
  `finding` issue.

Nothing here is on the owner's list: no rename or removal in the contract, no new dependency, no
deletion of user data (D5 *prevents* one), no change to a use case's Goal, check or end.
