## 3. Decisions

- [x] D1 The door is a row level security policy, not a definer function. `installation_targets ON
  backup_target FOR ALL USING (tenant_id IS NULL AND current_tenant_id() IS NULL) WITH CHECK (…)`
  follows `ai_provider`/`identity_provider`. The operator writes in `SystemScope` and reads in
  `InstallationScope`. A session with a tenant set still sees only its own rows, so the workspace's
  reads list none. — decided by: worker, after the 0129 precedent. #1494 is about definer functions
  owned by the table owner, which this does not use. Rejected: a `SECURITY DEFINER` reader (it would
  wait on #1494, and a policy is the narrower thing); a download (UC-BAK-07 *Where it ends*: "no
  direct HTTP download").
- [x] D2 The export's opener is its own: `admin.TenantExportArchivist` gets an `InstallationTargets`
  opener. It tries the workspace's target first and the installation's second. `StoreOpener.OpenTarget`
  stays tenant-only, so the DSR export, the audit archive and anchoring cannot reach an installation
  target. — decided by: worker, from the premise row on the shared opener.
- [x] D3 The export checks its target when it is accepted (exists in the workspace's or the
  installation's scope, enabled), so a wrong id is a 404 and not a failed job. — decided by: worker.
  It is a correction of `Export.go`, and what the operator observes in check 1 does not change.
- [x] D4 Installation targets are managed under `/admin/backup-targets` (list, create, test, remove;
  no update, as the workspace's targets have none beyond enable/disable — kept to the same shape).
  Token scope `admin:tenants`, and the operator register through `InstanceWriter.authorize`. Create
  and remove demand a fresh step-up (`step_up_token`, the `X-Hubtask-Step-Up` header), declared on
  their descriptors and added to the privileged list (`stepup_test.go`, identity.md §16.3): a storage
  credential every workspace's export may be written with is a privileged write.
  Same kinds, same validation, same sealing, through `backup.Writer`'s validation reused with the
  installation as owner. Audit: `instance.backup_target_configured` / `_removed` in the instance
  journal, kind and configuration, never the credential. — decided by: worker, the `InstanceAi` shape.
- [x] D5 No configuration-file mode for installation targets (unlike AI providers). — decided by:
  worker. Nothing asks for it, and an `enforce` file is a second writer the screen must then refuse.
  If wanted later, it is a task of its own.
- [x] D6 The instance area gets a *Backup targets* screen and the export form a picker. — decided by:
  worker, P-08 (the operator's other installation settings each have their screen). The UI is
  shown to the owner on the draft.
- [x] D7 Allowed in single mode too. — decided by: worker. There the owner is the operator, and the
  workspace's own targets stay the default. Written as a line in backup-restore.md §2.
- [x] D8 Nothing waits on the owner.
