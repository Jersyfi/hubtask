## 3. Decisions

- [x] D1 The ceiling is the existing one, unchanged: the use case reads the strongest role the
  target holds and asks `Authorize` again with `Grants` set to it, on the workspace's path.
  `MayGrant` then decides, `recordRefusal` records, the answer is `access.role_above_own` — no
  second mechanism. — decided by: owner (#1462) and the coordinator's brief; worker for the shape.
- [x] D2 **"The actor's own role" is the actor's role on the workspace, and "every role the account
  holds" is every role anywhere in the workspace, a hub's and a private hub's included.** A new way
  in is a credential to the whole account, which reaches every scope it holds at once, and the four
  doors are permitted by `MANAGE_MEMBERS` on the workspace — so the comparison is made where the
  door's own permission is asked. Measuring per membership along its own path (as a grant is) was
  rejected: a private hub's path discounts the workspace's roles, so a workspace owner would be
  refused for any member of a private hub, against "an owner issues one for anybody"; and a hub's
  owner who administers the workspace would gain a way into an account whose other roles the
  measurement then never meets. — decided by: worker, the decision's wording ("at or below the
  actor's own on the ladder of domain-model.md §3.2"); a code comment says it.
- [x] D3 Mail mode of `RenewInvitation` is unchanged: the mail reaches the invited address and not
  the actor, so it hands the actor no way in — the decision names "link mode". — decided by: owner (#1462).
- [x] D4 Order in each door: the permission as today, then the read (account and roles), the
  existing state refusals (`accounts.not_managed`, `accounts.not_invited`, not a service account),
  then the ceiling, then the step-up. An identifier that names no account, or one of another
  workspace, still answers not found before any ceiling. — decided by: worker; the brief's "before
  any step-up", and a refusal that says "not managed" for an account with an address stays the
  more useful answer. One exception, found while building: `RequestAddress` decides "not managed"
  under the account's row lock inside its writing transaction, after which a refusal could not be
  recorded, so there the ceiling comes before it — an administrator asking an address for an
  owner's ordinary account hears `access.role_above_own` rather than `accounts.not_managed`. An
  identifier of nobody holds no role and still answers not found.
- [x] D5 The race in §2 is accepted, as the grant doors accept theirs. — decided by: worker.
- [x] D6 T-25 in security.md names only the grant doors; no note is added there (the brief: only if
  the table names the doors). — decided by: coordinator's brief.
- [x] D7 One new read port, `repository.HeldRoles.HeldAnywhere(ctx, accountID) ([]identity.Role,
  error)`, separate from `Memberships` so that the authoriser's hot-path interface and its fakes do
  not grow. Implemented by `postgres.MembershipRepository`, one sqlc query (`SELECT DISTINCT role`
  over the account's and its groups' memberships). The strongest role is picked in the domain
  (`identity.Strongest`). — decided by: worker.
- [x] D8 The web app's controls (P-05) are part of this task, not a follow-up, since the server's
  change makes them offer what it refuses. — decided by: worker.
- [x] D9 Nothing waits on the owner.
