## 3. Decisions

- [x] D1 **"Without mail" is `features.mail` false, one predicate for both.** The composition root
  passes `Config.Mail.Host != ""` to `InviteAccount` and `RenewInvitation` and the manifest reads the
  same expression (a method on `environment.MailConfig`). A configured server that is down is not
  "without mail": the mail waits and retries, `/meta/health` says so. Decided by worker; rejected:
  letting the inviter choose link or mail where mail exists — the use case offers the link "where the
  installation has no mail configured", and a credential answered where it is not needed is one more
  copy of it.
- [x] D2 **Without mail the token is minted in the invitation's transaction and no mail job is
  queued.** Reusing `MintRedemptionToken` (nested `Within`), composing `<base>/redeem#token=…` with
  the same `BaseURL` the mail uses, so the link is the mailed one byte for byte in form. Queuing the
  job anyway would re-mint at every delivery attempt and kill the handed-over link (§ 1). If SMTP is
  configured later, nothing is mailed for these invitations; the link stays valid for its fortnight.
  Decided by worker; rejected: answering the bare token for the client to compose — a REST or MCP
  caller would have to know the route, and a client origin may differ from the base the mail names.
- [x] D3 **An automation run cannot invite or renew without mail**:
  `403 accounts.invitation_needs_a_person`, PH-06 D13's reasoning (a run reads no answer). With mail a
  run invites as today. Decided by worker, following PH-06 D13.
- [x] D4 **A new link for an invitation not accepted: `POST /accounts/{accountId}:renew-invitation`,
  use case `RenewInvitation`.** Without mail it mints and answers a new link once (the old one dies at
  once); with mail it queues the invitation mail again. Only an `INVITED` account; `MANAGE_MEMBERS` at
  the workspace; audit `account.invitation_renewed`, NOTICE. Needed by check 5 itself: a link shown
  once and lost, or run out, would leave the address taken for good — re-inviting answers `409`, no
  route removes an account, and the card already tells the person to "ask for a new invitation".
  Decided by worker; rejected: answering the link again on demand (not "shown once"), and re-inviting
  an `INVITED` address in place (check 6 asks for the opposite). The coordinator may split it into its
  own pull request of this task; the steps keep it separate (step 3).
- [x] D5 **Check 6 names the two cases.** An address of an account that is here answers
  `accounts.email_taken` as today; one with an invitation not yet accepted answers
  `accounts.already_invited` — "That address was invited already and has not accepted yet. Give them
  a new invitation link from the list." / "…Send the invitation again from the list." (the client
  picks by `features.mail`). Same status `409` and params, so a client that knew only `email_taken`
  still sees a conflict. Decided by worker.
- [x] D6 **The trail says how the invitation went out**: `account.invited` gains the open field
  `delivery` (`MAIL` or `LINK`); the renewal records the same field. Never the link. Decided by worker.
- [x] D7 **The web app shows the link in `OneTimeSecret`**, with acknowledgement before dismissal, as
  the start password; the grant that follows the invitation no longer hides the link when it fails.
  The hint without mail: "No mail goes out from here. You get a link to hand over yourself — by any
  messenger. It works once, for fourteen days." Where managed accounts are allowed, nothing more: their
  form sits right below. Decided by worker.
- [x] D8 **Message codes**: `en` always; `de` for `accounts.*` and `app.people.*`, both families
  already translated there. Decided by the template's rule.

Nothing here is on the owner's list: no field renamed or removed, no new dependency, no use case's
*Goal*/*How to check*/*Where it ends* changed, nothing from a released milestone's `Delivers` added.
