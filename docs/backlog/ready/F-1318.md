## 3. Decisions

- [x] D1 Hand every request to a job; the lookup, the verification, the trail entry and the mail job
  move into it — decided by: the finding's proposal (#1318), approved for this sweep. The handler is
  not detached: like `InvitationMessage` it writes the entry and enqueues the send in the runner's
  transaction, so they commit together exactly once — the guarantee `h.queue` gave inside the
  request. Rejected: a decoy (an equal-cost dummy write for an unknown address — the cost of a
  write cannot be made equal with confidence, and a test cannot prove it without a clock).
- [x] D2 The address travels sealed under the installation's master key (`Encryptor`, already in
  `SessionWriter`), purpose `password_reset.address:<tenant>`; the payload holds the envelope and
  the request identifier, never the address in clear — decided by: worker. The payload today is
  "identifiers only" so that no address sits in the queue table or a log line; sealing keeps that
  promise for the one value that cannot be an identifier (the account is not known yet). Precedent:
  the automation call's sealed secret. Rejected: the clear address (it would sit in the job table
  for 7 days); a hash (nothing can be looked up by it).
- [x] D3 The data catalogue gains a row for the request job: the address, sealed, kept with the job
  row 7 days after completion, `RETENTION` — decided by: worker. Not a change to a retention
  safeguard: the store, its period and its deletion path exist; this names one more value in it.
  Rejected for now: purging the payload when the job completes (a new queue method and query for a
  sealed value; can follow if the owner wants it shorter).
- [x] D4 The new kind is `identity.password_reset_request`, no dedupe key — decided by: worker. A
  dedupe needs a key derived from the address, which is the value being protected; the auth rate
  bucket sheds a burst before the use case, and the mail job still dedupes per account. Rolling
  update: a process of the previous release has no handler for the kind and returns the job to the
  queue (`Runner`), so nothing is lost.
- [x] D5 The request's trail entry keeps the request's identifier: the job copies `request_id` from
  the payload into the context it records under, so check 7's entry still names the request that
  asked — decided by: worker.
- [x] D6 Documents: identity.md's reset table (the request's work is the same for every address),
  `Reset.go` and `queue.Port` comments, the data catalogue (D3). No ADR: ADR-0068 §6 already decided
  "a job behind one answer"; this puts the lookup behind it too — decided by: worker.

## 4. Proof and steps

UC-ID-04 check 1 (the request's work): a unit test drives `ForgetPassword.Execute` for a held
address, a provider-only one, a disabled one and an unknown one with recording fakes of every port
the request touches (accounts, unit of work, encryptor, queue, audit) and asserts the four traces
are identical — the same calls, in the same order, the same job kind and payload keys — and that
no account was read and nothing audited at the request. This is the proof the finding asks for
without a wall clock: equal work by construction, not by timing. It fails on `main` (the held
address reads the account, audits and enqueues a mail job).
The job's decisions (who gets a mail, who gets an entry): unit tests through `RecordResetRequest`.
Check 7 on the stored rows: `test/integration/reset_tokens_test.go` drives the request, then the
request job inside a real transaction (Testcontainers), and reads `audit_log`.
