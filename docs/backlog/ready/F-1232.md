## 3. Decisions

- [x] D1 Option (a): a deleted comment keeps its text under a hold, reads as deleted, the sweep
  clears it after the last covering hold — decided by: owner, 2026-10-10, #1246 → data-retention.md
  §4, UC-LIF-06 check 9, milestone-PH.md Decision 8.
- [x] D2 The deletion decides at once: it reads the holds (under the shared lock) and clears the
  text in the same statement when no hold covers the comment; only held text waits for the sweep —
  decided by: worker. Keeping every deleted text until the next pass would hold removed words for
  hours without a hold (domain-model.md §3.5: no removed text retained). Rejected: always keep,
  always let the sweep clear.
- [x] D3 The text never leaves the database through a read: `FindComment` and `ListComments` answer
  `''` for a deleted row, so the domain's invariant (`Body` empty exactly when deleted) holds and no
  door can serve it — decided by: worker. Rejected: masking in the repository mapper (a second
  query added later would forget it) or in each door.
- [x] D4 Coverage is `Holds.Blocking` with the comment's entry as the target — containers, the
  entry's path, the entry's contributors — the target a purge of that entry would use. A comment
  falls with its entry, so whatever would keep the entry keeps its comments' text — decided by:
  data-retention.md §4 ("on an item, the item and what hangs off it"; an account hold covers what
  they contributed) and `LegalHold.go` Target.
- [x] D5 The archive carries the stored row, held text included (backup and the access export
  alike) — decided by: worker. A backup is the stored state, and `NEW_TENANT` (forensics) takes the
  holds along and should take what they keep; an Art. 15 export owes the author the text still
  stored about them. "Reads as deleted to everybody" governs the product's reading paths (D3).
  Rejected: stripping it from the archive — a restored copy would carry the hold and lose what it
  keeps. **The coordinator should look at this one**: if it counts as changing what a person
  observes, it goes to the owner.
- [x] D6 A merge with `overwrite` that rewrites a held tombstone is a restore's edit (check 6), not a
  deletion; restore modes are unchanged. After a restore, the next pass clears any kept text no hold
  covers, so a restored text never outlives its holds — decided by: worker.
- [x] D7 Migration 0122 (free on every remote branch on 2026-10-10): a partial index
  `comment (tenant_id, id) WHERE deleted_at IS NOT NULL AND body <> ''`, built `CONCURRENTLY`, so a
  pass reads the few kept texts instead of every comment of the workspace. Expand-only — decided by:
  worker.
- [x] D8 The pass reports the cleared texts as removed under the data kind `COMMENT` (metric
  `RetentionDeleted`, the pass outcome); a text still held is not counted as matched, so the job
  does not come straight back while a hold stands (the inbox's reasoning, `RunRetention.go:723-728`).
  No audit entry per text: `comment.deleted` already recorded the act, and the clearing is the
  hold's end, which `lifecycle.hold_released` records — decided by: worker. The data catalogue's
  `comment` row names the hold and the sweep; data-retention.md §3's `COMMENT` row stays (no rule
  may target comments).
