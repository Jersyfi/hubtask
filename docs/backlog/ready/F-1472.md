## 3. Decisions

- [x] D1 Nesting is bounded by CEL's own `ParserRecursionLimit`, set to 64 (`port.MaxDepth`), not by
  a scan of the text before the parser: the parser already counts depth the way the checker
  experiences it, and a hand scan would count something else. As the parser counts: a sum of n
  terms is n deep, n parentheses n+1, a chain of n maps n+1; `&&`/`||` chains are balanced and
  shallow (151 `&&` terms are 2 deep). Measured on this machine, worst accepted shape (the map
  chain): depth 64 → 50–94 ms, depth 91 → 256 ms, depth 99 → 339 ms, depth 121 → 598 ms. Depth 100
  would spend a third of the deadline per compile, and the run paths compile on every run, so 64 —
  ten times the deepest expression the repository ships (6) — decided by: worker. Rejected: 100
  (340 ms per compile, too near the deadline under load), 32 (refuses a sum of 33 terms for no
  measurable gain), keeping 250 (3.7 s). A stored condition deeper than 64 stops compiling and is
  listed by UC-AUT-08; none is expected — it took seconds to save.
- [x] D2 The deadline is the adapter's own, `port.CompileTimeout`: `Compile` runs parse, check and
  `Program` in `concurrency.Go` and waits for it or the deadline, whichever comes first. The port's
  signature does not gain a context — decided by: worker. Rejected: `Compile(ctx, …)` across the
  15 call sites — the checker cannot be interrupted, so a caller's context would only end the wait
  sooner, which the adapter's own deadline already does. **After the deadline the compiling
  goroutine keeps running until the checker finishes; D1 is what bounds that cost** (the parser
  refuses past depth 64 before the checker starts) — the deadline is the backstop, not the guard;
  said in the code comment at the wait and in `port.CompileTimeout`'s comment. The goroutine runs
  through `core/shared/concurrency.Go`, the function of `SafeGo.go` and the only place a `go`
  statement may appear (rule 5; `make gate-architecture` green).
- [x] D3 `CompileTimeout` is 1 s: a backstop, not the bound — ten or more times the worst accepted
  compile measured, because the run paths compile on every run and a deadline near the real cost
  would refuse legitimate rules under load — decided by: worker.
- [x] D4 A refusal by depth, by CEL's node count, or by the deadline answers
  `expression.too_complex` (VALIDATION, no position), not `expression.syntax`: the expression may be
  perfectly well formed, and "not a valid expression" sends its author to look for a typo —
  decided by: worker; the same reasoning as F-1471.
- [x] D5 The limit is written into automation.md §1.2's table ("Nesting depth · 64 · checked by the
  parser; compiling has a 1 s deadline"), where the other three limits are — decided by: worker;
  implementing rule 7, not a deviation from a rule.

## 4. Proof and steps

Proof, in `infrastructure/expression/CEL_test.go` against the real CEL compiler:
the pathological input (240 `.map`) is refused `expression.too_complex` in under 500 ms; the limit's
edges, so that the figures above are held by a test and not by this text — a sum of 64 terms
compiles and 65 is refused, a sum of 40 compiles, 63 parentheses compile and 64 are refused, 30 maps
compile and 64 are refused, 151 `&&` terms compile. The accepted chain is not 63 long and no compile
time is asserted: `gate-unit` runs under the race detector, where 63 maps take 605 ms (measured in
the first `verify-pr` run, which failed on a 500 ms assertion) against 90 ms without it; the time of
the worst accepted shape is this record's measurement (D1), not a test's;
with the deadline set to zero (a package variable, in `CEL_internal_test.go`) a 60 `.map` chain is
refused `too_complex`. The fuzz target gains the input as a seed and a fifth
property — one compile ends within twice `CompileTimeout` — so the nightly fuzz holds the bound.
`make gate-architecture` holds the code to `locales/en.json`.
