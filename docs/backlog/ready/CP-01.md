## 3. Decisions

- [x] D1 **A salt per archive**, drawn at write time and carried only in its manifest; the reader
  derives each archive's key from that archive's manifest (`archive.Keys`, a key per archive id,
  replaces the one key `Records` and `Medium` take) — decided by: worker, after review finding 1;
  backup-restore.md §4 says "bound to the target through a random salt the target is given when it
  is created", and is corrected in this task to "a random salt each archive is given when it is
  written", since nothing reads the salt before the manifest (§ 1). Nobody observes the difference — every
  promise of §4 holds, and two archives of one target no longer share a key either — and the pull
  request names the sentence's change so the owner sees it. Rejected: a salt per target in
  the database — a migration, a backfill, a rolling-update case for targets without one, and the
  database row the rule exists to make unnecessary.
- [x] D2 The salt goes into HKDF's salt parameter; the info stays the purpose
  `backup_target.archive` — decided by: worker. The port's `DeriveFromMaster` and
  `ReproduceFromMaster` gain the salt; `Envelope.derive`'s comment is rewritten; a nil salt keeps
  today's derivation for old archives. Rejected: the salt inside the purpose string.
- [x] D3 No migration — follows from D1.
- [x] D4 The manifest field is `encryption.archive_salt` (base64); `encryption.salt` keeps its
  passphrase meaning — decided by: worker; one field for two derivations is how a reader picks the
  wrong one.
- [x] D5 **Old archives keep opening**: a manifest without `archive_salt` is read with the old
  derivation under the target the restore names, exactly as today; only that case keeps
  `backup.restore_foreign_archive_encrypted` — decided by: worker; versioning-release.md (an archive
  of an earlier version stays readable).
- [x] D6 A foreign encrypted archive with a salt is accepted by `NEW_TENANT` when its key id is in
  the ring and the key opens its first member; refused `backup.archive_key_unknown` otherwise —
  decided by: UC-BAK-04 check 4 ("a new installation given the kept key material … restores an
  encrypted one"; after the loss, that workspace is one the new installation does not hold), and
  check 5. Authorisation is unchanged: only the operator's `NEW_TENANT` takes such an archive.
- [x] D7 `backup.archive_key_required` stops being a person's refusal: a reader asked to decrypt
  without a key is an internal error — decided by: UC-BAK-04 check 5.
- [x] D8 Archives enter the census as the store `backup_archive`, counted from successful, unexpired
  runs' manifests; re-seal skips them and they drain by expiry, as `automation_http_job` drains with
  its jobs; security.md §8.1 says that a key then stays in the ring as long as archives written under
  it are kept — yearly generations included — decided by: worker, security.md §8.1 ("remove k1 only
  at zero"). Archives this installation did not write are not counted; it cannot know them.
- [x] D9 No ADR: backup-restore.md §4 holds the rule (corrected per D1), security.md §8.1 gains the
  eighth store.

## 4. Proof and steps

Proof:
- **Crypto:** a table test that the same master key with two salts gives two keys and the same salt
  the same key; a test that a nil salt still derives today's key.
- **Backup service:** a new archive's manifest names `archive_salt` and its key; two archives of one
  target have different keys (check 3 kept); a chain of an old full and a new incremental, and a
  chain spanning a rotation, restore.
- **Old archives:** a test that an archive written by today's code (no `archive_salt`) still
  restores from its target, and BK-4's golden archive still imports.
- **Integration (Testcontainers, real PostgreSQL, a local target):** write an encrypted archive,
  start a second installation with the same ring and an empty database, create a target over the
  same location, list the archives as the operator, restore `NEW_TENANT`, compare the content
  (check 4). With the key id removed from the ring: `backup.archive_key_unknown` naming it (check 5);
  with another ring using the same id: the same code with `does_not_open`; nothing written.
- **Census:** a repository test that a successful run's key is counted under `backup_archive` and an
  expired one not; the health report warns for a key out of the ring that archives still name
  (check 6).

## 5. Review

Attacked on 2026-10-15 by the coordinator (a separate agent, no part in writing it), given this
record, the task and the repository. Findings and what changed:

1. *Why a salt per target in the database rather than per archive in its manifest?* Nothing needs
   the salt before the manifest is read (§ 1, the row "Anything needs the salt…", with file:line for
   verify, expiry, listing, media and the census). D1 now chooses a salt per archive; migration 0152,
   the backfill and the rolling-update case are gone (D3). Doing so showed that a restore reads a
   whole chain under the newest archive's key (§ 1), so the reader takes a key per archive; that
   also makes a chain spanning a rotation readable. backup-restore.md §4's "the target is given" is
   corrected in step 6.
2. *Old archives.* D5 states it; the proof tests an archive written by today's code and the golden
   archive, and a mixed chain.
3. *D4 (now D6): which check, which authorisation, which refusals.* UC-BAK-04 check 4 named; the
   authorisation (`NEW_TENANT` only, `admin:tenants` on top of the role, `Restore.go:467-490`) is in
   § 1 and the matrix; the matrix gained the rows key id unknown, key id in the ring with another
   installation's material, a foreign archive in another mode, and `NEW_TENANT` without the scope.
   D8 (census) states the key's longer life in security.md §8.1.

No open point remains; the verdict is `ready`.
