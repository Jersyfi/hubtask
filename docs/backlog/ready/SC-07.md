# SC-07 — The installation's defaults, usable

**Task:** SC-07 · issue #1063 · `docs/backlog/milestone-SC.md`
**Checked against:** `origin/main` at `4eb18bb3` on 2026-10-12
**Verdict:** ready

The work, in five parts:
- **One control per kind, declared by the server.** *Installation → Defaults* draws every key of
  every area with a control of its kind, in words. The kind comes from the server, not from a list
  in the screen, so a key PH-03 adds needs no new control (D1, D2).
- **The same refusals at all three doors.** The screen, `hubctl admin settings` and the file all
  go through the use case. The use case, not the REST adapter, decides what a missing value means,
  and it refuses what a workspace's own write refuses (D3–D5).
- **What a workspace sees.** The workspace's screens show the installation's legal links,
  language, time zone and week start beside their own fields (D6–D8).
- **The overview's operator count**, right on an empty register and with a plural.
- **The accessibility statement.** It is set on this screen. The health report names a
  multi-tenant installation that has none (D9).

No migration is needed (D7).

**(d) Standing rules and traps.**
* Rule 8: every word is a client message code. The server declares kinds and options as values,
  never as labels.
* Rule 11: contract first (step 1).
* Rule 15: no literal values.
* Rule 2: the kind and bounds are a declaration, and the use case still refuses.
* Rule 4: no clock, nothing random.
* Rule 7: the health source keeps `healthReadTimeout`.
* P-05: `workspace_may` is absent where no lock is possible. The lock switch is offered only for

* P-06: every value says where it came from.
* P-10: a private installation that decided nothing shows no "installation's default" line and

* Traps that apply:

## 3. Decisions

- [x] D1 **The server declares each key's kind.** `InstanceSetting` gains read-only fields:
  * `kind`: `COUNT`, `FLAG`, `CHOICE`, `CHOICES`, `LINK`, `LOCALE` or `TIME_ZONE`.
  * `options`: for `CHOICE` and `CHOICES`, the closed set ordered from loosest to strictest.
  * `minimum` and `maximum`: for `COUNT`, the product's bounds. Where it applies, `0` means off or
    unlimited.
  * `workspace_may`: `TIGHTEN`, `RAISE` or `REPLACE`. It is absent for localisation, which is never
    locked.

  The domain owns each declaration beside its switch: `identity` for sign-in, legal and
  localisation; `integration` for AI; the quota names in `quota`. A Go test holds that every key
  `ReadInstanceSettings` answers has a kind, and that a `CHOICE` key has options. This is the
  screen comment's own rule ("the screen keeps no list of its own") and ADR-0070 decision 8 ("the
  server's answer, never the screen's guess"). A third AI key — PH-03's `person_opt_out`, a
  `CHOICE` of `[OFFERED]` — then needs only its declaration and its words.
  Decided by the worker. Rejected: a kind table in the client. The bug in check 2 is exactly a
  client guessing the kind, and PH-03 would have to add a row in two places.
- [x] D2 **One control per kind, in a component of the screen's own.** `InstanceValueField.svelte`
  sits under `apps/webapp/src/lib/instance/` and is built from the controls SC-06 uses:
  * `COUNT` → `Input type="number"` with `min` and `max`. Empty means undecided.
  * `FLAG` → a `Select` of *Not decided / On / Off*. A switch cannot say "not decided".
  * `CHOICE` → a `Select` with an empty "Not decided" option first.
  * `CHOICES` → one checkbox per option, inside a fieldset.
  * `LINK` → `Input type="url"`.
  * `LOCALE` → the manifest's `supported_locales`.
  * `TIME_ZONE` → `zoneOptions`, as `WorkspaceSettingsView` does.

  Each row has a label in words (`app.instance.key.<area>.<name>`) and its values in words
  (`app.instance.value.<area>.<name>.<VALUE>`). The lock is a `Select` "Workspaces may: make it
  stricter / not change it", worded by `workspace_may`:
  * `TIGHTEN` → *make it stricter* / *not change it*.
  * `RAISE` → *go higher* / *not go higher*.
  * `REPLACE` → *use their own* / *not change it*.

  Localisation has none. The lock is offered only for a decided value; its reason is
  `disabledReason`. Rows are grouped by area with an `h2`, as on *Sign-in*. The screen and the
  navigation are called *Defaults*, the story's name. A refusal lands at its row through the
  field path (D4).
  Decided by the worker (P-06, check 1, check 3, the story). Rejected:
  * Lifting SC-06's snippets into the design system: they read a workspace's three-level
    `Setting`, not an installation entry. Two callers with different shapes is not one component.
  * A lock `Switch`: it cannot carry two kind-specific words.
- [x] D3 **"No value" means undecided, in the use case, for every area.** `instanceLevelFrom`
  treats an entry with an absent or `null` value as undecided before reading its kind.
  `instanceSettingMap` passes every entry through unchanged. Today the adapter makes this
  decision, which presentation/AGENTS.md forbids ("a value travels to the use case as it
  arrived"), and the file door disagrees with it (§ 1). Decided by the worker (rule 2, check 6).
- [x] D4 **The installation's write refuses what a workspace's write refuses, by kind.**
  * A `COUNT` must be a whole number ≥ 0. A string, a fraction or a negative is refused.
  * Bounds clamp on read, as they do for a workspace: `bounded` is unchanged.
  * `LOCALE` and `TIME_ZONE` go through `ValidDefaultLocale` and `ValidDefaultTimeZone`.
  * Every refusal names its own area: the param is `<area>.<name>` and the path `/<area>/<name>`.

  Decided by the worker: this is a correction of an inconsistency, not a change of a rule. A value
  this tightening refuses that is already stored still reads, through the adapter's tolerant read.
  Only new writes meet it.
- [x] D5 **hubctl types the word by the key's declared kind.** It reads the level first anyway.
  * `COUNT`: a whole number is sent as a number; anything else is sent as the word, so the server
    refuses it exactly as it refuses the file.
  * `FLAG`: `true`/`false`.
  * `CHOICES`: a comma list.
  * Any other kind: the word.

  A key the read did not answer is a usage error, naming `admin settings show`. Today the comma
  guess turns a link with a comma into a list. Decided by the worker (check 6). The acceptance
  test is one table of `(key, word)` driven through hubctl's typing plus the REST registry, and
  through `InstanceLevelOf`, asserting the same code.
- [x] D6 **The installation's language and time zone are what a new workspace starts with.** That
  is the Goal's own wording. They are not a level read on every request:
  * `ProvisionTenant` and the first-start `Setup` take them when the command names none, before
    the `en`/`UTC` fallback in `NewTenant`.
  * `GET /tenant` answers `installation_defaults: {locale?, time_zone?, week_start?}` with only
    what the installation decided.
  * The workspace's screen shows "The installation's default: …" under each field.
  * The anonymous chain's installation link stays `HUBTASK_DEFAULT_LOCALE` (i18n-l10n.md §2, which
    gains one sentence naming both).

  Decided by the worker. Rejected: resolving the workspace's locale on read. That needs
  `tenant.default_locale` nullable — an expand/contract over every reader of a `NOT NULL` column —
  for no check.
- [x] D7 **The week start gets a workspace level, and one vocabulary.**
  * The workspace's own is a key in `tenant.settings` (`localisation.week_start`), beside SC-11's
    `ai.sources`. That key is already archived, exported and restored, so there is **no migration**
    and no change to the import query.
  * `PATCH /tenant` takes `default_week_start` (`MONDAY`, `SATURDAY`, `SUNDAY` or `null`).
  * The chain is the account → the workspace → the installation → the locale's day → Monday
    (`AuthenticateToken.weekStart`, i18n-l10n.md §2 and §4).
  * The installation's `week_start` takes the same three words. A stored or sent 1, 6 or 7 is read
    as that day. 2–5 have no meaning at any other level and are refused on write.

  Decided by the worker. Check 4 says a week start is a default and never a lock, and
  multi-tenancy.md §4.1 says a workspace may differ from a default. Without a workspace level, the
  installation's day could not be differed from — a lock by another name. Rejected:
  * Only showing the installation's day: it is a lock in effect.
  * A `tenant` column: a migration plus the archive and import queries, for one optional
    setting.
- [x] D8 **The operator count.** The overview reads the register:
  * Empty, with the caller through it (one workspace): `digest_operators_sole` — "You run this
    installation because it has one workspace".
  * Otherwise: `digest_operators` as `{count, plural, one {# account may run this installation}
    other {# accounts may run this installation}}`.
  * The stale `later_ai` row goes, because SC-11 built it.

  Decided by: UC-INS-12 check 2's own words.
- [x] D9 **The health hint.** `config.accessibility_statement_missing`, severity `info`, from a
  warning source registered beside `RegisterWarnings`. It holds when the tenancy mode is `multi`
  (D5, D6) and the installation's `accessibility_url` is empty. It names the screen
  (`/instance/settings`) and `hubctl admin settings set legal.accessibility_url`. It is never shown
  in single mode (D1–D4, D7 single). A level it cannot read gives no hint, and the reason is
  logged: the hint is advice, not a fault. Decided by the milestone text and design-system.md §10.
  Its severity is `info`, because an installation may lawfully owe no statement (UC-ID-18
  *Where it ends*).
- [x] D10 **Two operators saving at once** stays last-writer-wins on a whole `PUT`, as today.
  Neither the use case nor this task promises more. Changing it needs a version on the level — a
  contract change no check asks for. Decided by the worker. Raised as a `finding`, not built.
- [x] D11 **The journal names localisation and quota keys** (`localisation.<name>`,
  `quotas.<name>`), never their values. UC-INS-12 check 3 says "default and lock changes". It is a
  finding outside `Delivers`, fixed on this branch with its own commit and test (AGENTS.md).
- [x] D12 **PH-03 coordination.** The coordinator merges the two; the one that lands second
  adapts.
  * If PH-03 lands first: its `aiChoices` row moves into a domain declaration (`CHOICE`,
    `[OFFERED]`).
  * If this task lands first: PH-03 replaces its row by the declaration and adds two words. The Go
    test of D1 fails until it does.

  Decided by the coordinator's brief.

None is on the owner's list:
* No field is renamed or removed; every field is additive.
* No *How to check* or *Goal* changes.
* No dependency, licence, security gate or deletion.
