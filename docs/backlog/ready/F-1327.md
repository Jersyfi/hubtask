## 3. Decisions

- [x] D1 Redemption is a sign-in for the rule — decided by: owner, 2026-10-13 → identity.md §8,
  §12; UC-ID-03 check 8.
- [x] D2 The redemption commits (account `ACTIVE`, password set, terms stored, token spent) before
  the challenge is minted, like the reset — decided by: worker. A person who closes the tab during
  setup can sign in with the password they chose and meets `ENROLL` there; holding the account
  `INVITED` until setup would need a second pending state and leave a spent token with nothing to
  show for it. Rejected: activating only at `:confirm`. Accepted consequence: the session that
  opens at `:confirm` records its method as *Password and second factor*, so no session records the
  invitation; the trail still holds `auth.invitation_redeemed`.
- [x] D3 The challenge is minted with an empty candidate, so `PASSWORD_CHANGE` cannot follow the
  password the rule just accepted — decided by: `Reset.go` `answer`, the same reasoning.
- [x] D4 The `202` carries the invited address (`email`), for the card's identity line — decided by:
  worker, as the reset's step does (UC-ID-04 check 5); the token proved the mailbox.
- [x] D5 The contract change is a `202` beside the `201`, the `MfaChallenge` schema reused —
  decided by: worker; additive, nothing renamed or removed (AGENTS.md's owner list does not reach
  it). `api-guidelines.md` counts "changing semantics" as breaking, and a caller that got `201`
  under the rule now gets `202` (the Python SDK's `redeem_invitation` is typed `-> SessionTokens`):
  the semantics are the owner's decision (D1), and `signIn` and `resetPassword` already answer a
  `202` under the same typing, so a client of the sign-in family already meets it. Clients: the
  generated SDKs gain the response; the web app is the one client of this route.
- [x] D6 D2's home: identity.md §12 gains one sentence — the redemption commits before the step,
  so a person who leaves setup signs in with the password they set and meets `ENROLL` there.
