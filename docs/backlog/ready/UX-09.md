## 3. Decisions

- [x] D1 The rule — decided by: owner, #1619–#1622 → `domain-model.md` §2, ADR-0087.
- [x] B1 The cut — decided by: coordinator, 2026-10-21, #1670 (S1, S2): UX-29 takes the entry side (former D5, D7, D8; UC-WRK-24/3; `items.level_hidden`; `WorkItem.hidden`); UX-10 and UX-11 depend on UX-29; the lock writer is here.
- [x] D2 **Layers and inheritance.** Per setting: collection → hub → workspace → installation → Hubtask's default. A layer stores values (B3); `preset` on it is provenance only. A layer value is a default for the layers below, bounded only by the installation (N2) — a collection may switch dates on under a hub without them; only a lock binds. **Creation** (B2): a collection created with its hub's preset, or none, stores no values and follows its hub; with another preset it stores a copy. A hub created without a preset takes a copy of the workspace's default preset, if one is set; the default applies to hubs only. **Choosing a preset on a layer replaces that layer's own values** with the preset's. Existing containers have no layer and answer today's behaviour. — decided by: coordinator (B2, B3) and worker.
- [x] D3 **Storage.** Container layer: `container.policies.structure`, except the collection's completion, which *is* `policies.completion_policy` (B4) — one store per value; a hub's completion lives in its layer. Workspace layer, locks and default preset: `tenant.settings.structure`, written under `tenant.version`. Hubtask's four presets are build data in `core/domain/model/work/Presets.go`, never rows (B5): no table, no exception to the security gates, nothing for the archive to exclude. Installation, workspace and person presets arrive with UX-28 and UX-27 in a tenant-scoped table with `FORCE`. — decided by: coordinator (B4, B5) and worker.
- [x] D4 **The bound and the domain rules** (`core/domain/model/work/Structure.go`). The bound is the system profile ∩ the in-force profile (S3): `item_capability_profile`'s tenant rows stay the installation-side bound; `settings.structure` is where a workspace narrows from now on. Every stored value and lock is clipped to the bound when resolved, never an error on read (the installation may narrow after a collection stored `DUE_DATE`). *Levels*: ordered offered types, closed top-down — a root always; any other type only when at least one of its system parents is offered (`ACTIVITY` has two, S12); a name per level, trimmed, NFC, 1–60 code points. *Fields*: per offered type an object `{capabilities: [...]}` (S8, room for field definitions), within the bound, `COMPLETION` mandatory. Widening is refused `capability_not_supported` / `structure.widens`. — decided by: worker.
- [x] D5 **Locks** (S4). Only the workspace writes one now (`WORKSPACE`, with `locked_by`); `INSTANCE` and `PLAN` arrive with their writers. A lock key is a setting (`views`) or, inside fields, a type and capability (`fields.TASK.DUE_DATE` — the story's "dates always on"). Shape: `locks: {"<key>": {"origin": "WORKSPACE", "locked_by": "<id>"}}` on reads; a write sends `locks: ["<key>", …]`, the whole set. A locked value applies below; a lower layer's differing value is ignored when resolving and refused when written explicitly (`structure.setting_locked`); a preset choice under a lock is accepted with the locked setting kept and named in `kept_by_lock`. Sources reuse the contract's vocabulary: `PolicySource` + `HUB`, `COLLECTION`; `PolicyLock` + `WORKSPACE` (S2). — decided by: coordinator (S2, S4) and worker; the shape of `identity.Effective`.
- [x] D6 **The eight settings and what is enforced now.** Enforced by the server here: *completion* (the roll-up, D11). *Levels* and *fields* are validated, stored and served; entries obey them with UX-29. **Stored and served only**, applied by later tasks: *views* (`{offered, default}`; the server never interprets a layout; UX-10), *what counts* (`OPEN|FIELD_SUM|DUE|RHYTHM|PROGRESS|FLOW|NONE` + field key; UX-24), *capture* (`LINES|AMOUNT|DATE|PERSON|LABEL`; UX-14, UX-12), *celebration* (`ALL|SUBTLE`; UX-25), *automation* (a closed set with no value yet — every value is refused; UX-26 adds `DONE_COLUMN_COMPLETES`, N3). Hubtask's default for an existing container is today's behaviour: every type and capability of the bound, views all four with `LIST_COLLAPSED` first, counts `NONE`, completion `MANUAL`, capture `DATE, PERSON, LABEL`, celebration `ALL`, automation none (S9). The contract says per setting that clients apply it. — decided by: worker; UC-WRK-23/2 needs all eight to exist.
- [x] D9 **Hubtask's four presets** (S9). *List*: levels `[TASK]`; fields `COMPLETION, HISTORY, CUSTOM_FIELDS` — no date, person, label, note editor or child (UC-WRK-23/4 wins over the concept sketch); views `LIST_COLLAPSED`; counts `OPEN`; `MANUAL`; capture `LINES, AMOUNT`; `SUBTLE`. *Tasks*: levels `[TASK, ACTIVITY]`, clipped to `[TASK]` until UX-08 lands (S12); task fields all but `MEMBERS, BUCKET, COVER`; activity as the bound; views `LIST_COLLAPSED, LIST_EXPANDED`; counts `DUE`; `MANUAL`; capture `DATE, PERSON, LABEL`; `ALL`. *Project*: the bound; all four views, `LIST_EXPANDED` first; counts `PROGRESS`; `ROLLUP`; capture `DATE, PERSON, LABEL`; `ALL`. *Flow*: levels `[TASK]`; task fields as the bound; views `KANBAN, LIST_COLLAPSED`, `KANBAN` first; counts `FLOW`; `MANUAL`; capture `DATE, PERSON, LABEL`; `ALL`. Automation none on all four. Notes for UX-12: grouping by category needs `LABELS` or a field switched on, and "amount" needs a field definition (the `fields` object leaves room, S8) — UX-12 decides. — decided by: worker.
- [x] D10 **Writes and races.** `PATCH …/structure` takes `{preset?, settings?, reset?: [setting…]}` with `If-Match` (ETag = the container's or the tenant's version, N5); `reset` is the real reset — a list, never a `null` (S1); hubctl `--reset <setting>`. Values are resolved and logged (S5): a container's effective structure is computed by the server and travels as one field; the client resolves nothing. Ordering: a container write takes its hub row and the tenant row `FOR SHARE` before reading their layers; a hub write updates its row (and so waits for, and is waited on by, its collections' writers) before reading its collections' layers; a workspace write takes the tenant row `FOR UPDATE`. So every fan-out reads the layers it computes from after the competing writer committed. The fan-out (N6): one upsert per inheriting container, at most 1,000 in one transaction; above that the write advances the workspace's sync epoch instead, and devices take a fresh snapshot (`offline-sync.md` §8, as a restore does). A replica pulled before this change holds containers without `structure`; a client seeing `features.structure` and such a record takes a fresh snapshot once (UX-10). A migration that ever narrows the installation profile advances every workspace's epoch (rule in §8). — decided by: coordinator (S1, S5, N5, N6) and worker.
- [x] D11 **The roll-up reads the effective completion** — `CompleteWorkItem.go:204`: the collection's own `completion_policy`, else the hub's, the workspace's, `MANUAL`. `PUT /policies` keeps its documented semantics (B4). — decided by: coordinator (B4).
- [x] D12 **Templates are defined against the installation topology** — `NewHierarchy(rows, system)` in `Template.go` and `InstantiateTemplate.go`. Independent of the rest of this task: nothing here narrows an in-force list; the need arises with UX-29's per-collection in-force lists (N8). — decided by: worker; `Hierarchy.go:45-58`.
- [x] D13 **Events and audit** (S6). A container layer change publishes `container.policies_updated` with `change_set.structure.<setting>: {from, to}` (snake_case); level names are included in `levels`' values — the event reaches only subscribers who may read the container (`ReadScope`), who read its name already; rule 10 covers logs, metrics, traces and audit, where they are hashed.
