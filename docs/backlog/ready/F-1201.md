## 3. Decisions

- [x] D1 Not a credential, so nothing to keep out: the five sources are enum codes recorded `OPEN`
  — decided by: the alert's flow (§ 1). Renaming the sources so CodeQL's name heuristic stops
  matching would hide the alert without fixing the guessable fingerprint, and dismissing it is not
  allowed (security gate, AGENTS.md); both rejected.
- [x] D2 The key is a pepper derived from `HUBTASK_SECRET_KEY` under its own purpose label
  (`hubtask/audit-fingerprint/v1`), the construction security.md §8 already uses for token
  storage — decided by: worker. It is mandatory on every installation, lives outside the database
  (a dump alone cannot be guessed against), and never rotates silently (changing it already ends
  every session and token). Rejected: a key derived from the master keyring — optional, empty by
  default, so the default installation would record no fingerprint at all, and a rotation would
  split comparability at every turn; a per-workspace random key stored in the database — a new
  table, a new kind for UC-INS-16 to count and re-seal, and readable beside the trail in a dump.
- [x] D3 The fingerprint is `hmac-sha256:` + hex(HMAC-SHA-256(pepper, tenant id ‖ 0x00 ‖ value)),
  the value canonicalised by `fmt.Sprint` as today — decided by: worker. The tenant binding keeps
  one workspace's values from matching another's (provider operation, exports side by side); the
  prefix tells a keyed fingerprint from an entry stored before this change, so an auditor never
  reads two different schemes as two different values. The field is not bound in (comparing a
  value across fields stays possible, as today). The `to_hash`/`from_hash` names stay (no rename,
  AGENTS.md); `AuditFieldChange`'s description says what the value is.
- [x] D4 Stored entries are never rewritten, and they keep verifying — decided by: audit.md §3
  (immutability) and the chain's design: verification recomputes the chain over the stored strings
  and never a fingerprint. Consequence, named so it does not surprise: a fingerprint written before
  this change (bare hex) and one written after it (prefixed) are not comparable even for the same
  value; old fingerprints stay as guessable as they were until their partition's period ends
  (audit.md §3, retention). That is the price of an immutable trail, not a choice this fix can
  avoid. What an auditor observes, stated in audit.md §4 and the pull request's Impact: two
  fingerprints compare only within one workspace and one installation secret — not across this
  change, not across a change of `HUBTASK_SECRET_KEY`, not across workspaces.
- [x] D5 Where the keyed step lives: `audit.Changes` still decides the masking in core (audit.md
  §4, the port's own reasoning) but records a `SENSITIVE` value as a deferred, unexported value;
  `audit.KeyFingerprints(entry, fingerprinter)` in the port replaces each with the keyed string;
  the sink calls it before `storedShape`. The fingerprinter is a port (`audit.Fingerprinter`),
  implemented in `infrastructure/security` — decided by: worker. Rejected: handing a fingerprinter
  to each of the 116 call sites (one forgotten is one unkeyed path); a sink decorator in the
  application layer (a path built on the bare sink would skip it). A sink without a fingerprinter
  records `changed` alone — the safe direction, never an unkeyed hash — which keeps the 64 test
  constructions of the sink unchanged; production builds it with one, proved by the integration
  test that uses the production constructor. The deferred value refuses JSON
  (`audit.fingerprint_unkeyed`), so an unkeyed path fails closed rather than storing `{}`.
- [x] D6 Documents: audit.md §4 (the `SENSITIVE` row: a keyed hash), security.md §8 (a row beside
  "Token storage"), deployment.md (`HUBTASK_SECRET_KEY` also keys the trail's fingerprints, so
  changing it splits their comparability), the port's comments — decided by: worker. No ADR: the
  rule lives in audit.md §4 and the construction in security.md §8, both already decided; this
  applies them. Not a deviation from audit.md §4: the rule asks for a hash that is comparable and
  not readable, and only a keyed one is both.
- [x] D7 Proof that the alert closes is CodeQL's own run: it runs on the pull request once it is
  ready (`.github/workflows/codeql.yml`, not on a draft) and on `main` after the merge, which marks
  alert 8 fixed — decided by: worker. The CodeQL CLI is not on this machine, and downloading it is
  not this task's to do. The model reading in § 1 and the absence of alerts on the existing HMACs
  are the evidence before that run.
