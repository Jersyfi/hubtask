# UX-13 — One palette for everything

**Task:** UX-13 · issue #1645 · `docs/backlog/milestone-UX.md`
**Checked against:** `origin/main` at `5f2562f02` on 2026-10-21 (UX-08, UX-02 and UX-09 merged;
UX-09 changed no file under `apps/webapp`), the dependency UX-03 read from its branch at
`05c020c32`; rebased onto `origin/main` at `77b3c5c02`, where UX-03 (#1665) has landed, before the
first web-app step
**Verdict:** ready

The bar's search dropdown becomes the palette. It is one panel that answers what is typed with
entries, hubs, collections, places, settings pages and the actions the reader may perform. `⌘K` /
`Ctrl K` and `/` open it from every framed page, and `?` opens *Help and shortcuts*. The work is
client-only. No contract, no migration, no message reaches the server, and every permission the
palette shows is one the web app already reads from `/meta/capabilities` and the memberships. Most
of the work is **where the actions come from**. The palette computes no permission of its own: the
head of each screen already decides, by P-05, what it offers, and the palette lists exactly that
(D3). For a collection the reader only matched by name it asks the same questions through the same
functions the collection's screen asks (D4). *Ask* (UX-22) and capture's `Q` (UX-14) get seams and
nothing else (D9).

UX-03 is a dependency because the palette draws its rows from the cases of its decision 12. A role
refusal stays absent, and an item that is "not possible right now" carries a `disabledReason`,
which the palette reads as "not listed" (D3). UX-03 changes no file this task touches
(`git diff --stat origin/main...origin/ux-03-reason-never-moves` names no file under
`apps/webapp/src/lib/frame`, `lib/search`, `views/`, `PageHeader` or `Menu`). The line numbers
cited are those of `5f2562f02`; UX-03's merge moved none of them.

**(d)** Standing rules and principles.
Rules 1–12 and 14: nothing under `core/`, `presentation/`, `infrastructure/`, `api/` or `db/`
changes. Rule 13. Rule 15: the panel and the dialog use existing tokens
(`--z-popover`, `--shadow-overlay`, `--bg-surface-hover`, space steps), and `pnpm lint` holds it.
**P-05**, for every value that tells the client "this can be done now":
* a head action: listed iff the head offers it **and** it carries no `disabledReason` (D3). The
  head's own condition is the full condition, and the palette adds none and drops none.
* *New {type} in X*: `mayDo(roleOf(path(X)), 'create', false) === true` ∧ X not effectively
  archived ∧ `rootTypes().length > 0` — the three conditions of `ContainerView.svelte:183` and
  `addDisabledReason` (`:555-561`), as one exported function the screen and the palette both call
  (step 3), so they cannot drift.
* *Open X as {layout}*: the layout is reported by the manifest and drawn by this client — the
  function `LayoutSwitch` uses, exported once (step 3); a layout offered there with a reason is not
  listed here.
* settings pages and places: the frame's functions with the frame's inputs; a row the frame does
  not draw for this reader is not listed.
* a shortcut: listed in *Help and shortcuts* only where its handler is registered (`Q` until UX-14).

**P-13**: the panel is a `listbox` with `aria-activedescendant` from the field, as today, and a
`Dialog` on `compact`. Each kind of row is a `role="group"` with `aria-labelledby` its heading.
Option ids derive from the row's identity (`palette-row-<kind>-<id>`), not its index, so an
announced row is still that row when hits arrive. A row with a shortcut carries `aria-keyshortcuts`
and draws the key `aria-hidden`, so it is read once. The number of matches is said through the
existing `announcer`, never a region mounted with text. Focus returns where it was on Escape (2.4.3).
Every shortcut is a convenience beside a control that a pointer and `Tab` reach.

| WCAG 2.1.4 Character key shortcuts | How it is met |
|---|---|
| a single-character shortcut (`/`, `?`) can be turned off, remapped, or acts only on focus | neither acts while focus is in a text field, a `menu`, a `listbox` or a `grid`, so a typed `/` or `?` types itself; with focus elsewhere it acts, which is the conformant "active only" case for a page with no typing target in focus. `Q` (UX-14) inherits the same matcher |

Known traps that apply:
* *Splitting a screen breaks what pointed into it* — `BarSearch`/`SearchMenu` are replaced. Grep
  `#search-menu`, `search-row-`, `app.searchmenu.*`, `data-tour`, `Search everything` and
  `Take the tour again`. The id and the accessible name the walks use are kept
  (`e2e/search.test.mjs:275-307`); the walks naming the tour row are re-pointed in step 7
  (`e2e/shell.test.mjs:85`, `e2e/instanceplace.test.mjs:46-47`).
* *A capability test can ask itself* — the P-05 unit tests assert against literal role tables
  from `e2e/fixture.mjs`'s `ROLES` shape, not against `mayDo`'s own answer.
* *A live region created already filled is not announced* — the hit count is announced through the
  existing `announcer`, never a region mounted with text.
* *`locales/*.json` is grouped, not sorted* — the new codes go by hand beside `app.searchmenu.*`.
* *The design-system gates read comments* — no element names in angle brackets or pixel values in
  the new comments.
* *`engine.reset()` clears every subscription* — the palette's hub-level reads are opened while it
  is open and closed with it; nothing module-level holds one. The membership scopes it opens stay
  open for the session, as every `people.open` does (its cleanup is empty, `people.svelte.ts:54-58`;
  `SearchView.svelte:224-227` is the precedent), and a reset re-reads them through the same store.

**Two writers at once:** none. The palette writes nothing. An action it runs is the screen's own
write, guarded as today.

## 3. Decisions

- [x] D1 **One palette, two hosts.** From `medium` up the bar's field *is* the palette's input
  and the panel opens under it, focus staying in the field, as the bar search does today. Below
  `medium`, where the bar has no field (§11.2), the shortcuts **and the bottom bar's *Search***
  open the same panel with its own field in a `Dialog`; its *All results* and *Open search* lead to
  `/search`, so a phone reaches the palette by tap and the search page through it. The panel has a
  minimum inline size from the layout tokens, so a narrow bar field does not squeeze it. One
  component and one row engine serve both. — decided by: worker; the bottom bar's *Search* by the
  coordinator. Reason: UC-WRK-18 check 1 says "typing in the bar", and the bar's walks rely on a
  combobox there; a touch phone has no `⌘K`. Rejected: a modal palette on every width with the bar
  as a button (it breaks that check, its walks and §11.2's field), and a second palette for phones
  (two answers to one question).
- [x] D2 **Enter with nothing highlighted still means the words**: "All results" with words,
  "Open search" without, the row the key is drawn on (design-system.md §11.4, ADR-0066). Arrows
  highlight, Enter performs the highlighted row (check 5). The highlight follows a row's identity
  rather than its index, so hits arriving late do not move it onto another row. The *All results*
  row says what Enter does through its `aria-describedby` ("Enter"), so a screen reader hears where
  the key lands without a highlight. — decided by: worker. Reasons: the entries arrive 200 ms after
  the local rows, so an automatic highlight would change what Enter does while somebody presses it;
  UC-WRK-18 and the walks in `e2e/search.test.mjs` rest on Enter carrying the words to `/search`;
  and a wrong automatic choice runs an action, where a wrong search costs a Back. Rejected:
  highlighting the first match automatically.
- [x] D3 **The actions "here" are the head's own.** Each of the six views with head actions hands
  the palette the same `primary` (with its list), `secondary` and `menu` it hands `PageHeader`,
  through a webapp registry (`lib/palette/commands.svelte.ts`, `offer(source, list)` with a
  cleanup, like `page.offer`). An item with a `disabledReason` is not listed. A collection also
  offers its layouts (*Show as board* …) through the same registry. **"Here"** is the page head's
  lists, plus the open detail pane's entry menu while the pane is open (its `ItemView` offers like
  any head). Not here: the actions in the page's body — a row's menu, the list's add form, a
  board column's menu — because they act on one row or column the palette cannot name, and the
  entry menu everywhere is UX-16's; the bulk bar, because it acts on a selection, which the palette
  would close. Each view builds the lists once (`offered`) and hands the same value to the head and
  the registry. The filter over a list (drop what has a reason, flatten the primary's list) is a
  pure function in `lib/palette/actions.ts`. — decided by: worker; the extent of "here" by the
  coordinator. Reason: the head
  already applies P-05, and a second permission computation in the palette would be a second answer
  that drifts. Rejected: widening `PageHeader`'s `onmenu` to every width (a design-system component
