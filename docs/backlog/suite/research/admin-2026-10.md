# Configuration architecture for Hubtask: Atlassian, peers, standards, recommendations

Research date: 2026-10-28. Sources are listed per section. Anything I could not confirm against a primary source is marked **(unverified)**.

## 1. Atlassian administration, 2025–2026

### 1.1 The layers

| Layer | Where | What is configured there |
|---|---|---|
| **Organization** | admin.atlassian.com | Users, groups, managed accounts (verified domains), app access (renamed from "product access" in 2025, since Atlassian now calls its "products" "apps"), billing, release tracks, sandboxes, audit log, data residency. |
| **Atlassian Guard** (formerly Access) | admin.atlassian.com, paid add-on | SSO/SAML, SCIM user provisioning, authentication policies, data security policies (e.g. block export or public links), external-user policies, mobile app policies, detection alerts. |
| **Site / app admin** | inside each app (Jira, Confluence, JSM) | Global Jira configuration: work types (formerly issue types), statuses, workflows, custom fields with contexts, screens, every scheme, global permissions, global automation, Assets. |
| **Space admin** (Jira "projects" were renamed "spaces" starting Sept/Oct 2025) | inside the space | In a **company-managed** space: pick schemes, roles, components, versions, space automation. In a **team-managed** space: its own work types, fields and workflow, local to that space. |
| **Users** | their profile | Notifications (partly), personal filters and dashboards. |

Sources: release tracks https://support.atlassian.com/organization-administration/docs/what-are-release-tracks/; projects become spaces https://community.atlassian.com/forums/Jira-articles/Evolving-Jira-terminology-Projects-will-soon-be-Spaces/ba-p/3034977 and https://community.atlassian.com/forums/Jira-articles/Jira-Spaces-have-landed/ba-p/3117620; products become apps https://confluence.atlassian.com/x/mdjCP.

### 1.2 The scheme model of company-managed Jira

A company-managed space is the sum of independently assigned schemes:

- **Permission scheme**: who may browse, create, transition, delete and so on, granted to roles, groups or fields.
- **Notification scheme**: which events email whom.
- **Workflow scheme**: which workflow applies to which work type.
- **Work type scheme**: which work types the space offers.
- **Work type screen scheme → screen scheme → screens**: which screen appears for *create*, *edit* and *view*, per work type. That is three levels of indirection.
- **Field configuration scheme → field configuration**: whether a field is required, hidden, which renderer it uses, its description. **Being replaced in 2026** by one *field scheme* that maps fields to work types and spaces. Field *contexts* (defaults and options per space or work type) stay separate. Sources: https://support.atlassian.com/jira-cloud-administration/docs/what-are-field-schemes/ and https://community.atlassian.com/forums/Jira-Cloud-Admins-articles/Announcing-General-Availability-of-Field-Schemes/bc-p/3247472. Planned caps are 700 fields per configuration and 150 work types per scheme.
- **Issue security scheme**: levels that limit which items a person can see.
- **Priority scheme**: which priorities a space offers.
- **Custom field context**: default values and option lists per space or work type. It sits in a different place from the field configuration, which controls whether a field is required.

So "is field X required, visible, defaulted and editable on create in space P for type T?" has **four or five answers spread across separate objects**: screen, field configuration, context, workflow validator, plus apps such as ScriptRunner Behaviours. Atlassian's own KB article "Issue creation fails silently after entering all field data" exists because a field marked required in the field configuration can be missing from the create screen (https://support.atlassian.com/jira/kb/issue-creation-in-jira-fails-silently-after-entering-all-field-data/).

### 1.3 Team-managed vs company-managed

Team-managed spaces (formerly "next-gen", 2018) keep all configuration local: one workflow per work type, fields local to the space, simple roles. Company-managed spaces share schemes. Known gaps and pains:

- **The type cannot be converted.** Moving between the two means creating a new space and moving the items. Sprints do not move company-managed → team-managed, and custom fields must be recreated (https://confluence.atlassian.com/jirasoftwarecloud/migrate-from-a-next-gen-project-to-a-classic-project-957974933.html).
- Team-managed fields are local, so "Story Points" may exist N times, which breaks cross-space reporting, JQL and Advanced Roadmaps/Plans.
- Feature gaps have narrowed over the years (team-managed now has automation, approvals in JSM, sprints, roadmaps), but there is still no shared scheme, no issue security scheme, limited field-level control, and fewer app integrations.
- **Convergence:** Atlassian's visible direction is to *simplify company-managed* (field schemes replacing two layers, a modernized create dialog, a new workflow editor, "space templates") rather than to merge the two types. I found **no official announcement of a merge (unverified)**. Practitioner posts from late 2025 and 2026 still treat them as two models (https://us.seibert.group/blog/team-managed-company-managed).

### 1.4 Create screen vs forms vs portal: the owner's example

Jira has **at least four entry paths** into one work item, each with its own rules:

1. **Global "Create" dialog**: uses the create screen and field configuration. It can make a field required or optional and hidden or shown, but has **no conditional logic**, no per-field lock, and no section logic. Since 2025 the create dialog has been "modernized" (simple create, plus the full layout when needed) (https://jirareleases.atlassian.com/announcements/a-faster-way-to-create-new-work-in-jira).
2. **Jira forms (ProForma, acquired 2021)**: has conditional sections, validation and field linking. Forms are a **separate path**: reached from the space's Forms tab or a form URL, attached to an item, or used through the portal. The request "Allow selecting a Jira Form when using the global Create button" is still open (https://jira.atlassian.com/browse/JRASERVER-79275). An employee can therefore always go around the form by using Create.
3. **JSM portal + request types**: each request type maps to one work type and carries its own field list, labels, help text and hidden fields with presets, plus optional forms. Fields added to a request form can disappear if they are not also on the work type's screens. Re-adding them also re-adds them to screens, which changes what customers see (https://community.atlassian.com/forums/Jira-Service-Management/Custom-Fields-added-into-Request-Type-Forms-are-hidden/qaq-p/3123623). The work type field itself cannot be hidden on the create screen of a JSM space (https://community.atlassian.com/forums/Jira-Service-Management/Is-there-a-way-to-hide-Issue-Type-on-quot-Create-quot/qaq-p/2495090).
4. **Email, API, automation, CSV import**: these bypass screens. Only workflow validators on the *create transition* (and field configuration "required" for REST) apply.

The lesson: **layout and validation are attached to the entry path, not to the record type.** A rule that must hold for every item has to be written as a workflow validator, an automation rule, or an app script (ScriptRunner Behaviours), which is yet another place.

### 1.5 Automation, Assets, sandbox, release tracks, config as code, AI

- **Automation**: rules are scoped as global, multi-space or single-space. Rule actors, execution limits per plan, and an audit log per rule. Global rules belong to site admins and space rules to space admins, so the same logic gets duplicated per space.
- **Assets** (from Insight, acquired 2020): object schemas, object types with attributes and references; the CMDB for JSM. It has its own permission model (schema roles), separate from Jira permissions.
- **Sandbox** (Premium/Enterprise): an isolated copy linked to production. Data can be copied in. Configuration is promoted by hand or through **"copy configuration"/JCMA-style space copy (unverified for the exact feature name in 2026)**. Atlassian has no general config deploy pipeline.
- **Release tracks** (Premium/Enterprise): Continuous; Bundled (monthly, second Tuesday, 22:00 UTC); and Preview for sandboxes, which receive the bundle one month early. This protects admins from *Atlassian's* changes, not their own.
- **Config as code**:
  - REST API: complete but scattered, with separate endpoints per scheme type.
  - **Atlassian CLI (`acli`)**: official since 2025. It covers work items, boards, sprints and since v1.3.5 (Oct 2025) custom fields. Admin commands cover users, not schemes (https://developer.atlassian.com/cloud/acli/changelog/, https://developer.atlassian.com/cloud/acli/reference/commands/admin/).
  - **Terraform**: the official `atlassian/atlassian-operations` provider covers only JSM Operations (teams, schedules, escalations) (https://support.atlassian.com/jira-service-management-cloud/docs/set-up-atlassian-operations-terraform-provider/). Jira configuration has only community or partner providers (e.g. PlanApply). Customers have asked for an official provider for years (https://jira.atlassian.com/browse/JRASERVER-72890).
  - **JCMA / Cloud Migration Assistant**: moves Server/DC to cloud, including configuration. Partner apps (e.g. Configuration Manager for Jira by Appfire) fill the sandbox → production gap.
- **Rovo / AI admin**: Rovo agents (Agent Studio) can be scoped to spaces and work types (https://support.atlassian.com/rovo/docs/configure-tools-for-rovo-agents/). Community posts describe natural-language workflow editing ("add a transition restricted to space leads"). I could not confirm an official, documented Rovo **admin** agent that plans and applies configuration with a diff **(unverified)**.

### 1.6 Well-documented pain points

1. **"Which screen applies?"** Three levels (work type screen scheme → screen scheme → screen) plus field configuration plus context. Silent create failures (KB above).
2. **Scheme sprawl**: one admin reports cleaning 252 field configurations down to 11 and 250 field configuration schemes down to 15, leaving 131 statuses alone (https://community.atlassian.com/t5/Jira-articles/Tidying-Up-Jira/ba-p/1748466). Atlassian itself had to introduce configuration limits and "optimisation" reports (https://www.atlassian.com/blog/how-we-build/optimisation-tools-for-jira).
3. **Two project models** with no conversion path and duplicated fields.
4. **Entry-path inconsistency**: create, forms, portal and email each validate differently, and forms cannot be forced on Create.
5. **Duplicate mechanisms for one need**: required fields can come from the field configuration, a validator, a form or Behaviours. Visibility can come from screens, field configuration, issue security, request type hidden fields or forms. Notifications come from schemes, automation "send email" or JSM customer notifications.
6. **Split admin roles**: org admin, site admin, Jira admin, space admin and Assets schema admin are separate, and nobody sees the effective configuration.
7. **No first-class promotion or rollback** of configuration. Sandbox to production is manual or needs a paid app.

## 2. How other products do it

| Product | Model | Patterns worth copying |
|---|---|---|
| **Linear** | Workspace → Team (sub-teams since 2025 **(unverified)**) | Workspace-wide labels, statuses per team in fixed **status categories** (Backlog, Unstarted, Started, Completed, Canceled, Triage). Templates for issues, projects and documents at workspace or team level. Very few settings; strong opinions. https://linear.app/docs/configuring-workflows, https://linear.app/docs/issue-templates |
| **monday.com** | Account → Workspace → Board | Account admin vs workspace owner vs board owner. Board permissions are presets ("edit everything", "edit rows assigned"). **Workspace templates** and "managed templates" (Enterprise): a template whose updates propagate to the boards created from it. https://support.monday.com/hc/en-us/articles/4405738298130 (managed templates) **(URL unverified)** |
| **ServiceNow** | Instance → scoped application → table/record | "**Configure, don't customize**": configuration uses platform features and survives upgrades, while customization (scripts on base tables) makes upgrades harder. **Update sets** capture configuration changes as XML for promotion dev → test → prod, with preview showing conflicts before commit. **Scoped apps** are namespaced bundles. **Instance Scan** lints configuration against best-practice checks. **Skipped records** after upgrade show where local changes diverge from the base. https://www.servicenow.com/docs/ (update sets, Instance Scan) |
| **Salesforce** | Org → profiles + permission sets (+ permission set groups) → object → record type | **Record type** = page layout + picklist values + business process. **Validation rules and flows run at the object level**, so they apply to UI, API, import and integration alike. That is the single place the owner is looking for. **Dynamic Forms** put visibility logic into the layout. **Sandboxes** (developer, partial, full), **change sets**, **Metadata API / Salesforce CLI (sf)** with source tracking and **deploy --dry-run (checkonly)**. Profiles are being slimmed down in favour of permission sets (profile permissions end-of-life announced, then postponed **(unverified timing)**). https://developer.salesforce.com/docs/atlas.en-us.api_meta.meta/api_meta/, https://help.salesforce.com/s/articleView?id=sf.fields_about_field_validation.htm |
| **Notion** | Workspace → teamspace → page/database | Teamspace owners vs workspace owners. Permissions inherit down the page tree with explicit overrides. Database templates and properties. Admin can restrict teamspace creation and guest invites. https://www.notion.com/help/intro-to-teamspaces |
| **GitLab** | Instance → group → subgroup → project | **Cascading settings**: a value is inherited from the nearest ancestor that sets one, and an ancestor can **lock** it ("enforce for all subgroups"). The UI shows a lock icon with "set by group X". Resolution order: locked ancestor → locked instance → own value → nearest ancestor → instance default. Cascading is opt-in per setting. https://docs.gitlab.com/development/cascading_settings/ |
| **Google Workspace** | Organization → nested OUs (+ configuration groups) | Settings inherit down OUs, a child can **override**, and the console shows "Inherited" vs "Overridden". Groups can override an OU for selected services. https://support.google.com/a/answer/4352075 |
| **Microsoft 365 / Entra / Intune** | Tenant → admin units → groups | **Role-based admin** with built-in least-privilege roles. Conditional Access **"What If" tool** and **report-only mode** to simulate a policy before enforcing it. Configuration as code via Graph and Microsoft365DSC **(community project)**. https://learn.microsoft.com/entra/identity/conditional-access/what-if-tool |
| **Terraform / Kubernetes** (patterns, not competitors) | Declarative desired state | `plan` → reviewed diff → `apply`; drift detection; `kubectl diff` / server-side dry run; admission policies (OPA/Kyverno) as config linting. |

### Extracted patterns

1. **Inheritance with locks and visible provenance** (GitLab, Google, and Hubtask's own source mark): every effective value says where it came from and whether a parent locked it.
2. **Rules on the record type, not the entry path** (Salesforce validation rules and record types): one definition governs UI, API, import, email and agents alike.
3. **Simulation / "view as"** (Entra What If, report-only mode; Salesforce "Login as"; Jira "permission helper"): answer "can person P do X on item I, and why?"
4. **Configuration linting / health** (ServiceNow Instance Scan, Atlassian optimisation reports): unused objects, conflicting rules, unreachable statuses, required fields with no input path.
5. **Versioned configuration with promotion and rollback** (update sets, change sets, SFDX source tracking).
6. **Declarative plan/apply** (Terraform, `sf project deploy --dry-run`): the same format for export, review, apply and diff.
7. **Templates with an upgrade path** (monday managed templates, ServiceNow skipped records): instances remember their template version and can take updates, with a three-way diff where they diverged.
8. **Configure, don't customize**: a bounded set of primitives instead of scripts, which keeps upgrades and analysis possible.
9. **Few, opinionated status categories** (Linear, Jira's To do / In progress / Done): reports work across any custom workflow.

## 3. Industry standards and the primitives they need

The aim is that each standard is a **template** (blueprint) on generic primitives, not a feature module. The primitive catalogue, cited by letter below:

- **P1 Typed entries** with type-specific fields (custom fields with types, options and defaults).
- **P2 Statuses with categories** (open / active / waiting / done / cancelled) and **transitions with conditions, required fields and approvals**.
- **P3 Typed links** between entries and to external records (blocks, caused-by, duplicates, implements, affects-CI, parent/child beyond the five levels).
- **P4 Registers**: a collection whose entries are records rather than work (risks, CIs, assets, controls, processing activities). Same engine, different presets.
- **P5 Time boxes**: iterations, stages, increments with start and end, and membership of entries.
- **P6 Estimates and actuals**: points, hours, cost, with roll-up across levels.
- **P7 Clocks and SLAs**: targets per type, priority or class of service; business calendars with holidays; pause conditions; breach events.
- **P8 Approvals**: single, multi-person, quorum, sequential; a group as approver (CAB); recorded decision with reason.
- **P9 Rules/automation**: event → condition → action, scoped the same way as settings.
- **P10 Metrics**: cycle time, lead time, throughput, WIP, aging, burn-up/down, cumulative flow, SLA attainment. Derived from the status-category history, so P2 must store transitions with timestamps.
- **P11 Baselines and snapshots**: frozen copy of plan values (dates, cost, scope) for variance.
- **P12 Thresholds / tolerances**: numeric limits on a container (WIP limit, cost tolerance, time tolerance) that raise an exception event when crossed.
- **P13 Intake forms and catalogue**: a published list of offerings, each mapping to a type with its fields. Same layout as P1, not a separate form engine.
- **P14 Knowledge**: articles linked to entries, with review dates.
- **P15 Audit trail and retention**: who changed what, when; immutable for compliance standards.
- **P16 Roles per container**: named accountabilities (Product Owner, Change Manager, Risk Owner) bound to people per hub or collection.

### 3.1 ITIL 4 and ISO/IEC 20000-1

ITIL 4 defines 34 practices: 14 general management, 17 service management and 3 technical management (https://www.axelos.com/certifications/itil-service-management, now PeopleCert). PeopleCert announced an updated ITIL ("ITIL Version 5") for 2025–2026 **(unverified scope)**. The practices a work tool must carry:

| Practice | Concrete needs | Primitives |
|---|---|---|
| Incident management | Incident type; impact × urgency → priority matrix; assignment groups; response/resolve SLAs with business hours; major-incident flag and swarming; link to CI and problem | P1, P2, P3, P7, P9, P16 |
| Service request management | Catalogue items with their own fields; approvals; fulfilment tasks generated as children | P13, P8, P9, child entries |
| Problem management | Problem and known-error records; root cause field; workaround; links to many incidents | P1, P3, P14 |
| Change enablement | Change types (standard / normal / emergency); risk assessment; **CAB approval**; change calendar and freeze windows; implementation, backout and test plans; post-implementation review | P8, P5 (calendar), P2, P1 |
| Service level management | SLA/OLA definitions per service and customer; calendars; reporting of attainment | P7, P10 |
| Knowledge management | Articles, lifecycle (draft → reviewed → published → retired), link to incidents | P14, P2 |
| Service catalogue management | Published services, offerings, who may request what | P13, P16 |
| Service configuration management / IT asset management | CIs with types, attributes and relations (runs-on, depends-on); asset lifecycle; impact analysis | P4, P3 |
| Release management | Release record grouping changes; dates; deployment status | P5, P3 |
| Monitoring and event management | Inbound events (webhook/mail) → incident with de-duplication | Intake (P13) + P9 |
| Continual improvement | Improvement register (CSI), with value, owner and status | P4, P2 |
| Relationship management | Customers/stakeholders as records; link to services and requests | P4, P3 |

**ISO/IEC 20000-1:2018** asks that the service management system demonstrably operates these processes. A tool helps with clause 8 (operation: service catalogue 8.2.4, change 8.5.1, incident 8.6.1, service request 8.6.2, problem 8.6.3, configuration 8.2.6, service level 8.3.3, release 8.5.3, information security 8.7.3 **(clause numbering from memory, unverified)**), plus documented information (records retained and controlled → P15) and performance evaluation (→ P10). https://www.iso.org/standard/70636.html

### 3.2 Scrum, Kanban, scaled agile

**Scrum Guide 2020** (https://scrumguides.org/scrum-guide.html):

- Accountabilities: Product Owner, Scrum Master, Developers (P16).
- Events: Sprint, Sprint Planning, Daily Scrum, Sprint Review, Sprint Retrospective. The tool needs the Sprint (P5) and optionally scheduled event entries.
- Artifacts with commitments:
  - Product Backlog ↔ **Product Goal**
  - Sprint Backlog ↔ **Sprint Goal**
  - Increment ↔ **Definition of Done**
- Tool needs: ordered backlog (rank), sprint container with a goal field, a DoD as a checklist or policy attached to the collection, estimates and velocity (P6, P10), burndown.

**Kanban**: there are two guides, *The Kanban Guide* by ProKanban.org (https://kanbanguides.org/) and Kanban University's *Kanban Method* (https://kanban.university/kanban-guide/). Needs:

- Visualised workflow with columns mapped to status categories (P2).
- **WIP limits** per column, swimlane or person (P12).
- **Explicit policies** shown on the board, such as entry and exit criteria per column. These are text plus enforceable conditions.
- **Flow metrics**: WIP, throughput, cycle time, work item age (P10).
- **Service Level Expectation**: e.g. "85% within 10 days", shown against aging.
- **Classes of service** (expedite, fixed date, standard, intangible) with their own policies and SLE (P7, P12).
- Blocked flag with reason and duration.

**Scaled agile**:

- **SAFe 6.0** (https://framework.scaledagile.com/): Agile Release Train (team of teams), **PI Planning** (8–12-week increment, P5 at a higher level), PI Objectives with business value, **program/ART board** showing features × teams × iterations with dependency links (P3), **ROAM risks** (Resolved, Owned, Accepted, Mitigated: a register with a status set, P4), Epics with a portfolio Kanban and lean business case, WSJF prioritisation (computed field).
- **LeSS**: one Product Backlog for many teams, an overall Sprint, multi-team refinement. The tool needs one backlog collection fed by several teams.
- **Scrum@Scale**: Scrum of Scrums and a MetaScrum. That is hierarchy of teams plus a shared backlog.

### 3.3 Project and portfolio management

- **PMBOK 7** (2021) is principle- and performance-domain-based; PMI released **PMBOK 8 in late 2025 (unverified)**. Needs: WBS (the hierarchy), schedule with dependencies and baseline (P3, P11), cost, risk register, stakeholder register, change log.
- **PRINCE2 7** (2023, https://www.axelos.com/certifications/propath/prince2-project-management):
  - **Management stages** (P5).
  - **Tolerances** on time, cost, scope, quality, risk, benefit and sustainability, set per level (project board → project manager → team manager). This maps naturally to P12 with inheritance and locks.
  - **Exceptions** when a forecast exceeds tolerance, raised as an exception report entry.
  - **Issue register, risk register, quality register, lessons log, daily log** (P4).
  - Issue and change control (request for change, off-specification, problem/concern), with **Change Authority** as approver (P8).
  - **Product-based planning**: product breakdown, product descriptions, product flow (typed entries and dependency links).
  - Highlight, checkpoint and end-stage reports (generated from data).
- **ISO 21502:2020** (project management guidance, replaces ISO 21500:2012 as the practice standard), plus **ISO 21500:2021** (context and concepts). Same needs at a generic level: governance roles, plans, controls, change control, closure. https://www.iso.org/standard/74947.html
- **IPMA ICB4**: a competence baseline for people, not processes. It needs little from a tool beyond roles.
- **MoP (Management of Portfolios)** and **portfolio management in general**: a portfolio as a container of programmes and projects, with categorisation, scoring (computed fields), capacity, roadmap, and periodic review gates (P8).
- **RAID log**: Risks, Assumptions, Issues, Dependencies. Four register types with owner, probability × impact score, response, review date.
- **OKR**: Objectives with Key Results (numeric start, target, current; confidence), a time box (quarter), alignment links to parent objectives and to the work that moves them (P3, P5, P6 extended to arbitrary measures).

### 3.4 Other standards worth supporting

- **BPMN-lite approval flows**: sequential and parallel approval steps, gateway on a field value, timer escalation, and generated tasks. A transition graph with conditions (P2), plus approvals (P8), plus rules (P9). Full BPMN 2.0 is out of scope.
- **ISO 9001:2015 §10.2 Nonconformity and corrective action (CAPA)**: nonconformity record → containment → root cause → corrective action(s) with owner and due date → **effectiveness check** after a delay → closure. Also documented-information control (§7.5): versioned documents with approval. Needs P1, P2, P3, P8, P9 (timer), P15. **ISO 9001 revision expected ~2026 (unverified)**.
- **ISO/IEC 27001:2022**:
  - Risk assessment and **risk treatment plan** (§6.1.2–6.1.3).
  - **Statement of Applicability** over the **93 Annex A controls**. A controls register with applicability, justification, implementation status, owner and evidence links.
  - Internal audit and management review as recurring work.
  - Needs P4, P3, recurring entries, P15.
- **GDPR Art. 30 Records of processing activities**: a register of processing activities (purpose, categories of data and subjects, recipients, transfers, retention, TOMs). **DPIA** (Art. 35) as a workflow. **Data subject requests** (Art. 15–22) with a one-month deadline (P7 with calendar days). **Breach notification** within 72 hours (Art. 33). https://gdpr-info.eu/art-30-gdpr/
- **DevOps / DORA metrics**: deployment frequency, lead time for changes, change failure rate and time to restore. A fifth, "deployment rework rate", was added in 2024–2025 **(unverified naming)**. Needs deployment and change records from CI/CD (intake), links from incident to change, and P10 over them. https://dora.dev/guides/dora-metrics-four-keys/
- **Lean A3**: one structured page (background, current state, target, root cause, countermeasures, plan, follow-up). A typed entry with a fixed field layout and child tasks. Also **PDCA** as a status set.

### 3.5 What this means for the primitive set

Almost all of section 3 is covered by **P1–P16**. The ones Hubtask most likely does **not yet** have as first-class primitives (to verify against the domain model) are:

- **Registers (P4)**: entries that are records, not work.
- **SLA clocks with business calendars (P7)**.
- **Multi-party approvals (P8)**.
- **Thresholds/tolerances that raise exceptions (P12)**.
- **Baselines (P11)**.
- **A catalogue as an entry path (P13)**.

Each standard is then a blueprint: types + fields + status sets + link types + rules + roles + views + reports.

## 4. Recommendations for Hubtask

### 4.1 One configuration model

**Every configurable thing is a *setting* (a typed value) or a *definition* (a typed object: type, field, status set, link type, rule, view, form/layout, role, blueprint).** Both live in one registry with one schema. Both resolve along one chain:

```
Hubtask default → Installation → Plan → Workspace → Hub → Collection
```

Each node may **set** a value, **lock** it (children cannot change it), or **restrict** it (children may only choose from a subset or within a range, e.g. a WIP limit of at most 10, or one of these three status sets). That is the existing source mark plus lock, generalised from 8 preset settings to everything. Per value, the UI and API always return `{effective, source, locked_by, allowed}`. The GitLab resolution order is the model: locked ancestor wins → own value → nearest ancestor → default.

**One solution per feature**, as an explicit design rule, with a gate if possible:

| Need | The one place | Not also in |
|---|---|---|
| Required, visible, default, validation of a field | The **entry type's layout** (field rules with conditions), enforced in the application layer for **every** entry path: web, API, MCP, CLI, mail intake, import, catalogue | Screens per path, form-specific rules, workflow validators |
| Who may do what | **Roles** (capability bundles) bound per workspace/hub/collection | Per-field hacks, per-automation actors with extra rights |
| What happens on an event | **Rules** (event → condition → action) | Notification schemes separate from rules |
| Who gets told | Notification **rules** over the same events, plus personal preferences | |
| Intake for outsiders | A **catalogue entry** that *references* a type and layout and may only hide or preset fields | Its own field list |
| Visibility of entries | Container membership + role, plus at most one item-level restriction mechanism | Several security models |

This directly fixes the owner's example. **The form is the layout of the type.** The "Create" button, the portal and the agent all render or validate the *same* layout. A portal or catalogue entry can only *narrow* it (preset or hide), never add logic of its own. Salesforce record types plus object validation are the precedent.

### 4.2 Who configures what, at which level

| Level | Role | Configures | Typically locks |
|---|---|---|---|
| Installation | Operator | Infrastructure, mail, storage, auth providers, retention ceilings, feature availability, installation-wide blueprints, hard limits | Security, retention, limits |
| Plan | Provider (purchase platform) | Which features and quotas a plan includes; plan-default blueprints | Quotas, feature flags |
| Workspace | Workspace admin | Identity (SSO/SCIM), roles, workspace-wide types/fields/status sets/link types, catalogue, calendars, blueprint library, data policies | Shared vocabulary (types, fields, status categories) that reporting relies on |
| Hub | Hub owner | Which blueprints and types are available, hub roles, hub rules, defaults for its collections | Process for its collections (e.g. change needs CAB) |
| Collection | Collection owner | Preset/blueprint chosen, columns, WIP limits, views, local rules and local fields **only where not locked** | — |
| Person | Everyone | Personal notification preferences, views, filters | — |

Two rules prevent Atlassian's sprawl:

1. **Definitions are shared by reference.** A local field is allowed only when no workspace field with the same meaning exists. Linting suggests promoting duplicates.
2. **There is no "team-managed vs company-managed" fork.** Only one model exists, and the lock decides how much freedom a collection has.

### 4.3 Blueprints (templates)

- A **blueprint** is a declarative, versioned bundle: types, fields, layouts, status sets with categories, link types, rules, roles, views, reports, sample entries, and **parameters** (e.g. sprint length, SLA targets, approver group).
- **Composition**: blueprints are composable modules, e.g. "ITSM core" + "Change enablement" + "CAB approvals". They declare dependencies and versions (semver).
- **Instantiation records provenance**. Each created object remembers `blueprint@version` and its parameters. Local edits are recorded as an overlay, not by copying.
- **Upgrade path**: a new blueprint version produces a **three-way diff** (old blueprint, new blueprint, local overlay) with conflicts listed, applied through the same plan/apply as any change. This is ServiceNow's skipped-records idea done properly.
- **Scope of publication**: Hubtask-shipped, installation, plan, workspace. A workspace can lock "collections in this hub must use blueprint X ≥ 2.0".
- The existing presets List / Tasks / Project / Flow become the first four blueprints. ITIL, Scrum, Kanban, PRINCE2, OKR, RAID, CAPA, ISO 27001 SoA and GDPR RoPA follow as library blueprints on the same primitives (section 3).
- **Export and import** as a file (YAML/JSON with a published JSON Schema), so blueprints can be shared, reviewed in git and diffed.

### 4.4 AI agents (and humans) configure through the same pipeline

One configuration API, exposed via REST, MCP and CLI, with these verbs:

1. **`schema`**: machine-readable description of every setting and definition kind, its levels, constraints and locks (JSON Schema). An agent discovers what it may change without docs.
2. **`get --effective`**: resolved configuration for a container, with source and lock per value ("explain").
3. **`plan`**: takes a desired-state document or a patch and returns a **diff**. The diff includes what changes, at which level, which locks block it, **impact** (N collections, M entries affected; entries that would become invalid under new required fields), lint findings, and required permission. Nothing is written.
4. **`apply plan-id`**: applies exactly the planned diff, atomically, only if the base version is unchanged (optimistic concurrency). The actor may need a human approval for selected kinds (roles, retention, deletions); this is an approval primitive applied to configuration.
5. **`history` / `rollback version`**: every apply creates a configuration version. Rollback is a new plan that restores a version and is applied the same way.
6. **`simulate`**: "view as / what if": can person P create type T in collection C, which fields are required, which rule fires? This is Entra's What If for work management.
7. **`lint`**: health checks such as unused definitions, duplicate fields, unreachable statuses, required fields with no input on some entry path (impossible by design if 4.1 holds), rules that loop, locks that are overridden nowhere and could move up.

Safety properties:

- Agents act **as a person or a dedicated service identity with a role**. Authorisation lives in the application layer (rule 2).
- **Dry run is the default** for agents; apply is a separate, auditable call.
- Every apply writes an **audit entry** with actor, agent identity, plan, diff hash and reason. It contains no user content (rule 10).
- **Destructive changes** (removing a field with data, deleting a type) are never applied directly. They become a deprecate → hide → retain-for-period flow, in line with "anything that could irrecoverably delete user data" being an owner-level decision.
- Agents never see or emit credentials; secrets are references.
- The same desired-state file works from git in CI ("config as code"), so humans, agents and pipelines share one path.

### 4.5 What to avoid from Atlassian

1. **Schemes as indirection layers**: no scheme → scheme → object chains. Atlassian itself is collapsing field configuration schemes into field schemes in 2026.
2. **Entry-path-specific logic**: no separate rules for create screen, forms, portal and email.
3. **Two project models** that cannot be converted.
4. **Local duplicates of shared concepts** (N copies of "Story Points").
5. **Several mechanisms for one concern**: required (4 ways), visibility (5 ways), notifications (3 ways).
6. **Admin roles that do not see the effective result**: always show the resolved value with its source.
7. **Configuration without versioning, promotion or rollback**, which needs a paid marketplace app and a sandbox.
8. **Config-as-code as an afterthought** (no official Jira Terraform provider; CLI without scheme commands). Make the declarative format the primary API and build the UI on it.
9. **Unbounded growth**: set limits and lint from day one rather than introducing caps after the fact (700 fields per configuration, 150 work types per scheme).
