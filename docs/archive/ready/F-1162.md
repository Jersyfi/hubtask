## 3. Decisions

- [x] D1 The ledger is read through a function the migration owns, `applied_schema_versions()`,
  `SECURITY DEFINER`, `STABLE`, `plpgsql`, `SET search_path = public, pg_temp`, naming
  `public.goose_db_version`, granted to `hubtask_app` and revoked from `PUBLIC`, answering the
  applied versions as a `bigint[]` and `NULL` where there is no ledger — decided by: worker. The
  ledger stays closed to the application role (it must not be able to rewrite it), and numbers are
  all the function can answer. The set rather than the highest, because migrations apply out of
  order (§ 1). `plpgsql` so that `db/schema.sql`, applied without goose, still
  loads. Rejected: a view granted to the role (fails to create where the ledger is absent, and
  widens the grant surface); the migrate binary writing the version into a table the role can read
  (a second ledger that can disagree with goose's).
- [x] D2 The binary's embedded migrations must all be applied: any one missing is `behind` and not
  ready; all present and nothing higher is `ok`; all present and a higher version applied is `ahead`
  and ready. The report's `expected` is the binary's highest, `applied` the ledger's highest —
  decided by: deployment.md §5 (expand/contract: the old binary runs against the new schema; the
  new binary needs its own migrations). SQLSTATE 42883 (the function missing) means a database
  older than this migration: `behind`, `applied` read as `0`. `NULL` (no ledger) and every other
  error, a lost grant (42501) included, leave `migration` absent and readiness to the database
  probe, and are logged. A result that is not `behind` is cached for 30 seconds (a restore can move
  the schema back, so never for longer); `behind` is read again on every probe.
- [x] D3 `/startupz` stays "initialisation is complete" — decided by: worker. A failing startup
  probe makes the kubelet restart the container after its threshold, so a pod waiting for its
  migration would be killed in a loop instead of waiting; readiness is the gate that keeps traffic
  away, and the server logs the comparison once when it starts. observability-reliability.md §5 and
  deployment.md say so.
- [x] D4 A behind schema makes the report `down` (the pod will not serve) — decided by: worker; the
  ops listener's `/meta/health` then answers 503, as for any outage. Out of scope: a behind worker
  or scheduler process (ADR-0014 roles) is unready but still leases jobs; holding its background
  work back is a change to the runner, not to the health model, reported as a finding.
- [x] D5 The backup warnings count targets per workspace through the existing `Targets.Coverage`, in
  bounded transactions of the application role, in the background, served from the last count (the
  `KeyHealth` pattern: counted at start, and again when a report finds the count older than 15
  minutes) — decided by: worker. `backup_target` is under `FORCE` row level security, so a
  `SECURITY DEFINER` function owned by a non-superuser would count nothing; the per-workspace read
  needs no new privilege. Only enabled targets count. Rejected: a definer function (wrong on a
  managed database); counting on the report's path (one transaction per workspace).
- [x] D6 Before the first count, or when it failed, the report says so with a new code,
  `config.backup_coverage_unchecked` (info before the first count, warn after a failure; a failure
  keeps showing the last count beside it) — decided by: `Registry.AddWarningSource`'s contract (a
  source turns a failed read into a warning of its own) and `KeyHealth`'s precedent.
- [x] D7 The warnings are emitted only in single-tenant operation — decided by: worker, from
  backup-restore.md §1, §2 and §8.6. In provider operation the installation's backup is the
  operator's at the database level, and with tenant targets one workspace's target would clear
  `backup_not_configured` for every other workspace; A-12 watches targets per target there.
- [x] D8 Documents: deployment.md (D-5 rewritten as decided and closed — readiness compares, startup
  deliberately does not — and the rolling-update row), observability-reliability.md §5 (the
  `/startupz` and `/readyz` rows, the sentence on D-5), backup-restore.md §10 (a correction: §10
  said the codes wait for a workspace-facing check; they are emitted for a single-tenant
  installation from per-workspace counts) — decided by: worker. No ADR: ADR-0016 already gives readiness its meaning and the report its
  warnings.
- [x] D9 A target counts when it is enabled; whether it has a schedule is not asked — decided by:
  worker. The codes speak of targets (`not_configured`, `single_target`), and the message says no
  more than that. An enabled target with no schedule backs nothing up and clears the warning: a
  gap, named and reported to the coordinator rather than closed with a further code here.
- [x] D10 `config.backup_unencrypted` gains its plural form (known trap: a count needs the plural);
  de: not translated (the `config.` family in `de.json` holds only the instance file's codes) —
  decided by: worker.
