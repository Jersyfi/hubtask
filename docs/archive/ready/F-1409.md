## 3. Decisions

- [x] D1 `workspaceVerdict(manifest, permission)` in `capability.ts` (and `mayHere` in
  `capability.svelte.ts`): `undetermined` before the manifest, `permitted` when
  `workspace_permissions` holds it, otherwise refused with `app.gate.workspace_permission_missing`
  naming the permission — decided by: worker. `permissionVerdict` judges a role by the matrix;
  the administration is about the workspace itself, which `workspace_permissions` answers from
  every membership including groups'.
- [x] D2 A form or a section of writes is wrapped in `CapabilityGate` (inert, dimmed, reason
  beneath) rather than removed, so the auditor still reads what is configured; a per-row button
  (remove, release, rotate, enable) is absent where refused, its reason being the screen's gate —
  decided by: worker. Rejected: hiding the forms (the auditor's job is to read them); a gate per
  row (the same sentence twenty times).
- [x] D3 Each region asks the permission its write asks on the server (table in § 1), so a screen
  may carry two gates (sign-in: `STRUCTURE` and `MANAGE_MEMBERS`; backup and retention:
  `STRUCTURE` for test and run, `DELETE_CONTAINER` for the forms and the per-row changes; restore:
  `STRUCTURE`, and `DELETE_CONTAINER` for a destructive mode's real run) — decided by: worker. An
  administrator stops being offered the `DELETE_CONTAINER` ones too; that is the same defect,
  found while mapping, and it changes no use case's check (UC-BAK-01 and UC-LIF-01 already say
  the owner sets targets, schedules and rules).
