## 3. Decisions

- [x] D1 **Cancel deletion is a use case of its own**, `CancelTenantDeletion`,
  `POST /admin/tenants/{tenantId}:cancel-deletion`, beside suspend and resume — not a third mode of
  `shift`: it restores two things `shift` does not know (the earlier status, the rules). Decided by
  worker; the route follows `api-guidelines.md`'s `:verb` form as its neighbours do.
- [x] D2 **It returns the workspace to where it was.** Migration 0130 adds
  `tenant.status_before_deletion`; the deletion request writes it in its guarded `UPDATE`
  (`status_before_deletion = status`), the cancel restores it and clears it with `purge_after`. A row
  without one — requested by an older binary, or pending before this ships — returns `SUSPENDED`:
  fail closed, nobody regains access the operator did not choose, and *Resume* is one press away.
  Decided by worker (UC-INS-08 check 5, "restores the workspace"). Rejected: always `ACTIVE` — a
  workspace suspended for non-payment would come back open; always `SUSPENDED` — a mistaken deletion
  of an active workspace would need a second act to undo; reading the trail's `from` — the
  application does not read evidence back to decide.
- [x] D3 **A cancel never meets a purge in progress.** The grace job, once its guard decides to
  delete, marks the row (`tenant.purge_started_at`, migration 0130) in a write transaction *before* it
  removes a byte; the cancel's `UPDATE` requires `status = 'PENDING_DELETION' AND purge_started_at IS
  NULL`. Both write the same row, so one waits for the other and re-reads the condition: either the
  cancel lands first and the job finds the workspace not pending, or the mark lands first and the
  cancel is refused `admin.tenant_deletion_underway` (409). Under a hold the job does not mark (it
  removes nothing). Decided by worker (known trap "read-then-write without a lock"; the bytes-first
  order of `HardDelete.go:119-126`). Rejected: refusing a cancel once `purge_after` has passed — two
  clocks, a race at the edge, and a held workspace past its deadline must still be cancellable (D5).
- [x] D4 **The rules the deletion switched off come back on.** Migration 0130 adds
  `automation_rule.paused_for_deletion` (boolean, default false — no table rewrite); `DisableAll`
  sets it on the rules it switches off; the cancel switches exactly those back on and clears it.
  As enabling by hand does (`Rules.go:452-478`): a schedule's next moment is computed from *now*, no
  missed occurrence fires, and the tenant's poller is woken. Nothing in the workspace could change
  while it was pending (every credential refused), so the permission each rule was enabled under still
  stands; the cancel asks none again. The computation stays the automation package's
  (`NextOccurrence`): a small port in `admin`, implemented in `automation`, wired in
  `cmd/server/main.go`. Decided by worker (check 5, "restores the workspace": administrators cannot
  tell afterwards which rules were on). Rejected: leaving them off and saying so — it restores less
  than the check says, and the deletion's journal entry holds only a count.
- [x] D5 **Under a legal hold the cancel is allowed and the holds stay.** A cancel removes nothing, so
  it needs no hold check; it is the exit `data-protection.md` §5 and UC-LIF-06 name (PH-10 D4: cancel,
  then the release by the workspace's people, then a new request). Decided by
  `data-protection.md` §5 and PH-10 D4.
- [x] D6 **The operator's own workspace.** The client compares each row with its own workspace
  (`GET /tenant`'s id) and marks it; *Suspend* opens a confirmation naming the workspace for every row,
  and for the own one adds that the operator's session ends at once and the workspace is resumed from
  another operator's session; the delete dialog adds the same for the own workspace, and that a cancel
  then needs another operator. A warning, not a refusal, in multi mode: check 1 says so, and a
  multi-mode installation has a way back through another workspace's operator, or the server binary's
  `operator add` (UC-INS-03, SC-04). Decided by UC-INS-08 check 1 and milestone decision 3.
- [x] D7 **Single mode: no *New workspace*, no *Suspend*, no *Delete*.** In single mode the one
  workspace holds every operator (`is_operator`, `schema.sql:2631`): suspending it, or requesting its
  deletion, shuts everybody out of the installation, the operator included, with no way back — not
  even SC-04's `operator add`, which adds an operator to a workspace that refuses every credential —
  and a deletion that nobody can reach could never be cancelled, so check 5's promise would be false
  there. Milestone decision 3 (ADR-0077 §4: "it either refuses, or a way stays open") is applied: the
  server refuses `SuspendTenant` and `RequestTenantDeletion` in single mode with
  `admin.multi_mode_required` (403, its text widened from provisioning to the lifecycle), and the
  screen leaves the three controls out (P-05). *Resume* and *Cancel deletion* stay in every mode —
  they are the way back for a workspace suspended or pending before this ships. UC-INS-08 and
  UC-INS-07 serve D5–D7 only, so no check of theirs changes; UC-INS-07 check 4 is met by the absent
  button. Decided by worker under milestone decision 3. **Named to the coordinator** as the one point
  that removes something an operator can do today (in D1–D4).
- [x] D8 **No step-up and no typed name for a cancel.** It removes nothing and returns access, as
  *Resume* does, which asks for neither; both acts are in the trail and the journal. Decided by worker.
  Rejected: a step-up for symmetry with the request — the request asks one because it destroys.
- [x] D9 **Migration 0130**, expand only: three nullable or defaulted columns
  (`tenant.status_before_deletion tenant_status`, `tenant.purge_started_at timestamptz`,
  `automation_rule.paused_for_deletion boolean NOT NULL DEFAULT false`), and `admin_tenants()` dropped
  and created in the same transaction with `purge_started_at` (0121's precedent). A caller of the
  previous release names its columns and reads them unchanged; an older pod writes none of the new
  columns, which D2, D4 and the rolling-update row of § 2 bound. Decided by worker (rule 12).
- [x] D10 **The hold line says the way out.** `app.instance.legal_hold_waits` ("the deletion waits
  until every hold is released") is completed: nobody can release a hold while the workspace is
  pending, so it says that cancelling the deletion is what lets the workspace's people release it.
  Decided by worker (P-11; PH-10 D4).

Open for the owner: none. D7 is named to the coordinator, who may judge it owner-level.
