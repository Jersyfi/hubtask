## 3. Decisions

- [x] D1 Three use cases: `ListOwnPasskeys`, `StartPasskeyRegistration`, `CompletePasskeyRegistration`
  under `/accounts/me/passkeys` — decided by: worker; the provider connection's shape.
- [x] D2 The step-up is demanded by `start`, and the challenge it mints is bound to that session for
  five minutes; `complete` requires that challenge and that session — decided by: UC-ID-22 check 2
  (proof, then device) and identity.md §23.2–§23.3 (adding takes a step-up; the challenge is bound to
  the session). A step-up at `complete` would put the device first or run the ceremony twice. The task
  text is corrected.
- [x] D3 The verifier, per Level 3 §7.1: client data from the raw bytes (type `webauthn.create`, the
  challenge compared in constant time, the origin exact, `crossOrigin` not true, no `topOrigin`,
  `tokenBinding.status` not `present`, at most 4 KiB), hashed as received; the attestation object a
  CBOR map of `fmt` (≤ 32 bytes), `attStmt`, `authData`; in the authenticator data the RP ID hash, UP
  set (UV recorded, not required at registration), AT set, BS only with BE, the counter, the AAGUID
  read and discarded (no maker's name), the credential id ≤ 1023 bytes and equal to `raw_id`, the COSE
  key, the extensions parsed and consumed exactly when ED is set, no trailing byte. The CBOR subset:
  major types 0–5 and the simple values false/true/null (extensions such as `hmac-secret` use them);
  no tags, floats or indefinite lengths; depth 16, 64 KiB, no duplicate keys. COSE: EC2/P-256 with
  ES256 (uncompressed, on the curve), OKP/Ed25519 with EdDSA (32 bytes), RSA with RS256 (2048–4096
  bits, an odd exponent ≥ 3 that fits an int); the `alg` must match the key and be one of the three
  requested. Transports from a closed list (`usb`, `nfc`, `ble`, `hybrid`, `internal`, `smart-card`),
  at most six. The creation options: `rp.id` (punycode), `rp.name` (the workspace's name), `user.id`
  (the handle), `user.name` (the address, or the sign-in name of a managed account), `user.displayName`
  (the display name), the challenge, ES256/EdDSA/RS256, five minutes, `excludeCredentials` with their
  transports, resident key and UV `preferred`, attestation `none` — decided by: ADR-0085 §1,
  identity.md §23.3.
- [x] D4 The port has two phases: `ChallengeOf(clientDataJSON)` reads the challenge (shape only), and
  after the core has consumed the matching pending row, `VerifyRegistration` checks everything against
  the expected challenge, origin and RP ID. `auth_pending` gains the purpose `PASSKEY_REGISTER` and two
  columns, `session_id` (composite reference to the session, `ON DELETE CASCADE`) and `user_handle`; a
  CHECK requires both for that purpose and neither for any other. The challenge is the secret of a
  token under a prefix of its own (`hbt_pkr_`), so only its hash is stored and it can never equal
  another door's token; the purpose check at every door stays the second guard — decided by: worker;
  a stored challenge would keep what the hash need not.
- [x] D5 The user handle: 32 random bytes, carried on each credential row. `start`, under the account
  row's lock, takes the handle of the account's credentials, else of a live pending registration,
  else mints one — so an account normally has one handle. PK-03 looks a credential up by its id and
  checks the returned handle against the row's — decided by: worker; identity.md §23.3 (opaque, never
  the address). A column on `account` was rejected: it would travel in the account's records.
- [x] D6 The attestation statement is not verified, a deliberate deviation from §7.1 step 19: `none`
  must carry an empty statement; any other format is accepted with its statement unread. The
  statement only proves that a maker's key signed, and Hubtask trusts no maker's key — decided by:
  ADR-0085 §1 and identity.md §23.3 ("attestation `none`: the server checks no maker"), the owner's
  #1520. Browsers send `none` for this conveyance; the walk with real keys shows what arrives.
- [x] D7 Recovery codes: ten new codes where the account holds no unused one, read and replaced in
  the insert's transaction under the account lock — decided by: identity.md §9 ("they back every
  factor") and §23.2 ("when the account holds none"). Counting, regenerating and keeping them with a
  key alone, and `RECOVERY` as a step-up beside a key, are PK-02's and PK-04's (added to their task
  text in this commit).
- [x] D8 The name is chosen in the dialog (default "Passkey" and the next number, in the reader's
  language), 1–64 characters after trimming, no control characters — decided by: worker; UC-ID-22
  *Where it ends* ("the person names it").
- [x] D9 The relying party: the RP ID is the workspace's canonical `tenant_host`, or the derived host
  where there is no row, in ASCII form; the origin is the base URL's scheme, that host, and the base
  URL's port where it is not the default. Without a base URL there is none, and nothing is offered —
  decided by: identity.md §23.3, its origin row corrected in this commit (there is no development
  switch).
- [x] D10 The data backup keeps the table, as identity.md §23.5 says: an archive entity (`Later`,
  format 1 is additive) with its export and import statements; both exports leave the entity out
  entirely, a new rule beside `redactedFields` — decided by: identity.md §23.5 and tenant-export.md §9
  ("a copy of a credential is a credential" — for the exports). A restore brings back a key the person
  removed since, as it brings back an earlier password hash; and a person's export carries no passkey
  names or dates, as it carries no second factor today. Both said in tenant-export.md.
- [x] D11 `RevokeCredentials` removes the account's passkeys in every erasure mode — decided by:
  identity.md §23.5 and the milestone's matrix ("its credentials go with the erasure"). The same
  reading covers the other credential tables that survive anonymisation, but changing what an erasure
  deletes there is outside this task: a `finding`.
- [x] D12 Audit: `auth.passkey_registration_started` (info, as the enrolment's start) and

- [x] D13 The ceremony's refusals are not counted in the attempt ledger: a step-up has already proved

- [x] D14 No refusal of these routes is a 401: a stale challenge is 409 — decided by: worker; the

- [x] D15 The list answers `can_add` and its reason from the same function `start` asks (a person, a
