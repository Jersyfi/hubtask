## 3. Decisions

- [x] D1 The server answers `purge_after` on each trash entry: the earliest moment the automatic pass
  may remove it — `deleted_at` plus the period the pass reads (its floor applied), and never earlier
  than `deleted_at` plus the offline window — decided by: worker. The pass's own two numbers live on
  the server; a client that combined a rule it may not read with a window it is never told would be
  a second answer to "when". Rejected: exposing the window to the web app through the sync engine
  (still the wrong period, check 9, and a member reads none); rewording the screen to "at least N
  days" (does not meet check 6, whose wording is the owner's).
- [x] D2 The date is the earliest moment, not a promise: the pass runs on its own cadence, and a
  legal hold keeps an entry longer without a date (data-retention.md §4 item 1). The contract's
  description says "unless a legal hold keeps it" — decided by: worker.
- [x] D5 One home for the formula: `Policy.RemovableAfter(deletedAt, window)` in
  `core/domain/model/lifecycle/Retention.go`, beside `Cutoff`, with the floor applied the same way;
  `ListTrash` calls it, and the window it is given is the `cfg.Retention.TombstoneWindow` the Purger
  gets — decided by: worker. Rejected: computing it in the use case (a second statement of the
  pass's rule).
- [x] D3 Showing a member the date tells them, in effect, the trash period, which `/retention-policies`
  answers only to `retention:read`. Accepted: UC-LIF-02's *Goal* — "the person knows beforehand
  exactly what goes and when" — names PE-member among its actors, and no safeguard or gate changes.
  This reverses the silence `retention.svelte.ts` and `TrashView.svelte` describe for a reader
  without the right; both headers are updated in step 4 — decided by: worker; named in the pull
  request.
- [x] D4 The web app counts down to `purge_after` where it is present and keeps today's sentence
  where it is not (an older server) — decided by: worker.
